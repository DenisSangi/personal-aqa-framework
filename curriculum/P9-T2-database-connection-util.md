# P9-T2 — DatabaseConnectionUtil (JDBC)

**Фаза / слой:** Фаза 9 — Слой БД
**Теги:** java, sql

## Описание

Java-код впервые ходит в базу. Класс `DatabaseConnectionUtil` с двумя публичными методами и одним приватным:

- `getConnection()` — приватный, устанавливает соединение по параметрам из конфига;
- `executeQuery(String query)` → `List<Map<String, String>>` — для `SELECT`: каждая строка результата превращается в `Map` «имя колонки → значение», все строки — в список;
- `executeUpdate(String query, Object... params)` → `int` — для `INSERT`/`UPDATE`/`DELETE`, возвращает количество затронутых строк.

Плюс подготовка: JDBC-драйвер PostgreSQL в `pom.xml` и параметры подключения в конфиге.

Это прямой аналог боевого `DatabaseConnectionUtil.java` из ClinCard — с одним сознательным упрощением: там `getConnection()` получает временный токен через AWS IAM, у нас простой `user`/`password` (решение зафиксировано в `PLAN.md`). Всё остальное — один в один.

## Место в фреймворке

Зависимость: опирается на P9-T1 (база, схема, сид — есть куда ходить) и на Фазу 1 (`FrameworkConfig` — откуда брать параметры подключения).

От неё зависит: P9-T3 — тест, который через `executeUpdate` создаёт запись и через `executeQuery` её проверяет.

## Мотивировка

Пока что твой фреймворк проверяет только то, что видно снаружи: UI показал текст, API вернул JSON. Но огромный класс дефектов снаружи не виден — данные записались в базу не в ту колонку, потерялись при конвертации, сохранились с неверным статусом, продублировались. Пользователь этого не увидит, API вернёт `200`, а данные повреждены.

Слой БД закрывает именно это: тест может проверить **фактическое состояние системы**, а не только её ответ. В ClinCard это ровно то, что делает `ClinCardMergeProfilesI2cEUOnlyTest` — сливает профили через UI и SQL-запросом проверяет, что в базе действительно осталась одна запись с правильными связями.

Побочная, но важная для тебя польза: `try-with-resources` (тема, которую ты закрывал ещё в подготовке к EPAM) здесь не абстракция из теории, а необходимость — незакрытое соединение с БД это утечка ресурса, которая в CI кладёт весь прогон.

## Открытые вопросы (обсудим перед кодом)

### Вопрос 1 — статические методы или объект с состоянием?

Референс объявлен так:

```java
@AllArgsConstructor
public class DatabaseConnectionUtil {
    private final String rdsEndpoint, username, dbName;
    private final int port;
```

То есть это **объект**: параметры подключения передаются в конструктор, и в тесте создаётся экземпляр под конкретную базу. Логика такая: в ClinCard баз несколько (разные окружения, разные сервисы), и один и тот же класс должен уметь ходить в любую.

У тебя база одна, а `FrameworkConfig` отдаёт параметры статически (`FrameworkConfig.APP_URL` и т.п.). Вопрос: делать `DatabaseConnectionUtil` объектом с параметрами в конструкторе (как референс) или классом со статическими методами, берущими параметры прямо из `FrameworkConfig` (как твои `RandomDataGenerator`/`DateTimeUtil`)? Аргументируй — обе позиции защитимы, важно обоснование.

### Вопрос 2 — критика референса: что делать при `SQLException`?

Посмотри внимательно на два метода боевого класса — они ведут себя **по-разному**:

```java
// executeQuery:
} catch (SQLException e) {
    LOG.error("Failed to execute query " + e.getMessage());
}
return results;          // ← вернётся ПУСТОЙ список

// executeUpdate:
} catch (SQLException e) {
    LOG.error("Failed to execute update query " + e.getMessage());
    throw e;             // ← пробрасывает дальше
}
```

Представь: база недоступна, или в запросе опечатка в имени таблицы. `executeQuery` запишет строчку в лог и вернёт пустой список. Что после этого произойдёт в тесте, который делает `assertEquals(result.size(), 0)` для проверки «записей быть не должно»? А в тесте, который проверяет «в базе должна быть 1 запись»?

Вопрос: какое поведение правильное для тестового фреймворка — и почему одно из двух в референсе стоит считать недостатком, а не стилем? (Мы этот класс проблем разбирали уже трижды на этой неделе.)

### Мелкий вопрос 3 — где хранить пароль от БД?

Параметры подключения (`url`, `user`, `password`) должны попасть в код. У тебя уже есть механизм из P1-T1 — `framework.properties` + приоритет env var → system property → файл. Стоит ли класть туда же параметры БД, и что из этого в реальном проекте нельзя коммитить в публичный репозиторий?

## Типичные ошибки

Все три открытых вопроса решены верно до кода. Особо: **Вопрос 2 (критика референса)** — Денис не просто выбрал вариант «бросать исключение», а сам сформулировал точный механизм отказа: «тест, ожидающий ноль записей, при недоступной базе получит пустой список и станет зелёным». Это тот же класс проблемы, который на предыдущих задачах показывал ему я (`.toString()` вместо `.asString()`, assert без эффекта, контейнер без таблиц) — здесь он впервые нашёл его сам, в чужом боевом коде.

**Находки в конфигурации (до самого util-класса):**
1. **`getValue()` не читал `DB_PROPERTIES`** — второй `Properties` был объявлен и наполнен в `static`-блоке, но в теле `getValue()` опрашивался только первый. Проверено живьём: `ExceptionInInitializerError` → `IllegalStateException: Missing required configuration for: DB_NAME`, то есть падал **любой** тест, трогающий `FrameworkConfig`. Прямой повтор бага P1-T1, где `getValue` растерял ветки.
2. **Файл с учётными данными попал в git-индекс** (`A src/main/resources/dbconnect.properties`) при том, что сам Денис в ответе на Вопрос 3 предложил «завести файл и добавить в gitignore». Поймано до коммита; история осталась чистой (`git log` по этому пути пуст).
3. `POSTGRES_USER` изменён в compose, но контейнер уже был инициализирован со старым пользователем — `\du` показывал только `postgres`. Это ловушка из теории (env-переменные образа работают только при первой инициализации); причину и решение (`docker compose down -v`) Денис назвал сам.
4. Шаблон `dbconnect.example.properties` сначала состоял из закомментированных строк — копия такого шаблона эквивалентна пустому файлу. Отдельно обсуждено: пустое значение (`DB_NAME=`) вернётся из `getProperty` как пустая строка, а не `null`, и проверку `!= null` пройдёт.
5. Обсуждено (без обязательной правки): при отсутствии файла `getResourceAsStream` вернёт `null`, а `load(null)` бросит `NullPointerException` — заготовленное сообщение «file is missing» в этом сценарии не напечатается, потому что ловится `IOException`.

**Находка в тестах — главная, доказана живым прогоном:**
6. **Тест зависел от порядка строк и был «зелёным» только на первом прогоне.** `SELECT id, name, country FROM users` без `ORDER BY` + `result.get(0)` — опора на несуществующую гарантию. Первый прогон прошёл, второй упал: `expected [India] but found [Israel]`. Причина видна в самой базе: `testExecuteUpdate` изменил строку с `India`, Postgres при `UPDATE` физически записывает новую версию строки в конец — и порядок выдачи поменялся. Классический вопрос собеседования: **`SELECT` без `ORDER BY` не гарантирует порядок вообще**. Исправлено `ORDER BY id`.
7. **Тест необратимо менял сид-данные.** `testExecuteUpdate` проставлял `birth_date` и не убирал за собой — база уезжала из состояния, заданного init-скриптами, и следующий тест это чувствовал. Исправлено `@AfterMethod` с восстановлением. Отмечено на будущее: восстановление зашивает знание о сиде; более чистый паттерн — тест работает со своей строкой (реализуется в P9-T3).
8. Мелочи: `executeQuery` вызывался дважды подряд ради одной логической проверки (два похода в базу); создание util дублировалось в обоих тестах; лишние кавычки вокруг `"users"`; имя класса `DataBaseConnectionUtil` вместо `DatabaseConnectionUtil`. Всё исправлено.

**Сильные стороны:** сам нашёл дефект в боевом коде референса и обосновал его через конкретный сценарий отказа; при исправлении порядка строк выбрал гарантию на уровне запроса, а не «подгонку» ожидаемого значения; класс `DatabaseConnectionUtil` в итоге воспроизводит референс полностью (три ресурса в `try-with-resources`, `ResultSetMetaData`, нумерация с 1, `PreparedStatement` с биндингом) и при этом исправляет его недостаток.

**Осталось не сделанным (осознанно, не блокирует):** `System.out.println` вместо логгера; `@AfterMethod` без `alwaysRun = true`.

**Живая проверка:** три прогона `DatabaseConnectionUtilTest` подряд — стабильно зелёные, состояние таблицы после прогонов совпадает с сидом. Полный `mvn clean test` — 22/22.
