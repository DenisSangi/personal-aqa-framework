# P5-T1 — LoginReusableActions (первый сценарный хелпер поверх нескольких POM)

**Фаза / слой:** Фаза 5 — Reusable Actions
**Теги:** java, selenide

## Описание

Открываем новый слой фреймворка. Один класс, `LoginReusableActions` (пакет `reusableActions`, рядом с `pages`), с одним методом `loginAsDefaultUser()`, который склеивает в одно место ровно ту последовательность шагов, что уже есть внутри `BaseNavigationTest.loginFlowTest()` (P4-T2):

```
открыть сайт → HomePage.verifyPageIsOpen() → clickSignupLoginLink() → LoginPage.verifyPageIsOpen()
→ setEmail(...) → setPassword(...) → clickLoginButton() → HomePage.verifyLoggedUsername(...)
```

Метод возвращает `HomePage` — ту страницу, на которой сценарий заканчивается (ровно то же правило "возвращаем актуальный POM", что мы использовали в навигационных методах Фазы 4).

После того как класс готов, `loginFlowTest()` должен превратиться в одну строку — вызов `new LoginReusableActions().loginAsDefaultUser()` — вместо всей цепочки целиком.

## Место в фреймворке

Зависимость: опирается целиком на Фазу 4 (`HomePage`/`LoginPage` уже реализуют весь нужный сценарий по шагам — Reusable Actions ничего нового в POM не добавляет, только вызывает уже существующие методы в правильном порядке).

От этой задачи будет зависеть Фаза 6 (базовый тестовый класс, скорее всего, будет логиниться в `@BeforeMethod` именно через `LoginReusableActions`, а не напрямую через POM) и любой будущий тест, которому для сценария нужен залогиненный пользователь на главной странице как отправная точка.

## Мотивировка

Ты только что в `loginFlowTest()` (P4-T2) написал ровно эту последовательность из 7 шагов вручную. Если в проекте появится второй тест, которому тоже нужен залогиненный пользователь (а такие тесты будут — почти любой сценарий "что-то сделать в личном кабинете" начинается с логина) — придётся copy-paste той же цепочки. Изменится DOM/шаг сценария (например, сайт добавит капчу или чекбокс "запомнить меня") — придётся синхронно править N тестов вместо одного места. Это и есть паттерн **Facade** (design-patterns.md #6 в `java-selenide-pp`): простой интерфейс (`loginAsDefaultUser()`) поверх многошаговой подсистемы (`HomePage` + `LoginPage`), который прячет от теста сам факт, что логин — это на самом деле переход через 2 страницы, а не одно действие.

## Открытый вопрос (обсудим перед кодом)

Посмотри на реальный пример `ENVXLoginRA` из `site-payments-test-automation` (референс, только для понимания структуры — читаем, не копируем):

```java
public class ENVXLoginRA {
    private final ENVXLoginPage atPage = new ENVXLoginPage();

    public void loginAs(AbstractUser user) {
        atPage.login(user);
    }
}
```

Обрати внимание: `atPage` — это ПОЛЕ, создаётся один раз при создании `ENVXLoginRA`, и все методы класса работают через это одно и то же поле.

А теперь вспомни, как устроена навигация в нашем `HomePage`/`LoginPage` (Фаза 4): каждый переход — это `return new NextPage()`, то есть мы никогда не держим один и тот же объект страницы дольше одного шага, каждый следующий шаг работает уже с НОВЫМ объектом, который вернул предыдущий.

Вопрос: если `LoginReusableActions` заведёт похожее поле (`private final HomePage atPage = new HomePage();`) — будет ли от него реальная польза в нашем сценарии, где страница за пределами первого шага меняется несколько раз (`HomePage` → `LoginPage` → снова `HomePage`, но уже ДРУГОЙ экземпляр после логина)? Или для нашей навигационной модели поле вообще не нужно, и `loginAsDefaultUser()` должен просто быть цепочкой вызовов без сохранённого состояния?

## Теория

Facade — уже разобран на реальном примере в `design-patterns.md` #6 (`ClinCardConfig` прячет properties+env+Kubernetes+AWS за простыми константами) — по аналогии: `LoginReusableActions` прячет 7 шагов за одним вызовом. Новой отдельной теории не нужно, это применение уже знакомой идеи в новом контексте (Facade поверх POM, а не поверх конфигурации).
