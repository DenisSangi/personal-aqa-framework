# P14-T1 — Карта «какой паттерн где применён»

**Фаза / слой:** Фаза 14 — Финальный проход по паттернам
**Теги:** interview-prep

## Описание

Собрать «заготовку на 60 секунд» для технического интервью — короткий устный ответ на вопрос «какие паттерны проектирования вы использовали?», но не абстрактный список названий, а на СВОЁМ фреймворке: 4-6 паттернов, для каждого — где именно в `personal-aqa-framework` он применён (класс/метод) и что было бы без него (цена отказа). Формат и объём — по образцу секции «Как отвечать на собеседовании» в `design-patterns.md` референсного проекта, но с собственными ссылками на код, который ты писал сам и можешь разобрать на любом уровне глубины.

## Место в фреймворке

Зависит от всего уже построенного (Фазы 0–10 закрыты; Фазы 11–13 не обязательны — задача описывает уже существующий код, не новый). Ничего не блокирует технически — это не код фреймворка, а материал для интервью. Но по приоритету поставлена **первой в Фазе 14** (решение от 2026-08-03/04): она напрямую кормит собеседование в четверг, тогда как P12 (ThreadLocal) — только тема для разговора, если спросят.

## Мотивировка

Прямая связь с диагностированным на EPAM пробелом (см. память `qa-interview-prep`): интервьюер тогда прямо сказал — ответы были верными, но **без конкретного примера**, и именно это снижало впечатление. Здесь тренируется ровно это умение: не «мы используем Page Object», а «вот `HomePage.clickProductsLink()` возвращает `new ProductsPage()` — если бы каждый тест сам знал URL следующей страницы, при реструктуризации сайта правился бы не один навигационный метод, а десятки тестов».

Цена отказа от этой задачи: на вопрос «какие паттерны вы применяли» будет пауза и impromptu-вспоминание вместо готового, отрепетированного ответа — то самое несовпадение «знаю концепцию / не могу произвести артефакт под давлением», из-за которого сорвалось прошлое интервью.

## Открытые вопросы (обсудим перед тем, как писать финальный текст)

**Вопрос 1 — какие 4-6 паттернов войдут в 60-секундный ответ?**

Ниже — **проверенный мной** (не придуманный) список кандидатов: паттерн → где именно в коде этого проекта он реально встречается. Это сырьё для отбора, не готовый ответ — короткий устный список лучше сработает с 4-6 пунктами, чем с десятком. Выбери те, что можешь разобрать глубже всего, если интервьюер попросит пример.

| Паттерн | Где в `personal-aqa-framework` |
|---|---|
| Page Object | `pages/HomePage.java`, `LoginPage.java`, `ProductsPage.java`, `CartPage.java` |
| Fluent Interface | `HomePage.verifyPageIsOpen()` возвращает `HomePage`; `BaseElement<T>.waitAndGetElement()`/`shouldBe(...)` возвращают `T` — self-bounded generic |
| Facade | `FrameworkConfig` — прячет properties-файл + env var + system property за простыми константами; `LoginReusableActions.loginAsDefaultUser()` — один вызов вместо 6 шагов через 2 страницы |
| Adapter | `BaseElement`/`InputElement`/`ButtonElement`/`TableElement` — обёртки над `SelenideElement`; `RestClient` — обёртка над REST Assured (`given().baseUri(...)...`) |
| Builder | `AccountModel.builder()...build()` в `AccountFactory.createValidAccountModel()` (Lombok) |
| Factory | `AccountFactory.createValidAccountModel()` — сама подставляет случайные валидные данные, вызывающий код не знает деталей сборки |
| Template Method | `BaseTest` → `LoginTest`/`ProductsMainFlowTest` (`@AfterMethod tearDown()` — общий шаг, наследники добавляют свои `@Test`) |
| Observer | `@Listeners(ScreenshotOnFailureListener.class)` в `BaseTest` — TestNG уведомляет листенер о `onTestFailure`, листенер не знает, что делает сам тест |
| Strategy (частично) | `RetryOnFailureAnalyzer.isTransient(Throwable)` — решает, «переиграть» ли конкретное падение, по типу исключения — семантически близко к выбору стратегии реакции на отказ |

**Вопрос 2 — писать ли «цену отказа» для каждого пункта сразу целиком, или сформулировать устно на живом обсуждении, а потом закрепить письменно?**

В `denis-learning-style` зафиксировано, что активное вспоминание своими словами закрепляется лучше, чем чтение готовой формулировки — особенно за день до интервью. Предлагаю: на каждый выбранный пункт ты формулируешь «что было бы без паттерна» вслух (1-2 предложения, конкретно про ЭТОТ код, не абстрактно), я поправляю только фактические неточности — и это идёт в файл.

## Итоговый ответ (≤60 секунд)

> В нашем фреймворке используются следующие паттерны:
>
> 1. **Page Object** — одна страница = один класс (`HomePage`, `LoginPage`, `ProductsPage`, `CartPage`).
> 2. **Fluent Interface** — каждый метод POM возвращает `this`/новый экземпляр другой страницы; в `BaseElement<T>` методы возвращают тип конкретного наследника, а не сам `BaseElement`, через `return (T) this`.
> 3. **Adapter** — поля в POM инициализированы как экземпляры кастомного `BaseElement` и его наследников (`ButtonElement`, `InputElement`, `TableElement`...), а не как сырой `SelenideElement`.
> 4. **Facade** — `FrameworkConfig` прячет алгоритм выбора и доступа к данным из нескольких источников (env var / system property / properties-файлы) за простыми статичными константами.
> 5. **Builder** — модели (например `AccountModel`) через Lombok `@Builder` — не нужно вызывать конструктор с кучей позиционных параметров.
> 6. **Factory** — `AccountFactory.createValidAccountModel()` возвращает готовый `AccountModel` с валидными сгенерированными значениями, чтобы не собирать модель вручную в каждом тесте.

**Резервный слой (если интервьюер попросит углубиться в конкретный пункт)** — развёрнутая «цена отказа» для каждого паттерна, отработанная в диалоге:
- Page Object: без него — дублирование локаторов/методов по всем тестам; смена одного локатора требует правки во всех местах, где страница используется.
- Fluent Interface: без него — каждый шаг сценария отдельной инструкцией через повторное обращение к объекту страницы, код громоздкий, теряется наглядность перехода между страницами.
- Adapter: без него — фреймворк жёстко привязан к API Selenide; смена библиотеки (Selenium/Appium/Playwright) потребовала бы переписать каждое поле в каждом POM-классе.
- Facade: без него — каждый вызывающий код сам разбирался бы, откуда брать значение (env/system property/файл) и в каком порядке — логика дублировалась бы в каждом месте использования.
- Builder: без него — конструктор на 10+ позиционных `String`-параметров; легко перепутать местами два соседних аргумента одного типа, компилятор такую ошибку не поймает.
- Factory: без него — ручная сборка валидной модели в каждом тесте (например в 50 местах) вместо одного места, которое уже знает, как собрать валидные данные.

## Типичные ошибки

1. **Fluent Interface — чужой пример вместо своего.** Первая версия ссылалась на `given().baseUri(...).get(endpoint)` из `RestClient` как на пример паттерна — но это встроенный fluent-API самой библиотеки REST Assured, а собственный `RestClient.get()/post()/delete()` НЕ fluent (возвращает `Response`, не `this`, дальше не чейнится). На интервью это разная по глубине заявка — «мы применили паттерн» vs «мы вызвали чужой fluent-API». Убрано, оставлены только свои примеры (POM-цепочки, `BaseElement<T>`).
2. **Facade — подменено «инкапсуляцией».** Первая формулировка сводила `FrameworkConfig` к «спрятали значение за константой», что по сути просто инкапсуляция одного поля. Уточнено: Facade именно потому, что прячется **координация нескольких источников** (env var → system property → 2 properties-файла) с порядком приоритета — алгоритм из нескольких шагов, а не одно поле.
3. **Builder — цена отказа сформулирована не о том.** Первая версия описывала «пришлось бы переписывать класс заново», хотя класс `AccountModel` остался бы тем же независимо от Builder — паттерн не про описание класса, а про создание экземпляра. Также не называлась конкретная причина ошибки. Уточнено: цена — конструктор на 10+ `String`-параметров подряд, где легко перепутать местами два соседних аргумента, и компилятор этого не поймает.
4. **Factory — имя класса и метода перепутаны трижды подряд.** Сначала «`AccountFabric.getValidAccount()`» вместо `AccountFactory.createValidAccountModel()`; затем в финальной короткой версии дважды подряд «`AccountModelFactory`» вместо `AccountFactory` — исправлено только с третьей попытки. Устойчивая невнимательность именно к точным именам, при полностью верном понимании сути паттерна.
5. **Adapter — несуществующее имя класса в короткой версии.** Черновик 60-секундного ответа называл обёртку «класс `Elements`» — такого класса в проекте нет; реальные имена — `BaseElement` и его наследники (`InputElement`, `ButtonElement`, `TableElement`...). Исправлено.
6. **Формат — смешаны заголовок и глубина.** Первый полный проговор (все 6 пунктов с «что было бы без паттерна» целиком) занял 3-4 минуты вместо 60 секунд — не было разделения на короткий список для старта ответа и развёрнутый материал про запас на случай уточняющего вопроса. Разделено на два слоя (см. «Итоговый ответ» выше).
7. **`BaseElement<T extends BaseElement<T>>` — тема, закрытая на P3-T1 (2026-07-28), «поплыла» в новом контексте.** Подтверждение паттерна из `denis-learning-style`: «закрыто» не значит «закреплено навсегда» — при повторной встрече темы в другом контексте нужен повтор. Разобрано заново напрямую (без наводящих вопросов и абстрактных примеров — по прямой просьбе Дениса, прямое применение правила из `review-feedback-style`) через трассировку на `getText()`/`dismissAdIfPresent()` как примеры методов БЕЗ `T` — терминальная операция (возвращает `String`) и приватный внутренний хук (не часть fluent-цепочки) не нуждаются в сохранении типа наследника.
8. **`FrameworkConfig.getValue()` — почти верно понял механизм с первой попытки.** Денис сам правильно вывел, что метод не выбирает источник ПО ключу, а перебирает все источники в фиксированном порядке при каждом вызове, возвращая первый непустой результат. Единственная неточность: предположение, что удаление полей `PROPERTIES`/`DB_PROPERTIES` «исключит источники из перебора» — на деле это сломает компиляцию, поскольку `getValue()` обращается к этим полям напрямую по имени (не через абстракцию/цикл по списку источников), а не «просто перестанет их проверять».
