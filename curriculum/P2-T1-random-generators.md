# P2-T1 — RandomGenerators

**Фаза / слой:** Фаза 2 — Утилиты
**Теги:** java

## Описание

Построить класс-утилиту `RandomGenerators` (статические методы, без состояния) с минимальным набором генераторов, нужных для тестовых данных на `automationexercise.com`:

- `generateAlphabetic(int count)` — случайная строка из букв.
- `generateAlphanumeric(int count)` — случайная строка из букв и цифр.
- `generateNumber(int count)` — случайная строка из цифр (для телефона, ZIP-кода и т.п.).
- `generateEmail()` — валидный по форме email на основе `generateAlphanumeric(...)` + случайный домен из небольшого фиксированного набора (`gmail.com`, `yahoo.com`, ...).

Открытый вопрос на обсуждение (не решай заранее — обсудим на созвоне): референсный класс использует внешнюю библиотеку `org.apache.commons.lang.RandomStringUtils` для генерации строк, а в `pom.xml` этого проекта такой зависимости нет. Есть два пути — добавить `commons-lang3` (как в Фазе 0 добавляли Allure/REST Assured) или реализовать генерацию строк вручную через `java.util.Random`/`ThreadLocalRandom` и диапазоны символов. Второй путь ближе к теории этой задачи — решим вместе, когда будешь готов обсуждать.

## Место в фреймворке

Зависимость: опирается на Фазу 0 (компилируемый `pom.xml`, структура `src/main`). От неё зависят: Фаза 8 (продвинутые тестовые данные — использует генераторы для уникальных сущностей), Фаза 10 (реальные тесты — регистрация пользователя на `automationexercise.com` требует случайных имени/email/пароля при каждом прогоне). Не зависит от `FrameworkConfig` (P1-T1) — это независимая, изолированная утилита.

## Мотивировка

Без генератора тестовых данных есть два плохих варианта: (1) захардкодить конкретные значения (email, имя) — тогда второй прогон теста упадёт на дубликате/конфликте уникальности, а параллельные прогоны будут конкурировать за одни и те же данные; (2) дублировать логику генерации в каждом тесте отдельно — тогда правило «как выглядит валидный тестовый email» размазано по десяткам мест, и его невозможно поменять в одном месте. Отдельный `RandomGenerators` даёт один источник правды для формы тестовых данных и делает тесты независимыми друг от друга и от истории прошлых прогонов.

Цена отказа: тест регистрации, использующий захардкоженный email, будет зелёным один раз и красным на каждом следующем прогоне (или красным при параллельном прогоне с самим собой) — причём ошибка на экране будет про «email уже занят», а не про баг в тестируемом функционале. Отладка такой причины отнимает время именно потому, что она никак не связана с тем, что тест на самом деле проверяет.

## Теория

- `java.util.Random`: как устроен генератор (seed, `nextInt()`, `nextInt(bound)`), почему у объекта есть внутреннее состояние.
- `ThreadLocalRandom.current()`: чем отличается от `new Random()` при параллельном выполнении тестов (нет конкуренции за один и тот же объект между потоками).
- Диапазоны символов: как получить случайную букву/цифру через арифметику над `char`/`int`, не выписывая алфавит вручную.
- Файл: [theory/03-random-and-threadlocalrandom.md](../theory/03-random-and-threadlocalrandom.md)

## Типичные ошибки

Реальные ошибки, найденные за несколько раундов ревью этой задачи:

1. **`generateAlphanumeric` первой версии падал на `count < 3`.** Реализация строила всю строку буквами (`generateAlphabetic(count)`), затем ЖЁСТКО заменяла последние 3 символа на цифры (`resultString.replace(resultString.length()-3, resultString.length(), digits)`). При `count` меньше 3 `resultString.length()-3` уходил в отрицательный индекс → `StringIndexOutOfBoundsException`. Урок: если в реализации появляется "магическое число", завязанное на длину входного параметра (здесь — фиксированные "последние 3"), первым делом стоит спросить себя, что произойдёт, если входной параметр окажется МЕНЬШЕ этого числа — DoD никогда не гарантировал `count >= 3`.
2. **Та же первая версия принудительно форсировала регистр** (`substring(0,1).toUpperCase() + substring(1,count).trim().toLowerCase()`), хотя этого не было ни в описании задачи, ни в DoD. После вопроса на ревью — убрано вместе с переходом на более простую однопроходную логику (случайный выбор буква/цифра на каждой позиции через `nextBoolean()`).
3. **Тесты содержали проверку через `matches(regex)`, но не были подключены к `assert`.** `testingRandomAlphabetic.matches(regex);` — вызов есть, но результат (`boolean`) нигде не используется, поэтому тест физически не может упасть по этой проверке независимо от реального формата строки. Та же категория ошибки, что уже встречалась на [P1-T1](P1-T1-config-facade.md) (там — логически бессмысленный assert; здесь — assert вообще отсутствует при наличии проверки). Урок повторился второй раз подряд — стоит взять за привычку при написании проверки сразу спрашивать себя "а что будет, если это условие окажется ложным — тест правда покраснеет?".
4. **Промежуточный регресс при попытке ответить на вопрос об эффективности.** На вопрос "не дорого ли выделять `StringBuilder` на каждый символ в `generateAlphanumeric`" (не блокирующий, для размышления) Денис вместо правки самого `generateAlphanumeric` переписал НЕСВЯЗАННЫЕ методы `generateAlphabetic`/`generateNumber`: заменил рабочий `StringBuilder` на `char[]` + `Arrays.toString(...)` + четыре цепочки `.replaceAll(...)` (`]`, `[`, `,`, `" "`), чтобы вручную убрать форматирование, которое сам же `Arrays.toString` и добавляет (`"[a, b, c]"` → нужно `"abc"`). Результат был функционально верным, но избыточно сложным. После наводящего вопроса вспомнил `new String(char[])` — прямой конструктор `String`, превращающий массив символов в строку без промежуточного форматированного представления. Урок: если для простой операции («массив символов → строка») получается решение с несколькими цепочками текстовых замен — это сигнал поискать более прямой путь в стандартной библиотеке, а не первый работающий вариант.
5. **Мелкая гигиена: неиспользуемый импорт `java.util.Arrays`** остался после перехода на `new String(char[])`, пока на ревью не указали явно.
