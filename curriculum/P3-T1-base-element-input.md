# P3-T1 — BaseElement&lt;T&gt; + InputElement

**Фаза / слой:** Фаза 3 — Слой element-обёрток
**Теги:** java, selenide

## Описание

Первая задача с реальным Selenide-кодом в проекте (зависимость в `pom.xml` с P0-T1, но до сих пор не использовалась). Нужно построить:

1. Абстрактный базовый класс `BaseElement<T extends BaseElement<T>>` — self-bounded generic, единственный метод `waitAndGetElement()`: дождаться существования элемента → проскроллить его в видимую область → дождаться видимости. Возвращает `T` (не `BaseElement`), реализовано через `(T) this`.
2. Первый конкретный адаптер — `InputElement extends BaseElement<InputElement>`, минимум: `setValue(String value)` (сначала `waitAndGetElement()`, потом `element.setValue(value)`) и `getValue()` (возвращает текущее значение поля).

**Сознательно НЕ входит в объём этой задачи** (это не полный аналог референса — там `BaseGPElement` под 20 методов): `find`/`findElement`/`format`/`reinitElement` (рефлексия для клонирования элементов), `dragAndDropElement`, `download`, переключаемый флаг `scrollIntoView` (у нас скролл всегда включён, без настройки), множественные перегрузки `should`/`shouldBe`/`shouldHave`. Если что-то из этого понадобится — вернёмся отдельной задачей, когда будет конкретный сценарий, а не заранее.

## Место в фреймворке

Зависимость: опирается на Фазу 0 (Selenide уже в `pom.xml`). От неё зависит вся Фаза 4 (Page Object) — POM-классы будут обращаться к Selenide ТОЛЬКО через такие обёртки, никогда напрямую через `$`/`$x`.

## Мотивировка

Без этого слоя каждый Page Object будет писать вызовы Selenide прямо в своём теле — `$x(...).shouldBe(visible).setValue(...)`. Два конкретных последствия:

1. **Зоопарк ожиданий.** Один разработчик в одном месте ждёт `visible`, другой в соседнем методе — `editable`, третий вообще не ждёт ничего и получает `ElementNotInteractableException`. Без единой точки, где решается "что значит дождаться элемента", это неизбежно расползается по всей кодовой базе.
2. **Точечная замена вместо переписывания всего.** Если завтра решат сменить Selenide на другую библиотеку (или просто мажорно обновить её API) — при прямых вызовах Selenide из POM придётся редактировать КАЖДЫЙ POM-класс во всех модулях. С адаптером меняется один слой, POM не трогается вообще.

Цена отказа: любая проблема с ожиданием элемента (или смена библиотеки автоматизации) превращается в правку N файлов вместо одного.

## Теория

- Selenide-основы: `$`/`$x`, `SelenideElement`, `Condition.visible`, ленивый запуск браузера без явной конфигурации.
- Self-bounded generics (CRTP) — почему обычный `return this` в базовом классе ломает цепочку вызовов у наследника, и как `T extends BaseElement<T>` это чинит. Изолированный пример в вакууме (`Animal`/`Dog`) — до реального кода.
- Template Method — `waitAndGetElement()` в базовом классе как обязательная "прелюдия" перед специфичным действием наследника.
- Файл: [theory/05-selenide-basics-and-generics.md](../theory/05-selenide-basics-and-generics.md)

## Типичные ошибки

Финальный код — без единой функциональной ошибки. Показательными оказались шаги К нему (теория + процесс), не сам код:

1. **Механическое копирование референса без понимания.** Первая попытка — переписывание `BaseGPElement` "на глаз". Денис сам это заметил и остановился, вместо того чтобы доводить до конца вслепую — попросил разбить задачу на шаги. Отдельный ценный навык сам по себе, стоит поощрять на будущих задачах.
2. **Путаница статический/динамический тип объекта.** На вопрос "какой объект реально лежит в `this` внутри `eat()`, вызванного на `dog`" ответил "Animal" — хотя реальный (динамический) объект — `Dog`, просто ОБЪЯВЛЕННЫЙ (статический) тип возврата метода — `Animal`. Поправлено разбором разницы статического/динамического типа.
3. **`@SuppressWarnings("unchecked")` ошибочно назван причиной, почему `Dog extends Animal<Cat>` компилируется.** Аннотация только глушит предупреждение компилятора, не влияет на компилируемость — реальная причина в том, что `T extends Animal<T>` проверяет соответствие типа условию, а не совпадение с самим объявляющим классом.
4. **Первое объяснение self-bounded generic — через "доступ к полям/методам".** Доступ к полям/методам родителя и наследника даёт обычное `extends`, это не про generic. Реальный эффект `<InputElement>` — фиксирует возвращаемый тип `T` у методов родителя. Дошёл до точной формулировки после сравнения "что возвращает `waitAndGetElement()` до и после добавления generic".
5. **Первая словесная формулировка `waitAndGetElement()` пропускала проверку существования** — назвал только скролл и видимость. Поймано ДО кода, на словесном разборе шагов, не в код-ревью.
6. **Считал, что `waitAndGetElement()` должен возвращать `SelenideElement`.** Не сразу увидел, что это ломает инкапсуляцию адаптера — возврат `SelenideElement` наружу означает, что вызывающий код "выпадает" обратно в мир Selenide (даже если у `SelenideElement` случайно есть одноимённый метод типа `setValue`, это уже не наш адаптер). Понял после разбора конкретного примера с `input.waitAndGetElement().setValue(...)`.

Мелочь, не блокирующая аппрув: тестовый email `"myEmail@.com"` выглядит не вполне валидно (домен без имени) — для теста неважно (проверяется echo значения, не формат), но для реалистичности лучше подбирать правдоподобные тестовые данные.
