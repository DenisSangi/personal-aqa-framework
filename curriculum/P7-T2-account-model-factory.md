# P7-T2 — AccountModel (Builder) + AccountApiService + AccountFactory

**Фаза / слой:** Фаза 7 — Слой API-сервисов
**Теги:** java, rest-assured

## Описание

Второй API-сервис проекта, но с новой проблемой — у `POST /api/createAccount` **17 параметров** (проверено `curl`, реально работающий запрос):

```
name, email, password, title, birth_date, birth_month, birth_year,
firstname, lastname, company, address1, address2, country, zipcode, state, city, mobile_number
```

Собирать это вручную в `Map<String, String>` в каждом тесте (как делал `LoginApiService` с двумя полями) — уже реально больно. Три новых класса:

1. **`AccountModel`** — класс данных под эти 17 полей.
2. **`AccountApiService extends BaseApiService`** — `createAccount(AccountModel model)` и `deleteAccount(String email, String password)` (нужен для cleanup — см. мотивировку).
3. **`AccountFactory`** — фабрика, возвращающая уже готовую, валидную `AccountModel` с разумными дефолтами и уникальным email/именем (через `RandomDataGenerator`/`DateTimeUtil` из Фазы 2 — первое реальное использование этих утилит в проекте с момента, когда они были написаны).

## Место в фреймворке

Зависимость: опирается на Фазу 2 (`RandomDataGenerator.generateEmail()`, `generateAlphabetic()` — для уникальности данных между прогонами) и P7-T1 (тот же `RestClient`/`BaseApiService`).

От неё зависит: Фаза 10 (`P10-T3`, API CRUD-тесты) будет использовать `AccountFactory` для setup, не собирая модель заново.

## Мотивировка

Ты уже прожил на своей шкуре, к чему приводит непроверенный запрос к живому API — на этой самой задаче я по неосторожности создал реальный аккаунт и был вынужден его удалять отдельным запросом. Это не абстрактный пример "что могло бы случиться" — представь, что то же самое сделает не один вызов, а десятки тестов, каждый раз создающих сущности и не удаляющих их за собой. Через неделю прогонов на `automationexercise.com` будут висеть сотни мусорных тестовых аккаунтов. Отсюда — `deleteAccount` в `AccountApiService` идёт в этой же задаче, не откладывается "на потом".

Вторая часть — сама модель. 17 полей вручную в каждом тесте — это тот же дублирующий код, который мы уже устраняли на каждом слое (POM убрал дублирование локаторов, `RestClient` — дублирование `given()`). Здесь дублируется **сборка тестовых данных**. `AccountFactory` — прямая параллель `ClinCardProgramFactory` из референса: фабрика хранит разумные дефолты и отдаёт готовый объект, тест указывает только то, что ему реально важно для конкретного сценария.

## Открытые вопросы (обсудим перед кодом)

### Вопрос 1 — `record` или Lombok `@Builder`?

`PLAN.md` предлагает оба варианта на выбор. У `record` (начиная с Java 16) есть готовый компактный конструктор и неизменяемость "из коробки" — но **все** поля обязательны в конструкторе, дефолтных значений нет средствами языка.

У Lombok `@Builder` (уже используется в проекте — `@Getter` на `Domains`, значит Lombok настроен и работает) есть `@Builder.Default` — конкретный механизм для полей вроде `address2`/`company`, которые в большинстве тестовых сценариев не важны и могут иметь разумное значение по умолчанию, как в референсном `ClinCardSiteModel`:

```java
@Builder.Default private String newAddress = "";
```

Вопрос: при 17 полях, часть из которых реально нужно варьировать в тестах (email, password), а часть — почти всегда одинаковая (country, title) — какой из двух подходов подходит лучше?

### Вопрос 2 — кто превращает `AccountModel` в `Map<String, String>` для `RestClient.post(...)`?

Три варианта:
- метод `toFormParams()` внутри самой `AccountModel`;
- `AccountApiService.createAccount(model)` сам собирает мапу из полей модели;
- что-то ещё.

Вспомни раздел «Сервис ≠ модель ≠ session» из `Framework explanation/4-api-services-layer.md` — там прямо разбирается, почему `ClinCardSiteModel.save(session)` (модель сама себя отправляет) сознательно **не выбран** как подход — это Active Record, и модель в референсе ничего не знает про HTTP. Как это должно повлиять на ответ?

## Типичные ошибки

Самая насыщенная находками задача проекта на сегодняшний день — почти десяток раундов ревью. Открытые вопросы решены верно и обоснованно ДО кода: Lombok `@Builder` вместо `record` (17 полей, часть с разумными дефолтами — `@Builder.Default` под это и создан); `AccountApiService` (не модель) превращает `AccountModel` в `Map<String, String>` — модель не знает про HTTP.

**По `AccountModel`:**
1. Изначально не хватало поля `title` — сверка с реальным списком из 17 параметров `createAccount` (уже зафиксированным в этом же лесоне через `curl`) сразу показала пробел.

**По `AccountApiService`:**
2. Опечатка в ключе формы: `"assress2"` вместо `"address2"` — значение реально не долетало до сервера под нужным именем.
3. Пропущен `zipcode` целиком — ни одного `.put("zipcode", ...)` не было, при том что поле в модели `@NonNull`.
4. Контракт возврата `createAccount` прошёл три итерации: `String` (текст `message` из ответа) → `boolean` → финально `void`. Ключевой момент: я лично проверил `curl`'ом (тем же самым `POST createAccount`), что `account_id` в реальном ответе API **не существует вообще** — только `responseCode`/`message`. А `deleteAccount` просит не ID, а `email`+`password`, которые и так уже есть у вызывающего кода. Дальше выяснилось эмпирически (сам Денис проверил повторной отправкой той же модели), что у этого API **нет** легитимного "невиновного" отказа при создании (`email already used` не существует как отдельный исход — API просто создаёт дубликат) — значит любой не-`201` результат обязан быть исключением, а раз так, возвращать вообще нечего: `void`.
5. Сообщение исключения сначала использовало `response.getStatusCode()` — **тот же урок, что уже был на `verifyLogin` (P7-T1)**: этот API всегда отдаёт HTTP `200`, реальный код — в `responseCode` внутри тела. Поправлено на чтение `responseCode`.

**По тесту:**
6. `testCreateAccount`/`testDeleteAccount` изначально были ДВУМЯ независимыми `@Test`-методами, делящими общее поле модели — TestNG не гарантирует порядок между ними. Проверка на практике подтвердила: при совместном прогоне `testDeleteAccount` выполнился раньше, получил `404 Account not found!`. Объединено в один сценарий (create → verify true → delete → verify false), cleanup вынесен в `@AfterMethod(alwaysRun = true)` (перенос урока Фазы 6) с защитным `if (verifyLogin(...))` перед удалением — чтобы `deleteAccount` не падал, пытаясь удалить аккаунт, которого не было создано из-за более раннего сбоя (тот же принцип, что `safeDelete` в референсе).
7. Тестирование `void`-методов потребовало отдельного разбора: как проверить действие без возвращаемого значения — либо "не упало исключение", либо (более сильная проверка) наблюдаемый эффект через НЕЗАВИСИМЫЙ канал. Именно так и решили — `LoginApiService.verifyLogin(...)`, уже готовый и протестированный на другой задаче, стал независимым доказательством, что аккаунт реально появился/исчез, а не просто "метод не бросил исключение".

**По `AccountFactory`/`RandomDataGenerator` (генерация даты рождения и возраста):**
8. Дата рождения изначально собиралась из **трёх независимых вызовов** `generateDateFromTodayOfYearsAgo(25)` (для `birthDate`/`birthMonth`/`birthYear` порознь) — каждый вызов включает случайный сдвиг внутри года, значит три поля описывали три никак не связанных между собой даты. Поправлено на один вызов, результат сохранён в локальную переменную.
9. Промежуточная версия того же исправления держала `LocalDate` как `static final` поле класса — то есть дата вычислялась один раз при загрузке класса в JVM, а не при каждом вызове `createValidAccountModel()` (все остальные поля при этом оставались случайными на каждый вызов — рассинхрон). Перенесено в локальную переменную внутри метода.
10. `.getDayOfWeek()` (день недели, "MONDAY") и следом `.getDayOfYear()` (число 1–366, "какой день в ГОДУ") — обе неверные попытки получить "день месяца" (1–31) до того, как дошли до правильного `.getDayOfMonth()`.
11. При попытке сделать случайным сам возраст ("сколько лет назад") — `Integer.parseInt(generateNumber(25))` — **та же путаница, что уже разбиралась на дне/месяце в начале задачи**: `generateNumber(count)` генерирует `count`-значную строку случайных цифр (25 цифр — заведомо больше, чем вмещает `int`), а не "случайное число до 25". Реальный `NumberFormatException` подтверждён падением `mvn clean test` на инстанциации тестового класса (значение генерируется в конструкторе через инициализатор поля). Решено верно и самостоятельно — новый общий метод `RandomDataGenerator.generateNumberInRange(min, max)` (через `ThreadLocalRandom.nextInt(origin, bound)`), границы (`18`–`90`) остались знанием `AccountFactory`, не внутри общего генератора.
12. Для случайной страны — самостоятельно узнал в `utils/Domains.java` (Фаза 2) готовый паттерн ("enum + `getRandomDomain()`") и верно перенёс его один в один на `Countries`/`getRandomCountryValue()`, без подсказки конкретной реализации.

`mvn clean test` — весь проект зелёный (единичный сетевой таймаут CDP на несвязанном `TableElementTest` не воспроизвёлся при повторном прогоне — внешняя нестабильность, не логическая ошибка, тот же класс, что уже документирован в P3-T2/P4-T2). Живой цикл create→verify→delete→verify подтверждён.
