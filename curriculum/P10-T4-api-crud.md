## Описание

Фаза 7 построила API-слой наполовину. `AccountApiService` умеет `createAccount` (Create) и `deleteAccount` (Delete); `LoginApiService.verifyLogin` — это косвенный, слабый Read (только `true`/`false`, ни одного реального поля профиля). Полного CRUD нет: не хватает прямого Read (получить актуальные данные аккаунта) и Update. Вторая часть задачи — домен товаров вообще не тронут API-слоем, только UI (`ProductsPage`, Фаза 10.2).

Задача закрывает оба пробела:
1. Дополняет `AccountApiService` методами `getUserDetailByEmail` (GET) и `updateAccount` (PUT).
2. Заводит новый `ProductApiService` с одним read-методом поверх `GET /api/productsList`.

Оба реальных эндпоинта проверены `curl` заранее (см. раздел фактов ниже) — задача построена на том, что реально возвращает сайт, а не на предположении.

## Место в фреймворке

Зависимость: опирается на Фазу 7, которая уже готова целиком — `RestClient`, `BaseApiService`, `AccountModel`, `AccountFactory`. Это последняя задача Фазы 10 (Test Coverage) — после неё все четыре куска реального regression-сьюта закрыты (UI happy/negative логина, UI поиск/корзина, стабилизация, API CRUD), и Фаза 11 (Allure) получает представительный сьют, а не один демонстрационный тест.

От неё напрямую ничего не зависит, но она физически расширяет `RestClient` (Adapter) — тем же классом будут пользоваться все будущие API-сервисы.

## Мотивировка

Это не искусственный повод «сделать ещё методов» — расширение обязательно на уровне механики:

- `RestClient` сейчас умеет `get(String)` **без параметров**, `post(...)`/`delete(...)` — с form-параметрами. Ни GET с query-параметром, ни PUT он не умеет вообще. `GET /api/getUserDetailByEmail?email=...` требует именно query-параметр (у GET физически нет тела запроса), `PUT /api/updateAccount` требует нового HTTP-глагола. Без расширения `RestClient` эти два реальных эндпоинта нельзя вызвать в принципе — это не "было бы неплохо", а жёсткое ограничение текущего кода.
- Половинчатый CRUD (Create+Delete есть, Read+Update нет) хуже демонстрирует владение темой на собеседовании, чем полный цикл — а для user-сущности сайт эти два метода реально предоставляет.
- Товарная сторона (`ProductApiService`) показывает то же API `automationexercise.com` с другого угла: паблик read-only каталог без единого form-параметра — специально контрастирует с 17-полевым `createAccount` и не даёт зафиксировать ложную мысль "все API-сервисы одной формы".

## Факты, проверенные `curl` до выдачи задачи

- `GET /api/getUserDetailByEmail?email=<существующий>` → HTTP 200, тело `{"responseCode": 200, "user": {"id":..., "name":..., "email":..., "title":..., "birth_day":..., "birth_month":..., "birth_year":..., "first_name":..., "last_name":..., "company":..., "address1":..., "address2":..., "country":..., "state":..., "city":..., "zipcode":...}}`.
- `GET /api/getUserDetailByEmail?email=<несуществующий>` → HTTP **200** (не 404!), тело `{"responseCode": 404, "message": "Account not found with this email, try another email!"}`.
- `GET /api/getUserDetailByEmail` без параметра `email` → HTTP 200, тело `{"responseCode": 400, "message": "Bad request, email parameter is missing in GET request."}`.
- **Вывод из трёх пунктов выше: тот же паттерн, что уже был на `verifyLogin`/`createAccount`/`deleteAccount` (Фаза 7) — этот стенд всегда отвечает HTTP 200, реальный код результата только внутри тела, в поле `responseCode`.** Четвёртое независимое подтверждение одного и того же факта про этот конкретный API.
- `PUT /api/updateAccount` — по официальной документации сайта (`automationexercise.com/api_list`, API 13) принимает те же 17 параметров, что `createAccount`, отвечает `responseCode: 200` при успехе ("User updated!"). **Реальный PUT-вызов заранее не выполнялся** (в отличие от GET-проверок выше) — это мутирующий запрос, а трогать общий тестовый аккаунт (`framework.properties`, `USER_EMAIL`) без необходимости — против уже установленного в проекте правила (прецедент P7-T2). Сам вызов будет сделан живьём в тесте, на аккаунте, который тест сам создал, а не на общем.
- `GET /api/productsList` → HTTP 200, тело `{"responseCode": 200, "products": [{"id": 1, "name": "Blue Top", "price": "Rs. 500", "brand": "Polo", "category": {...}}, ...]}` — список из нескольких десятков товаров, `id: 1`/`name: "Blue Top"` подтверждены как первая запись списка.

## Открытые вопросы (обсудим перед кодом)

### Вопрос 1 — как расширить `RestClient` под GET с параметром и под PUT?

Сейчас `get(String endpoint)` не принимает параметров вообще, а `post`/`delete` принимают `Map<String, String> formParams` и кладут их как **form-параметры** (в тело запроса). `GET /api/getUserDetailByEmail?email=...` — это **query-параметр** (в URL, не в теле). REST Assured различает `.formParams(...)` и `.queryParams(...)` — это разные вызовы на `given()`.

Вопрос: какую сигнатуру дать новому GET-методу с параметром(-ами)? И должен ли `put(...)` по форме повторять уже существующий `post(...)` (тот же `Map<String,String> formParams`, раз `updateAccount` шлёт ровно те же 17 form-полей, что `createAccount`)?

### Вопрос 2 — что возвращает `getUserDetailByEmail`?

Варианты, каждый — уже виденный в проекте прецедент:
- `boolean` (аккаунт существует/нет) — по образцу `verifyLogin`;
- одно конкретное поле, нужное вызывающему коду (например `String getFirstNameByEmail(...)`) — узкий контракт под задачу;
- полноценный объект (собранный вручную по одному полю через `jsonPath()`, как частично уже делает `createAccount` с `responseCode`, только в обратную сторону — чтение, не запись).

Не вариант **на сейчас**, но стоит проговорить вслух почему: response можно было бы десериализовать целиком через Jackson (`response.as(AccountModel.class)`) — это отдельная, уже занесённая в план задача **P7-T3**. Смысл вопроса не в том, чтобы сделать её здесь заранее, а в том, чтобы осознанно выбрать, чего достаточно именно сейчас — критерий выбора: что реально понадобится тесту на update (см. Вопрос 4).

### Вопрос 3 — `AccountModel` и `toBuilder`

`updateAccount` шлёт все те же 17 полей, что `createAccount` — значит тесту нужен способ взять уже существующую валидную модель (ту, что использовалась при создании) и поменять 1-2 поля, не пересобирая с нуля 14 обязательных `@NonNull`-полей заново. Сейчас `AccountModel` объявлен `@Builder` **без** `toBuilder = true` — соответственно, `.toBuilder()` у уже существующего объекта недоступен.

Референсный `ClinCardStudyModel` в `java-selenide-pp` как раз использует `@Builder(toBuilder = true)` ровно для этого сценария — построить второй вариант объекта на основе первого (`clinCardStudyModel1.toBuilder().programId(...).build()`). Нужно ли включать эту опцию здесь? Если да — как это меняет тело теста на update?

### Вопрос 4 — что именно проверяет тест на update?

Update нельзя проверить тем же способом, что create (`verifyLogin` не видит ни одного профильного поля, только факт логина). Что должно измениться и как это подтвердить — сравнить значение поля до/после через `getUserDetailByEmail` (Вопрос 2), или иначе?

### Вопрос 5 — нужна ли модель для товара?

`createAccount`/`updateAccount` строят `Map` из полей объекта — там модель оправдана, потому что нужно что-то *отправить*. `getAllProducts()` — чистый Read без единого исходящего параметра, тест только читает готовый ответ и проверяет 1-2 факта о нём. Нужен ли отдельный `ProductModel`, или это ровно тот случай, когда `jsonPath()` напрямую в сервисе/тесте — осознанно достаточно, без переусложнения ради формального единообразия с account-стороной?

## Теория

Расширение уже существующего Adapter (`RestClient`) новыми HTTP-глаголами по мере реальной необходимости — тот же принцип, что уже применялся на P7-T1, когда `post(...)` был сознательно сужен до `formParams` под конкретный эндпоинт, а не спроектирован «на все случаи» заранее. Дополнительно: различие **query params vs form params** на уровне HTTP-протокола — у GET физически нет тела запроса, поэтому единственный способ передать параметр — строка запроса (`?key=value`); у POST/PUT есть тело, поэтому у них выбор шире.

## Типичные ошибки

Реальные находки живого ревью 2026-08-14, по порядку появления:

1. **Путаница термина Dependency Injection.** На вопрос, как `AccountApiService` получает доступ к методам `RestClient`, был назван DI — на деле `BaseApiService` создаёт `RestClient` сам через `new` внутри собственного конструктора (`restClient = new RestClient(FrameworkConfig.APP_URL)`), это композиция без инверсии контроля, не DI. Настоящий DI — когда зависимость передают снаружи (параметр конструктора/сеттер/контейнер).
2. **Метод изначально назван `getUserDetailByEmail`, как сам эндпоинт, при узком контракте** (возвращает только `first_name` строкой) — то самое несовпадение имени и контракта, которое Вопрос 2 должен был предотвратить. Переименован в `getUserFirstnameByEmail` после прямого вопроса.
3. **Тихий `null` из-за неверного JSON-пути.** `jsonPath().getString("first_name")` искал поле в корне ответа, а оно вложено в объект `user` (`user.first_name`) — классический случай, когда `jsonPath()` на несуществующем пути тихо возвращает `null` вместо ошибки. Денис сам нашёл причину, проверив сырой `response.getBody().asString()` вместо того, чтобы гадать, и сам поправил путь.
4. **Дублирование сборки `formParams`** между `createAccount` и `updateAccount` (17 идентичных строк). Первое предложение по устранению — приватный метод `buildFormParams(...)` в **тестовом** классе (`AccountApiServiceTest`) вместо продакшн-класса — не работало бы физически (тестовый класс не вызывается из продакшн-методов). После вопроса «а кто на самом деле вызывает дублирующийся код» сам назвал верное место (`AccountApiService`) и написал чистый приватный метод.
5. **Перепутан порядок аргументов `assertEquals` в TestNG** (`actual, expected`, не как в JUnit) в `updateAccountTest` — тот же класс ошибки, что уже был на P3-T2 в этом проекте, при этом в соседнем методе того же файла (`getUserFirstnameByEmailTest`) порядок был верный. Исправлено сразу после сравнения с соседним методом.
6. **`ProductApiService` изначально возвращал сырую строку JSON** (`response.getBody().asString()`) вместо использования `jsonPath()` — при том что Вопрос 5 был именно про «`jsonPath()` напрямую, без модели». Переписан на `List<String>` через `getList("products.name", String.class)`.
7. **`getList("products")` без вложенного пути возвращал бы список целых объектов** (`LinkedHashMap` на рантайме), не имён — присваивание в `List<String>` компилируется за счёт unchecked generic-инференса, но при первом реальном использовании элемента как `String` вылетел бы `ClassCastException`. Денис честно сказал «не понимаю сам, просто механически пишу код» вместо того, чтобы притвориться, что разобрался — после разбора на изолированном примере (`items`/`items.name`) закрыл тему сам, включая верный вывод о том, что `, String.class` — это про типобезопасность, а не про сам механизм извлечения (это делает путь `products.name`).
8. **Рассинхронизация `statusCode`/`responseCode` в тексте исключения.** Проверка условия использовала верное поле `responseCode`, а сообщение об ошибке — несуществующее `statusCode`, что при реальном сбое API привело бы к `NullPointerException`, маскирующему настоящую причину вместо информативного сообщения.
9. **Тест `ProductApiServiceTest` дважды вызывал API-метод** (по разу на каждый `assert`) — лишний HTTP-запрос и источник потенциальной нестабильности между двумя вызовами. Исправлено сохранением результата в переменную.
10. **Опечатка в `regression.xml` молча исключила `ProductApiServiceTest` из официального сьюта.** Строка `<class name="api.services.ProductApiService"/>` (без `Test` в конце) ссылалась на продакшн-класс без единого `@Test`-метода — `mvn clean test` (сьют явно задан в `pom.xml` через `surefire.suiteXmlFile`) молча пропускал его, не выполняя ни одного теста из этого класса и не сообщая об ошибке. Найдено арифметикой: ожидалось 32 теста (29 было + 3 новых), прогон показал 31 — расхождение в один тест указало точно на пропавший класс. Найдено уже **после** формального закрытия DoD по первому прогону — задача была бы закрыта с ложным подтверждением «весь проект зелёный», если бы не пересчитали ожидаемое количество тестов. После фикса — реальные 32/32.

**Сильные стороны:** по своей инициативе предложил новый рабочий цикл сессии («вопрос → код → ревью → следующий вопрос»), заметно снизивший потерю контекста; дважды сам находил и чинил баги после живой проверки на реальном API, а не верил на слово компиляции (`null` first_name, дважды подтверждённый через сырой JSON); честно признавал непонимание механизма вместо угадывания (getList/products.name); все 5 открытых вопросов закрыты с адекватным обоснованием с первой попытки.
