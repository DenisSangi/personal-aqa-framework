# P6-T1 — BaseTest (Template Method) + lifecycle

**Фаза / слой:** Фаза 6 — Базовый тест и lifecycle
**Теги:** java, testng

## Описание

Открываем новый слой — тестовые классы перестают быть независимыми друг от друга и начинают наследоваться от одного общего `BaseTest`.

Прямо сейчас в проекте **пять** тестовых классов, и у каждого — дословно одинаковый блок:

```java
@AfterMethod
public void tearDown() {
    Selenide.closeWebDriver();
}
```

(`InputElementTest`, `ButtonElementTest`, `DropdownElementTest`, `TableElementTest`, `BaseNavigationTest` — можешь сам сверить, текст один в один).

Задача: завести `BaseTest`, перенести туда этот `@AfterMethod`, и переписать все пять классов на `extends BaseTest`, убрав из них свою копию.

## Место в фреймворке

Зависимость: опирается на то, что уже во всех тестах используется Selenide (`Selenide.closeWebDriver()`) — то есть фактически на весь код, написанный с Фазы 3 (элементы) по Фазу 5 (Reusable Actions).

От неё зависит: P6-T2 (Listener на скриншот при падении — будет вешаться на `BaseTest`, не на каждый класс по отдельности) и вообще любой будущий тестовый класс — начиная с этой задачи новый тест по умолчанию наследуется от `BaseTest`, а не пишет lifecycle с нуля.

## Мотивировка

Это не гипотетическая проблема "а вдруг понадобится в будущем" — дублирование уже произошло, ты сам его написал пять раз подряд, копируя один и тот же блок из класса в класс. Цена этого уже была видна на P4-T1: `BaseNavigationTest` на первой версии **забыл** `@AfterMethod` вообще — потому что копирование вручную из класса в класс не гарантирует, что скопируешь именно во ВСЕ файлы, где нужно.

Представь дальше: P6-T2 требует добавить общий listener на скриншот при падении теста. Если lifecycle не вынесен в одно место — этот listener придётся вручную подключать в пяти местах (и не забыть про шестое, седьмое, десятое, когда тестов станет больше). Одно упущенное место — тихий пробел в отчётности, который не подскажет о себе сам, ты просто не увидишь скриншот при разборе конкретного упавшего теста.

Это ровно паттерн **Template Method** (design-patterns.md #7 в `java-selenide-pp`): базовый класс задаёт "скелет" — что должно происходить до и после каждого теста — а конкретные тестовые классы наследуют этот скелет и добавляют только свою уникальную часть (сам `@Test`-сценарий).

## Открытый вопрос (обсудим перед кодом)

В `design-patterns.md` #7 и в `Framework explanation/1-test-layer.md` реальная иерархия — **трёхуровневая**: `GreenphireBaseTest` (общий для всех продуктов) → `ClinCardBaseTest` (специфика конкретного продукта — свой логин, свои cleanup-хуки) → конкретный тестовый класс.

У нас пока один "продукт" — `automationexercise.com`. Вопрос: нужен ли нам сейчас промежуточный уровень (что-то вроде `AutomationExerciseBaseTest` между `BaseTest` и конкретными тестами), или для одного сайта это преждевременная абстракция — достаточно `BaseTest` → конкретный тестовый класс напрямую, а второй уровень добавим, когда (и если) в проекте появится второй сайт/продукт?

Второй, более мелкий вопрос: нужно ли `BaseTest` что-то делать в `@BeforeMethod`, или на этой задаче хватит одного `@AfterMethod`? Смотри, что сейчас происходит в каждом `@Test`: `Selenide.open(FrameworkConfig.APP_URL)`, `Selenide.open(FrameworkConfig.APP_URL + "/login")`, `Selenide.open(FrameworkConfig.APP_URL + "/view_cart")` — у разных тестов разная стартовая страница. Есть ли смысл выносить что-то общее в `@BeforeMethod` при таком разбросе, или это тот случай, где "варьируется от теста к тесту" перевешивает "одинаково у всех"?

## Теория

Новый материал — `theory/testng-lifecycle-and-template-method.md`: полный порядок выполнения хуков TestNG (`@BeforeSuite`/`@BeforeClass`/`@BeforeMethod`/`@Test`/`@AfterMethod`/`@AfterClass`), зачем `alwaysRun = true` на teardown-хуках, и как наследование тестовых классов реализует Template Method (базовый класс фиксирует шаги lifecycle, наследник добавляет только тело `@Test`).
