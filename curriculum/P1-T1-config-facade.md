# P1-T1 — Config Facade + порядок разрешения параметров

**Фаза / слой:** Фаза 1 — Конфигурация и инфраструктура
**Теги:** java, config

## Описание

Построить класс-фасад конфигурации (например `FrameworkConfig`) в **реальном пакете** (не default package — это первый настоящий класс фреймворка, не одноразовая заглушка; выбери и зафиксируй пакет, дальше в нём же будет жить весь `src/main`):

- Внутренний метод разрешения значения по ключу, цепочка в строгом порядке: **env var → system property → properties-файл**.
- Один `.properties`-файл в `src/main/resources/` с дефолтным значением хотя бы одного параметра (например `BASE_URL=https://automationexercise.com`), подключается через classpath.
- Наружу — простая статическая константа (`BASE_URL`), а не сырой вызов метода-резолвера, разбросанный по вызывающему коду.
- Осознанное решение, что происходит, если значение не найдено ни в одном источнике (не забыто молча).

## Место в фреймворке

Опирается на Фазу 0 (нужен рабочий `pom.xml`, класс должен компилироваться и подхватывать resources). От неё зависят все последующие слои, которым нужен URL/креды — Page Object (Фаза 4), API-сервисы (Фаза 7), БД-util (Фаза 9). Это первая реальная (не placeholder) единица кода фреймворка.

## Мотивировка

Без единой точки конфигурации каждый вызывающий код сам городит логику «откуда брать URL» — часть кода читает system property, часть — захардкодит строку, часть полезет в properties-файл напрямую. Это дублирование и рассинхрон между окружениями: локальный прогон и CI видят разные значения не потому что так задумано, а потому что логика получения URL с самого начала не централизована. Ошибка здесь (например, забытый приоритет источника) проявится не сразу, а как «на CI тест ходит не туда» — далеко от места настоящей причины.

## Типичные ошибки

Реальные ошибки, найденные за несколько раундов ревью этой задачи (обе части — сам `FrameworkConfig` и `FrameworkConfigSmokeTest`):

1. **Скопировал цепочку из референса, но потерял 2 из 3 веток.** Первая версия `getValue(key)` содержала только проверку `System.getenv(key)` и сразу бросала исключение, если её не было — ветки для system property и properties-файла отсутствовали. Результат: весь `static`-блок, загружающий `PROPERTIES` из файла, стал мёртвым кодом, а класс не мог загрузиться (`ExceptionInInitializerError`) без переменной окружения. Урок: при адаптации кода из чужого референса — не просто копировать форму, а понимать, что каждая ветка условия обязана быть перенесена, иначе получится не "тот же алгоритм, только по-своему", а другой, сломанный алгоритм.
2. **IDE-автодополнение подставило чужой метод по совпадению имени.** Первая версия имела `import static sun.net.NetProperties.get;` — внутренний служебный API JDK, вообще не связанный с собственным `PROPERTIES`. IDE предложила его, потому что метод с именем `get` ещё не существовал в классе на момент набора кода. Урок: автодополнение по имени метода — не гарантия правильного импорта, особенно когда своя реализация ещё не написана; всегда проверять, откуда реально взялся импорт.
3. **`InputStream` не закрывался — использован обычный блок кода вместо try-with-resources.** `InputStream in = ...; { PROPERTIES.load(in); }` выглядит похоже на `try (InputStream in = ...) { ... }`, но это просто голый блок кода — переменная объявлена ДО скобок `try`, а не внутри них, поэтому поток не закрывается автоматически. Урок: try-with-resources требует объявления ресурса именно в круглых скобках после `try`, а не где-то рядом с ней.
4. **`APP_URL` объявлен как `final` без присвоения значения** — не компилировалось в принципе на раннем черновике. Урок: `static final`-поле обязано получить значение либо сразу при объявлении, либо в статическом блоке, выполняющемся раньше него по тексту класса.
5. **IDE-ловушка при создании ресурса: "New Resource Bundle" вместо обычного файла.** Resource Bundle в IntelliJ — фича под i18n (создаёт группу `base_locale.properties` файлов), не обычный конфиг-файл. Нужен был обычный `New → File`. Урок: не всякий пункт меню с похожим названием — то, что нужно; уточнять назначение конкретной IDE-фичи, а не полагаться на созвучное название.
6. **В `FrameworkConfigSmokeTest`: `.body().toString()` вместо `.body().asString()`.** `.then().extract().body()` в REST Assured возвращает объект-обёртку ответа, а не текст; `.toString()` на нём даёт стандартное `ClassName@hashcode`, а не HTML. Тест с `assertNotNull(...)` на этой строке был зелёным всегда, независимо от реального содержимого ответа — ложное чувство защищённости. Урок: когда результат метода выглядит подозрительно "техническим" (адрес объекта, а не ожидаемые данные) — это сигнал, что вызван не тот метод из API библиотеки, а не что тест прошёл.
7. **Негативный тест на статус-код был логически поглощён позитивным.** Сначала `assertNotEquals(204, ...)` — не ловит вообще ничего осмысленного (почти любой код кроме 204 "проходит"). После сужения до `assertNotEquals(500, ...)` — стало более прицельно, но всё ещё логически избыточно: `200 ≠ 500` всегда, значит если первый тест (`assertEquals(200, ...)`) проходит — второй пройдёт автоматически, а если первый падает на каком-то коде, отличном от 500 (например 404) — второй тест всё равно молча "зелёный", хотя ситуация ненормальная. В итоге тест заменён на содержательно другую проверку (тело ответа), а не на более узкий вариант той же проверки статус-кода. Урок: "негативный" тест-компаньон должен проверять действительно ДРУГОЙ сценарий/ветку поведения, а не более узкую формулировку той же самой проверки — иначе это не дополнительное покрытие, а просто более длинный путь к тому же вердикту.
8. **Первая версия content-проверки была завязана на изменчивые данные каталога (`"/brand_products/Polo"`), а не на структуру страницы.** Сайт `automationexercise.com` — чужой, неконтролируемый источник; если бренд Polo уберут из каталога, тест упадёт по причине, не имеющей отношения к тому, что он должен проверять (жив ли `FrameworkConfig.APP_URL`). Заменено на структурный маркер (`"All Products"` — заголовок страницы). Урок: assert в smoke/content-тестах на внешние источники должен цепляться за стабильные структурные признаки страницы, а не за конкретные бизнес-данные, которые владелец сайта может поменять в любой момент независимо от тебя.
