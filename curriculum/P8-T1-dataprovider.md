# P8-T1 — @DataProvider + параметризованный тест

**Фаза / слой:** Фаза 8 — Продвинутые тестовые данные
**Теги:** java, testng

## Описание

Научить тесты принимать параметры: один `@Test`-метод, который TestNG запускает несколько раз с разными наборами данных из `@DataProvider`-метода.

Применяем не на выдуманном примере, а на реальном месте в твоём же коде — `LoginApiServiceTest` (P7-T1). Посмотри на него глазами "где здесь скрытая параметризация":

```java
@Test
public void incorrectCredentialsTest() {
    String incorrectEmail = "Qwedwe2@gmail.com";
    assertFalse(loginApiService.verifyLogin(incorrectEmail, FrameworkConfig.APP_USER_PASSWORD));
    String incorrectPassword = "Qwedwe2";
    assertFalse(loginApiService.verifyLogin(FrameworkConfig.APP_USER_EMAIL, incorrectPassword));
}
```

Это ОДИН тест, внутри которого вручную прошиты ДВА сценария одной и той же проверки ("невалидные креды → `false`"), различающиеся только данными. Задача: переписать через `@DataProvider` так, чтобы сценарий был описан один раз, а данные — отдельно, строками таблицы.

## Место в фреймворке

Зависимость: опирается на Фазу 7 (реальный `LoginApiService`, на котором параметризуем) и Фазу 6 (`BaseTest` — тестовый класс уже в общей иерархии).

От неё зависит: Фаза 10 (Test Coverage) — негативные сценарии регистрации/логина будут писаться сразу параметризованно, а не копипастой методов. P8-T2 — решение по ней принимается в этой же сессии (см. ниже).

## Мотивировка

Сейчас добавление третьего негативного сценария (например, "пустой email + валидный пароль") — это дописывание ещё двух строк в тело теста. Пятого — ещё двух. Тест растёт вниз, и при падении на третьем сценарии ты не увидишь в отчёте, КАКОЙ из пяти наборов данных упал — отчёт покажет один упавший `incorrectCredentialsTest`, а дальше — раскопки.

С `@DataProvider` каждый набор данных — **отдельный запуск теста в отчёте**: упал только `verifyLogin("", "Qwer1234")` — это видно сразу, остальные строки зелёные. Плюс данные отделены от логики: новый сценарий = новая строка массива, тело теста не трогается.

В боевом `java-selenide-pp` это один из самых используемых механизмов — весь `ClinCardMergeCardholderSuccessfullyBaseClass` построен на прогоне одного сценария по множеству конфигураций участников через `@DataProvider`.

## Открытые вопросы (обсудим перед кодом)

### Вопрос 1 — что именно попадает в провайдер, а что нет?

В `LoginApiServiceTest` сейчас три теста: `baseLoginApiTest` (позитив → `true`), `incorrectCredentialsTest` (два негатива → `false`), `exceptionTest` (два кейса → исключение). Искушение — затолкать ВСЁ в один провайдер "email, password, ожидаемый результат". Но у трёх групп **разные проверяемые исходы**: `assertTrue`, `assertFalse`, `assertThrows` — это разная логика тела теста, не разные данные.

Вопрос: какие из трёх тестов имеет смысл объединять под один `@DataProvider`, а какие должны остаться отдельными методами? Каким правилом ты бы это решал?

### Вопрос 2 — где живёт метод-провайдер?

`@DataProvider`-метод можно объявить в самом тестовом классе, а можно вынести в отдельный класс (`@Test(dataProvider = "x", dataProviderClass = Y.class)`). Референс держит провайдеры в тестовом классе. Что выберешь для двух-трёх строк данных и почему?

## Теория

Новый материал — `theory/testng-dataprovider.md`: механика `@DataProvider` (`Object[][]`, связка по имени, каждая строка = отдельный запуск в отчёте), сигнатура тестового метода должна совпадать со строкой массива, почему компилятор это НЕ проверяет (`Object[][]` стирает типы — связка живёт только в рантайме через рефлексию), краткое отличие от JUnit 5 `@ParameterizedTest`.

## Типичные ошибки

Одна из самых чистых задач проекта — код заработал с первой попытки, обе находки пойманы ещё на этапе обсуждения/гигиены, не в логике:

1. **Третий элемент строки провайдера не был подключён к телу теста (поймано устно, ДО кода).** В плане реализации ожидаемый результат лежал в строке провайдера (`{email, password, false}`), но тело теста предполагалось как `assertEquals(verifyLogin(email, password), true)` — с литералом `true`. Трассировка на строке с негативом показала: тест был бы красным на валидных данных, третий элемент строки никак не использовался. Исправление — третий элемент становится параметром метода (`boolean expected`) и встаёт в `assertEquals` вместо литерала. Классическая ошибка первого знакомства с `@DataProvider`: данные в строку положил, параметром не принял.
2. **Пакет теста не зеркалил пакет тестируемого класса:** `LoginApiServiceTest` лежал в `api`, тогда как `LoginApiService` — в `api.services` (и соседний `AccountApiServiceTest` уже был в `api.services`). Перенесён.

Сильные стороны: правило "один `@Test` = один класс исхода" не просто применено, а самостоятельно переформулировано точнее, чем в теории ("исход — boolean" объединяет и `true`, и `false`; исключение — отдельный класс исхода); негативные креды в провайдере — через `RandomDataGenerator`, а не хардкод, то есть гарантированно несуществующие и независимые от состояния сайта — собственное решение сверх обсуждённого.

**Решение по P8-T2 (принято в этой же сессии, 2026-08-01):** отложена до реальной потребности. Критерий из `PLAN.md` (≥3-4 связанных сущности на один прогон сценария) не выполняется ни одним текущим сценарием (логин — 1 сущность, аккаунт — 1 модель). Вернёмся, если Фаза 10 породит сценарий с достаточной связностью. Фаза 8 закрыта.

Живой прогон: сьют вырос с 18 до 20 тестов — 4 запуска `loginApiTest` по строкам провайдера видны в отчёте отдельно. `mvn clean test` — весь проект зелёный.
