# P4-T1 — Первая страница (HomePage/LoginPage) + навигационный переход

**Фаза / слой:** Фаза 4 — Page Object
**Теги:** java, selenide

## Описание

Первый Page Object проекта. Два маленьких класса, а не один — потому что сама суть навигационного метода в том, что он возвращает объект ДРУГОЙ страницы:

1. **`HomePage`** — главная страница `automationexercise.com`. Поле-обёртка на ссылку `Signup / Login` в шапке сайта (реальный локатор: `a[href='/login']`), метод `verifyPageIsOpen()` (fluent, возвращает `this`) и ОДИН навигационный метод `clickSignupLoginLink()`, который кликает и возвращает `new LoginPage()`.
2. **`LoginPage`** — пока только каркас: поле-обёртка на email-инпут формы логина (реальный локатор: `input[data-qa='login-email']` — тот же, что уже использовался в `InputElementTest` из P3-T1) и `verifyPageIsOpen()`. Полноценные методы логина/сигнапа на этой странице — предмет **P4-T2**, не этой задачи.

**Локаторы — инлайн, прямо внутри конструктора элемента** (`new ButtonElement($x("a[href='/login']"))`), без отдельных `static final String`-констант. Решено в живом обсуждении 2026-07-29 (было изначально предложено иначе — см. ниже): оба локатора этой задачи фиксированные, известны целиком уже сейчас, ничего в них не подставляется в рантайме — константа над таким локатором добавила бы второе имя для того же факта, который уже несёт имя самого поля (`signupLoginLink`), и не окупила бы себя.

## Место в фреймворке

Зависимость: опирается на Фазу 1 (`FrameworkConfig.APP_URL` — тест открывает главную страницу через конфиг, не хардкодит URL) и на Фазу 3 (`ButtonElement`/`InputElement` уже готовы, используются как есть, без изменений).

От этой задачи зависят: P4-T2 (доразвивает `LoginPage` и добавляет первый настоящий двухшаговый сценарий), вся Фаза 5 (Reusable Actions — оркестрация поверх нескольких POM) и Фаза 6 (тесты будут писаться через POM, не напрямую через Selenide).

## Мотивировка

Без Page Object локаторы и клики были бы разбросаны прямо по телам тестовых методов. Пример цены отказа: если бы 10 разных тестов сами открывали главную страницу и сами кликали `a[href='/login']`, а сайт вместо ссылки поставил бы кнопку с другим атрибутом — пришлось бы находить и править все 10 мест. С Page Object это одна правка в `HomePage.clickSignupLoginLink()`.

Отдельная причина именно ДВУХ классов (а не одного `HomePage` с методом `openLoginForm()`, возвращающим `void`): навигационный метод `clickSignupLoginLink()` физически переводит браузер на другую страницу. Если бы он возвращал `this` (то есть `HomePage`), в цепочке дальше можно было бы по ошибке вызвать метод главной страницы уже находясь на `/login` — компилятор бы это пропустил, а тест сломался бы в рантайме на элементе, которого больше нет на экране. Возврат `new LoginPage()` делает эту ошибку невозможной на уровне типов (см. `design-patterns.md` #1 и #2 в `java-selenide-pp`).

## Теория

- [theory/06-page-object-and-navigation.md](../theory/06-page-object-and-navigation.md) — Page Object на минимальном примере, почему навигационный метод возвращает `new NextPage()`, и ключевой вопрос "как это не падает, если следующая страница ещё не загрузилась" — разбирается через **Lazy Initialization** (`$`/`$x` не ищут элемент в момент вызова, а только запоминают локатор; реальный поиск с ожиданием происходит на первом `.should*`/`.click()`/`.setValue()`).
- Fluent Interface для `verifyPageIsOpen()` — уже знакомая идея из Фазы 3 (`BaseElement`/`InputElement`), просто на уровне страницы, а не элемента; в теории только фиксируется перенос, не разбирается заново.

## Типичные ошибки

1. **`HomePage` изначально всё же завёл локатор-константу** (`SIGNUP_LOGIN_LINK`), хотя по итогам обсуждения этой же сессии решили инлайнить фиксированные локаторы без констант — `LoginPage` в первой версии уже сделал правильно, `HomePage`, видимо, был написан до/по инерции от старой формулировки DoD. Поправлено — константа убрана, локатор ушёл прямо в конструктор `ButtonElement`.
2. **`BaseNavigationTest` не закрывал браузер** — не было `@AfterMethod` с `Selenide.closeWebDriver()`. Ровно тот же класс проблемы, что уже находили и фиксировали в P3-T2 ("тесты ломали друг друга при запуске всем пакетом" — общая сессия браузера между методами без сброса): тогда починили во всех четырёх тестах элементов, но конвенция не была перенесена автоматически на новый тестовый класс POM-слоя. Урок: новый тестовый класс, открывающий реальный браузер, — это не повод заново решать вопрос teardown'а, это уже settled конвенция проекта. Добавлено.
3. **Новый метод `BaseElement.shouldBe(WebElementCondition... var1)` нарушал оба принципа, установленных в Фазе 3:** возвращал `void` вместо `T` (единственный такой "action"-метод в иерархии — все остальные либо fluent (`T`), либо настоящий getter) и **не вызывал `waitAndGetElement()`** первым шагом, в обход центральной точки ожидания (`exist` → scroll → `visible`), которую все остальные методы (`click()`, `setValue()`) вызывают без исключений. Плюс параметр был назван `var1` (IDE-заглушка, не переименована). Поправлено самостоятельно после наводящих вопросов: `shouldBe(...)` теперь вызывает `waitAndGetElement()` первым шагом, возвращает `(T) this` (fluent, с `@SuppressWarnings("unchecked")` по аналогии с `waitAndGetElement()`), параметр переименован в `conditions`.
