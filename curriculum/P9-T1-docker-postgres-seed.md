# P9-T1 — Docker Postgres + схема + сид-данные

**Фаза / слой:** Фаза 9 — Слой БД
**Теги:** sql, docker

## Описание

Поднимаем СВОЮ базу данных: локальный PostgreSQL в Docker-контейнере, в нём — таблица `users` и несколько сид-строк. Это фундамент для всей Фазы 9: P9-T2 (JDBC-утилита) будет к этой базе подключаться, P9-T3 (SQL-верификация) — писать и читать из неё в тесте.

Напоминание, почему база своя (решение зафиксировано в `PLAN.md` ещё 2026-07-23): `automationexercise.com` доступа к своей БД не даёт, поэтому слой БД — самостоятельное упражнение на изолированной схеме. Механика при этом тренируется полноценно и один в один переносится на боевой проект.

Таблицу проектируешь сам — это часть задачи (DDL руками = прямая тренировка SQL к интервью). Ориентир: подмножество полей твоей же `AccountModel` — `id`, `name`, `email`, `password`, `country` + служебный `created_at`. Одно требование заложи обязательно: **`UNIQUE` на `email`**. Вспомни P7-T2 — API `automationexercise.com` молча создаёт дубликаты email. Вот где такие правила живут в нормальной системе: не в коде клиента, а в constraint'е БД — сервер физически не даст вставить второй такой же email. Готовый рассказ на интервью про то, чем ограничение в БД отличается от валидации в приложении.

## Место в фреймворке

Зависимость: опирается на Фазу 0 (репозиторий — файлы БД будут жить в нём). От Java-кода пока не зависит вообще — в этой задаче не пишется ни строчки Java.

## Открытые вопросы (обсудим перед кодом)

### Вопрос 1 — `docker run` или `docker-compose.yml`?

Один и тот же контейнер можно поднять двумя способами:
- **`docker run`** — одна команда в терминале со всеми флагами (`-e`, `-p`, `--name`...). Просто, но команда живёт в истории терминала/README — её надо не потерять и не опечатать.
- **`docker-compose.yml`** — декларативный файл в репозитории: вся конфигурация записана, поднимается через `docker compose up -d`, воспроизводимо на любой машине одной командой.

Референс перед глазами: `qa-arcade-trainer/docker-compose.yml`, сервис `postgres` (строки 9-22) — образ, env-переменные, порты, healthcheck. Что выберешь для нашего проекта и почему? Учти и портфолио-аспект (репозиторий публичный).

### Вопрос 2 — как создаётся схема и сид?

Два пути:
- **Вручную**: контейнер поднялся пустым → зашёл в `psql` → выполнил `CREATE TABLE` и `INSERT` руками. Каждый, кто клонирует репо, повторяет эти шаги сам.
- **Init-скрипты**: у официального образа Postgres есть механизм `/docker-entrypoint-initdb.d` — всё, что смонтировано в эту папку (`.sql`-файлы), выполняется автоматически при ПЕРВОЙ инициализации базы. Схема и сид лежат файлами в репозитории и накатываются сами.

Что выберешь и почему? Подумай о воспроизводимости и о том, что P9-T3 будет полагаться на известное стартовое состояние данных.

### Практическая деталь — порт (не вопрос, а предупреждение)

Хост-порт `5432` может быть занят локальным Postgres, а `5433` уже занят arcade-стендом (посмотри его compose — там прямо комментарий об этом). Выбери для нашей базы свободный порт, например `5434`, и разберись при этом, что означает запись `"5434:5432"` — какая из двух цифр чья.

## Типичные ошибки

Первая инфраструктурная задача проекта (ни строчки Java) и первый опыт с Docker/DDL — отсюда много находок именно синтаксического и модельного характера. Оба открытых вопроса решены верно: compose-файл вместо `docker run` (обоснование — стандарт индустрии, конфигурация версионируется), init-скрипты вместо ручного `psql` (обоснование — меньше ручных шагов, меньше поверхность для ошибки).

**Понятийные пробелы, закрытые до кода:**
1. **Проброс портов** — сам попросил объяснить, что это и зачем. Разобрано через аналогию «IP = здание, порт = квартира»: контейнер имеет собственную изолированную сеть, `5434:5432` — правило переадресации хост→контейнер. Проверочный вопрос (какое число попадёт в JDBC-строку) ответил верно. Попутно поправлена терминология: слушает порт **контейнер**, не образ.
2. **Структура задачи** — считал, что `docker-compose.yml` это «докер образ» и что нужно самому создать папку `/docker-entrypoint-initdb.d`. Разведено: образ (`postgres:16-alpine`) — готовый шаблон с Docker Hub, compose — рецепт запуска; `/docker-entrypoint-initdb.d` — путь ВНУТРИ контейнера, своя папка (`db/init`) монтируется в него. Ключевой момент понимания: `volumes: ./db/init:/docker-entrypoint-initdb.d` — **та же логика `хост:контейнер`**, что и у портов.
3. **Тихий отказ** — на вопрос «что будет, если `.sql` положить не в смонтированную папку» ответил «контейнер не поднимется». Реально: поднимется штатно, просто без таблиц, а узнаешь об этом только в P9-T2. Связано с уже пройденными случаями того же класса (`.toString()` вместо `.asString()` в P1-T1, assert без эффекта в P2-T1): «ошибок нет» ≠ «работает правильно».

**Находки ревью — compose:**
4. Лишний пробел в пути: `/docker-entrypoint-init db.d` — привёл бы ровно к тихому отказу из пункта 3. Нашёл сам после указания на строку.
5. `POSTGRES_DB: custom-db` — дефис делает имя неидентификатором (потребовал бы двойных кавычек в SQL); переименовано в `aqa_db` по конвенции.

**Находки ревью — схема:**
6. **Дата рождения тремя колонками `TIMESTAMP` + несуществующий синтаксис** `DEFAULT DAY 01` / `MONTH 01` / `YEAR 2001`. Две ошибки в одной: (а) такой конструкции в SQL нет, скрипт бы упал; (б) главное — форма API (три отдельных параметра HTML-формы) была скопирована в модель данных, хотя дата рождения — **одно значение**. Прямой повтор урока P7-T2, где три независимых вызова генератора давали три несвязанные даты. Исправлено на одну колонку `DATE`.
7. `title VARCHAR(3) DEFAULT 'Mr.'` — влезает `'Mr.'` (3 символа), но не `'Mrs.'` (4). Латентный баг, который выстрелил бы на сиде.
8. `created_at TIMESTAMP` без `DEFAULT` — поле, смысл которого в автозаполнении, заполнялось бы только вручную.

**Находки ревью — сид:**
9. **Двойные кавычки для строковых литералов** (`"testUser1"`) — реальный концептуальный пробел: в SQL `'одинарные'` = значение, `"двойные"` = идентификатор (колонка/таблица). Postgres искал бы колонку с именем `testUser1`.
10. `VALUES` повторялся перед каждой строкой + лишняя запятая; форма множественной вставки — `VALUES (...), (...), (...)`, ключевое слово один раз.
11. **Транспонированная группировка**: после исправления пункта 10 сгруппировал значения **по колонкам** (в одной скобке — три имени, в другой — три email) вместо **по строкам**. Разобрано на изолированном примере (`books`, 2 колонки × 2 строки) с правилом «значений в скобке = колонок; скобок = строк».
12. Опечатка `lst_name` — колонки с таким именем в схеме нет.
13. `birth_date` со значением `''` (пустая строка) вместо `NULL` — Postgres упал бы на приведении к `DATE`. Тот же принцип «пусто ≠ нет значения», который уже встречался в P7-T2 (API: `email=` даёт 404, отсутствующий параметр — 400).

**Сильные стороны:** `CHECK (birth_date <= CURRENT_DATE)` придумал и добавил сам, никто не просил — ровно то, ради чего constraints существуют, и готовый пример для интервью в дополнение к `UNIQUE`; после замечания про длины `VARCHAR` не просто «увеличил всё», а подобрал по смыслу каждого поля, а `password` взял ровно 60 — размер bcrypt-хеша из объяснения; в сиде одна строка получила `birth_date = CURRENT_DATE` — граничное значение собственного `CHECK`.

**Побочный урок из живого прогона (не ошибка Дениса):** при проверке готовности `pg_isready -U postgres -d <несуществующая_база>` ответил «готов» — эта утилита проверяет только, что сервер принимает соединения, а не доступность конкретной базы. Тот же класс, что «health-check возвращает 200, а сервис нерабочий» (README `qa-arcade-trainer`) — готовый пример для вопроса про диагностику на интервью.

**Живая проверка (DoD выполнен полностью):** контейнер поднят через `docker compose up -d`, логи инициализации без ошибок, `\d users` показывает все ограничения (`PRIMARY KEY`, `UNIQUE users_email_key`, `CHECK users_birth_date_check`), `SELECT` возвращает 3 сид-строки с сработавшими дефолтами (`created_at`, `title`, `company`). Попытка вставить дубликат email отбита базой: `ERROR: duplicate key value violates unique constraint "users_email_key"`.
