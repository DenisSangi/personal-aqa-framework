# P2-T2 — DateTimeUtil

**Фаза / слой:** Фаза 2 — Утилиты
**Теги:** java

## Описание

Построить класс-утилиту `DateTimeUtil` (статические методы, без состояния) с узкой задачей: получить текущую дату/время в виде строки, отформатированной под ПРОИЗВОЛЬНЫЙ переданный паттерн. Это НЕ полный аналог референса (там ~15 методов — парсинг чужих строк дат, сравнение часовых поясов, арифметика "N дней назад/вперёд") — для нашего фреймворка сейчас нужен только один практический сценарий: уникальный суффикс для имени тестовой сущности.

Минимум:
- Метод, принимающий строку-паттерн и возвращающий текущую дату/время, отформатированные по нему (сигнатуру и имя выбери сам — обоснуй на ревью).
- Минимум 2 именованных константы для часто нужных паттернов (по образцу `DD_MMM_YY_HH_MM` из референса) — реши сам, какие форматы реально пригодятся: один — под уникальный суффикс имени (дата+время до секунд), другой — под что-то попроще (например, только дата).

Открытый вопрос на обсуждение (не решай в одиночку): стоит ли уже сейчас добавлять `Locale.ENGLISH` вторым параметром в `DateTimeFormatter.ofPattern(...)`, или это преждевременно, пока в паттернах не используются буквенные имена месяцев (`MMM`)? Разберём на созвоне.

## Место в фреймворке

Зависимость: опирается на Фазу 0. Полностью независим от `FrameworkConfig` (P1-T1) и `RandomDataGenerator` (P2-T1) — самостоятельная утилита. От неё зависит Фаза 8 (продвинутые тестовые данные — уникальные имена сущностей = случайная часть из P2-T1 + датовая часть из P2-T2) и Фаза 10 (реальные тесты регистрации/создания сущностей).

## Мотивировка

Та же проблема коллизий, что и в [P2-T1](P2-T1-random-generators.md), но с другого угла: случайная строка снижает шанс коллизии почти до нуля, но не даёт человеку, читающему отчёт теста или базу данных вручную, сразу понять, КОГДА была создана сущность и из какого прогона она осталась (актуально при отладке "почему в системе застряли тестовые данные недельной давности"). Дата в имени сущности — это одновременно антиколлизийный механизм и человекочитаемый след прогона. В `clincard-ui-test-automation` это закреплено прямо как конвенция: "always include `getTodayDateByFormat(DD_MMM_YY_HH_MM)` in entity names to avoid collisions between runs".

Цена отказа: без датового суффикса тестовые сущности от разных прогонов невозможно быстро отличить друг от друга при ручной отладке в БД/админке — приходится смотреть на внутренние ID или логи, что медленнее и менее надёжно, чем прочитать дату прямо в имени.

## Теория

- `java.time`: `LocalDateTime` (неизменяемость, отличие от старого `Date`/`Calendar`), `DateTimeFormatter.ofPattern(...)`, буквы паттерна и ловушка `MM` (месяц) vs `mm` (минуты), роль `Locale`.
- Потокобезопасность `DateTimeFormatter` vs `SimpleDateFormat` — параллель с `Random`/`ThreadLocalRandom` из P2-T1.

## Решение по открытым вопросам

- **Метод:** `getTodayDateByFormat(String pattern)`, возвращает `String` — имя выбрано по образцу референса, обосновано на ревью.
- **Паттерны:** `DATE_AND_TIME_FORMAT = "yyyy-MMM-dd_HH-mm-ss"` (уникальный суффикс, включает буквенный месяц — сознательно, см. ниже), `DATE_ONLY_FORMAT = "yyyy-MM-dd"`.
- **`Locale`:** Денис сам предложил завести суффикс через буквенное имя месяца (`MMM`) именно для того, чтобы `Locale.ENGLISH` был не формальностью "на будущее", а реально влиял на результат уже сегодня — совпадает с конвенцией референса (`DD_MMM_YY_HH_MM`).

## Типичные ошибки

1. **Хардкод сегодняшней даты в ожидаемом значении теста.** Первая версия теста сравнивала результат с буквальным литералом `"2026-07-28"` — тест сломался бы в любой другой день. Найдено наводящим вопросом ("что будет с тестом завтра?"), не готовым ответом.
2. **Частичное покрытие после первого фикса.** Промежуточная версия стала вычислять "сегодня" динамически (`LocalDateTime.now().format(...)`), но для `DATE_AND_TIME_FORMAT` сравнивала только через `contains()` с датой БЕЗ времени — часть паттерна с `HH-mm-ss` оставалась фактически непроверенной (сломай `HH` на `hh` — тест всё равно останется зелёным).
3. **Тест частично зеркалит продакшн-код.** Промежуточная версия строила ожидаемое значение через тот же `DateTimeFormatter.ofPattern(...)`, что и код под тестом — независимой проверки не давало. Разобрано как общий принцип (не блокирующий фикс, а тема для интервью).
4. **Финальное решение — независимый regex через `matches()`.** Денис сам перевёл каждую букву паттерна в соответствующий класс символов (`\d{4}`, `[A-Z][a-z]{2}`, `\d{2}` и т.д.) и сравнил ПОЛНУЮ строку через `matches()` (не `contains()`) — теперь покрыта вся строка, включая время, без переиспользования кода из `DateTimeUtil`.
5. **`@Getter` от Lombok на классе без единого поля-кандидата.** Все константы и так `public static final` (прямой доступ), геттер не нужен и не для чего — мёртвая аннотация, скопированная по привычке. Убрана самостоятельно после вопроса "какому полю нужен геттер?".
6. **Неиспользуемый импорт** (`java.time.LocalDateTime` в тестовом классе, до того как он реально понадобился для динамической даты) — гигиенический момент, убран самостоятельно.

_Отдельно, не ошибка Дениса: обнаружена и устранена проблема окружения — `mvn clean test` в изолированной среде агента падал на `Domains.java` ("cannot find symbol: getDomain()"), потому что `JAVA_HOME` в этой среде резолвился в слишком новый Homebrew JDK 26, несовместимый с annotation processing Lombok `1.18.46`. В реальном терминале Дениса `~/.zshrc` уже содержал верный `export JAVA_HOME=$(/usr/libexec/java_home -v 22)` — проблема была специфична для среды агента, не для рабочего окружения Дениса. Отдельно проверена и поправлена настройка Project SDK / Maven Runner JRE в IntelliJ — тесты зелёные и там._
