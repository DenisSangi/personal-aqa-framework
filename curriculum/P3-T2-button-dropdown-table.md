# P3-T2 — ButtonElement / DropdownElement / TableElement

**Фаза / слой:** Фаза 3 — Слой element-обёрток
**Теги:** java, selenide

## Описание

Закрепление паттерна из [P3-T1](P3-T1-base-element-input.md) на трёх новых типах взаимодействия — без новой архитектуры, `BaseElement<T>` и `waitAndGetElement()` уже готовы и переиспользуются как есть:

1. **`ButtonElement extends BaseElement<ButtonElement>`** — минимум `click()` (сначала `waitAndGetElement()`, потом `element.click()`).
2. **`DropdownElement extends BaseElement<DropdownElement>`** — минимум `selectOption(String option)` и `getSelectedOptionText()`.
3. **`TableElement extends BaseElement<TableElement>`** — минимум `getRows()` (коллекция строк через `$$`) и `containsText(String text)`.

**Сознательно НЕ входит в объём** (референсы `ButtonGPElement`/`DropdownGPElement`/`TableGPElement` — десятки методов каждый, `TableGPElement` — самый большой класс в референсе, ~450 строк): клик по координатам/через JS, работа с датами внутри таблицы, поиск ячейки по имени столбца/строки, множественные перегрузки `selectOption`. Это конкретные задачи под конкретные будущие сценарии (Фаза 10), не нужны заранее.

## Место в фреймворке

Зависимость: полностью опирается на P3-T1 (`BaseElement`) — ничего нового в базовом слое не создаётся. Вместе с `InputElement` эти три класса закрывают набор обёрток, которого достаточно для старта Фазы 4 (Page Object).

## Мотивировка

Прямая проверка того, зачем вообще строился `BaseElement` в P3-T1: если бы `waitAndGetElement()` пришлось писать заново для каждого нового типа элемента — три новых класса означали бы три копии одной и той же логики ожидания (и три места, где её потом чинить/чуть-чуть по-разному сломать). Сейчас каждый новый адаптер — это только его СОБСТВЕННАЯ специфика (клик, выбор опции, чтение строк), общая часть уже есть и переиспользуется бесплатно.

Цена отказа: без общей базы каждая новая обёртка копирует wait/scroll-логику вручную — расхождения неизбежны (кто-то забудет скролл, кто-то использует другой timeout), и это ровно та проблема "зоопарка ожиданий", которую P3-T1 должен был решить раз и навсегда.

## Теория

- Selenide API для клика/`<select>`/коллекций (`$$`, `ElementsCollection`) — новый раздел добавлен в конец [theory/05-selenide-basics-and-generics.md](../theory/05-selenide-basics-and-generics.md), самого self-bounded generic заново разбирать не нужно.

**Открытый вопрос на обсуждение (не решай в одиночку):** `getRows()` должен возвращать `ElementsCollection` (сырой Selenide-тип) или как-то иначе (например, обернуть каждую строку в `TableElement`)? В P3-T1 мы разобрали, почему `waitAndGetElement()` НЕ должен возвращать `SelenideElement` — та же логика тут применима один в один, или есть разница? (Подсказка на подумать: там был возврат ОДНОГО элемента для дальнейших ДЕЙСТВИЙ через него, здесь — набор элементов для ЧТЕНИЯ.)

## Definition of Done

- [x] `ButtonElement extends BaseElement<ButtonElement>` — `click()`, вызывает `waitAndGetElement()` первым шагом.
- [x] `DropdownElement extends BaseElement<DropdownElement>` — `selectOption(String)` и `getSelectedOptionText()`, оба вызывают `waitAndGetElement()` первым шагом.
- [x] `TableElement extends BaseElement<TableElement>` — `getRows()` (через `$$x`) и `containsText(String)`, оба вызывают `waitAndGetElement()` первым шагом.
- [x] Осознанное решение по открытому вопросу — `getRows()` возвращает `ElementsCollection` (не `List<String>`): чтение, не действие, менять состояние страницы нечем, а переизобретать богатый API коллекции не нужно.
- [x] Живой прогон — по одному реальному сценарию на каждый из трёх классов: `ButtonElementTest` (подписка на рассылку), `DropdownElementTest` (регистрация + выбор дня рождения), `TableElementTest` (логин + корзина).
- [x] Компилируется, `mvn clean test` зелёный (весь проект, 14/14, стабильно на повторных прогонах).

## Типичные ошибки

Насыщенная ревью-сессия — большинство находок про инфраструктуру тестов (стабильность, изоляция), а не про сами классы-обёртки:

1. **`getRows()` сначала вернул `List<String>` вместо `ElementsCollection`.** Первая реализация сразу звала `.texts()` внутри метода — теряла доступ к конкретной строке как к элементу, хотя мы только что договорились о возврате коллекции. Поправлено после вопроса "что мы теряем".
2. **Локатор `(//button)[1]` на `ButtonElementTest` попал не туда.** "Первая кнопка на странице" оказалась кнопкой из рекламного виджета Google (`#google_vignette`), а не элементом сайта — урок про хрупкость позиционных локаторов на реальных страницах со сторонней рекламой.
3. **Перепутан порядок аргументов `assertEquals` в TestNG.** JUnit — `assertEquals(expected, actual)`, TestNG — наоборот, `assertEquals(actual, expected)`. Первая версия следовала JUnit-порядку.
4. **Тест `ButtonElementTest` временно перестал проверять `click()`.** Промежуточная версия проверяла `testingButtonElement.element.isEnabled()` — прямое обращение к `protected`-полю в обход публичного API обёртки, и `click()` вообще не вызывался. Переписано на реальный сценарий (заполнить email → кликнуть Subscribe → проверить сообщение об успехе).
5. **`element.$$(".//tr")` — CSS вместо XPath (ошибка в материале Tech Lead'а, не Дениса).** В `theory/05-selenide-basics-and-generics.md` был неточный пример: `.$$(...)` трактует строку как CSS-селектор, для XPath нужен отдельный метод `.$$x(...)`. Приводило к `InvalidSelectorException`. Теория поправлена, `TableElement.getRows()` — тоже.
6. **Тесты ломали друг друга при запуске всем пакетом.** По отдельности каждый тест был зелёным, а вместе (`mvn clean test`) — 3 из 14 падали: один тест логинился и оставлял сессию в браузере, следующий тест ожидал "чистую" стартовую страницу (например, форму регистрации на `/login`) и не находил нужных полей, потому что уже залогиненного пользователя сайт с `/login` редиректит. Причина — Selenide не закрывает браузer между тестовыми методами сам. Исправлено добавлением `@AfterMethod` с `Selenide.closeWebDriver()` во все четыre тестовых класса (`InputElementTest`, `ButtonElementTest`, `DropdownElementTest`, `TableElementTest`) — сознательно точечно, без построения общего базового тестового класса (это отдельная будущая Фаза 6).
7. **Race condition между `loginButton.click()` и последующим `Selenide.open(...)`.** Сабмит формы логина сам вызывает редирект на сайте; сразу следующий явный `Selenide.open(/view_cart)` иногда "терял гонку" и оставался на исходной странице. Три попытки исправить:
   - `assertEquals(url, ...)` — не решение, эта проверка ОДНОРАЗОВАЯ, не повторяется (не "ждёт"), поэтому просто падала в момент гонки.
   - `Selenide.webdriver().shouldHave(urlContaining(APP_URL))` — логическая ошибка: `/login` тоже содержит `APP_URL` как подстроку, поэтому условие было бы истинным ДАЖЕ БЕЗ реального редиректа — ничего не проверяло по существу.
   - Финально сработало: `Selenide.webdriver().shouldHave(url(APP_URL + "/"))` — точное совпадение с реальным URL после редиректа (со слэшем), НАСТОЯЩЕЕ ожидание с повторами через `shouldHave`.
8. **`@Slf4j` от Lombok без единого вызова `log`.** Тот же класс ошибки, что `@Getter` в P2-T1 — мёртвая аннотация, добавленная по привычке.

Оставшийся, не блокирующий момент: изредка (не воспроизводится стабильно) `mvn clean test` ловит обычный сетевой/браузерный таймаут на реальном сайте (`TimeoutException`/CDP-предупреждения о версии Chrome 150) — это общая нестабильность живого стороннего сайта под текущими короткими таймаутами Selenide, не логическая ошибка кода. Решается позже (более длинные таймауты / retry-механизм) — не в рамках этой задачи.
