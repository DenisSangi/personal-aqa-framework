# ThreadLocal-изоляция WebDriver и параллельный прогон в TestNG

Нужны для Задачи [P12-T1](../curriculum/P12-T1-threadlocal-parallel.md). Понятие `ThreadLocal` как такое уже вводилось на примере `ThreadLocalRandom` — см. [03-random-and-threadlocalrandom.md](03-random-and-threadlocalrandom.md). Здесь та же идея, но применённая не к генератору случайных чисел, а к WebDriver и к состоянию, которое реально живёт в этом фреймворке.

## Напоминание: что такое `ThreadLocal` в одном предложении

`ThreadLocal<T>` — не "потокобезопасная версия T", а контейнер, у которого **каждый поток видит свою собственную, независимую копию** значения; чтения и записи одного потока не видны и не мешают другому. Не синхронизация (не "по очереди"), а изоляция (не пересекаются вообще).

## Проблема без ThreadLocal — на изолированном примере

```java
public class Counter {
    private static int value = 0; // ОДНО поле, общее на все потоки

    public static void increment() { value++; }
    public static int get() { return value; }
}
```

Если два потока одновременно зовут `increment()`, `value++` — это не одна атомарная операция (прочитать → прибавить → записать), поэтому конкурентные вызовы могут "затереть" друг друга. Решить можно двумя разными способами:
- **`synchronized`/`AtomicInteger`** — потоки по очереди безопасно делят ОДНО значение.
- **`ThreadLocal<Integer>`** — у каждого потока СВОЁ значение, делить вообще нечего.

Для WebDriver в параллельном UI-прогоне нужен именно второй вариант: браузер потока A не должен быть виден потоку B ни при каких обстоятельствах — не "по очереди", а "у каждого свой".

## Ключевой факт этой задачи: WebDriver в этом фреймворке уже не расшарен

В отличие от учебной постановки "напиши свой `ThreadLocal<WebDriver>` с нуля", в этом фреймворке нет ни одного собственного поля-держателя драйвера — весь доступ идёт через статические методы Selenide (`Selenide.open(...)`, `$`, `$$`). Это не значит, что вопрос ThreadLocal тут не при чём — значит, что его уже решил сам Selenide, а не мы.

Проверено декомпиляцией реального jar-файла из зависимостей проекта (`~/.m2/repository/com/codeborne/selenide/7.2.3/selenide-7.2.3.jar` — та же версия, что подтягивается `selenide-testng` в `pom.xml`):

```
com/codeborne/selenide/WebDriverRunner.class
com/codeborne/selenide/impl/ThreadLocalSelenideDriver.class
com/codeborne/selenide/impl/WebDriverThreadLocalContainer.class
```

Имена классов говорят сами за себя: Selenide внутри себя держит драйвер именно в `ThreadLocal`-контейнере. Когда тест на потоке A вызывает `Selenide.open(...)`, новый драйвер создаётся и кладётся в ячейку, привязанную к потоку A; поток B, вызывая `$(...)`, получает драйвер из СВОЕЙ ячейки. Это ровно тот же паттерн, что выше в игрушечном `Counter`, только вместо `int` — `WebDriver`.

**Практический вывод:** не нужно (и не следует) заводить в проекте собственное поле `ThreadLocal<WebDriver>` — это дублировало бы то, что уже сделано библиотекой, добавляло бы второй источник правды и риск рассинхронизации. Задача — не *реализовать* изоляцию, а (1) убедиться, что она действительно есть, вместо того чтобы поверить на слово, и (2) настроить TestNG так, чтобы ей было что изолировать — то есть реальный параллельный прогон.

## Другой класс проблемы: расшаренные данные, а не драйвер

ThreadLocal в реальных фреймворках нужен не только для драйвера. Пример из референсного проекта (`clincard-ui-test-automation/.../UserService.java`) — пул тестовых пользователей: у сервиса есть общий `ConcurrentHashMap<ClinCardUser, Integer>` (доступные пользователи, общие на все потоки — их специально делят, окружение одно на всех) и `ThreadLocal<ClinCardUser>` (пользователь, которого **этот конкретный поток** сейчас "занял"). Здесь ThreadLocal и общее состояние сосуществуют в одном классе, каждое для своей цели — общий пул специально общий (иначе не из чего выбирать), а "что занято именно мной" обязано быть отдельным для каждого потока.

Это тот же принцип, который стоит вынести из задачи как общий вопрос: параллельный прогон ломается не только на драйвере, а на **любом мутабельном состоянии, которое случайно оказалось общим на несколько потоков**. Отсюда в DoD задачи — не только настройка `testng.xml`, но и осознанная проверка остального кода фреймворка на этот класс риска.

## TestNG: `parallel` и `thread-count`

Параллельность в TestNG настраивается в suite-файле (`testng.xml`), не в самих тестах:

```xml
<suite name="Suite" parallel="methods" thread-count="4">
    <test name="Test">
        <classes>
            <class name="tests.ProductsMainFlowTest"/>
            <class name="tests.LoginTest"/>
        </classes>
    </test>
</suite>
```

- **`parallel="methods"`** — каждый `@Test`-метод из всех перечисленных классов может выполняться в своём потоке (самая мелкая гранулярность).
- **`parallel="classes"`** — методы одного класса выполняются последовательно в одном потоке, но разные классы — параллельно друг другу.
- **`parallel="tests"`** — параллельны `<test>`-блоки suite-файла целиком (крупная гранулярность, для разделения по группам/окружениям).
- **`thread-count`** — верхняя граница числа одновременных потоков (пул), не гарантированное число — если тестов меньше, часть потоков просто не понадобится.

`parallel="methods"` — самая требовательная к thread-safety гранулярность (методы ОДНОГО класса могут оказаться на разных потоках одновременно), поэтому именно на ней честнее всего проверяется вся цепочка выше: и Selenide-драйвер, и `FrameworkConfig`, и генераторы случайных данных.

## Как реально запустить suite-файл через Maven Surefire

Сам по себе `testng.xml` ничего не запускает — Maven Surefire нужно явно на него указать. В референсном проекте (`clincard-ui-test-automation/pom.xml`) это делается через системное свойство:

```
-Dsurefire.suiteXmlFile=<путь-к-suite.xml>
```

тогда как plugin-конфигурация в `pom.xml` подставляет туда переданное значение (или дефолтное, если параметр не передан):

```xml
<suiteXmlFiles>
    <suiteXmlFile>${surefire.suiteXmlFile}</suiteXmlFile>
</suiteXmlFiles>
```

Без такого файла Surefire по умолчанию просто находит все классы `Test*`/`*Test`/`*Tests` в classpath и гоняет их — без параллельности от TestNG вообще (максимум — собственный, куда более грубый параллелизм самого Surefire, если явно включён отдельно). Поэтому "positional" параллелизм из PLAN.md ("parallel="methods"/"classes" в testng.xml") без подключения suite-файла к Surefire не даст никакого эффекта — файл просто не будет использован при `mvn test`.

## Как убедиться, что прогон РЕАЛЬНО параллельный, а не просто быстрый

Быстрый прогон — не доказательство параллельности (сеть/сайт могли быть просто быстрыми в этот раз). Надёжный способ — залогировать имя потока в начале каждого теста:

```java
System.out.println(Thread.currentThread().getName() + " -> " + testName);
```

Если в выводе видно несколько разных имён потоков (`TestNG-methods-1`, `TestNG-methods-2`, ...) вперемешку по времени — прогон действительно параллельный. Один и тот же поток на все тесты — конфигурация не сработала (файл не подключился, либо `thread-count="1"`).
