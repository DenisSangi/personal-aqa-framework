# 18 — Ожидания: implicit, explicit, fluent (и что такое «динамические»)

Опора для [P12-T2](../curriculum/P12-T2-parallel-hardening.md), Вопрос 1. Написан 2026-08-11 по итогам живого разбора — все факты о библиотеках проверены на версиях, реально лежащих в зависимостях проекта, а не взяты из статей.

---

## 1. Проблема, из которой всё выросло

Код выполняется мгновенно, страница — нет. Между «нажали кнопку» и «модалка отрисовалась» проходит время, и оно каждый раз разное.

Измерено на нашем целевом сайте (10 запросов `curl`, только сетевая часть — без рендеринга, ресурсов страницы и рекламы):

```
мин 0.48 с → медиана 0.79 с → макс 1.69 с      (разброс в 3.5 раза)
```

Наивное решение — фиксированная пауза:

```java
Thread.sleep(5000);
$("#btn").click();
```

Плохо всегда: если страница ответила за 0.3 с — потеряли 4.7 с на ровном месте; если за 6 с — всё равно упали. Пауза не связана с реальностью.

## 2. Ядро: любое настоящее ожидание — это опрос в цикле

Механизм всех трёх видов одинаков:

```java
long deadline = now() + timeout;
while (now() < deadline) {
    if (условиеВыполнено()) return;   // ← выход СРАЗУ, как только готово
    sleep(pollingInterval);            // короткая пауза между проверками
}
throw new TimeoutException();
```

**Главное следствие, которое стоит уметь сформулировать:** таймаут — это **потолок**, а не длительность. Если элемент появился за 200 мс, ожидание вернётся через 200 мс, даже если лимит стоит 10 секунд.

Практическое подтверждение из нашего проекта: поднятие `Configuration.timeout` с 4 до 10 секунд **не замедлило** сьют — успешные прогоны как шли ~48 секунд, так и идут. Замедляются только настоящие падения (ждут дольше, прежде чем сдаться).

Три вида ожиданий отличаются ровно двумя вещами: **что стоит в `условиеВыполнено()`** и **кто его задаёт**.

## 3. Implicit (неявное)

Настраивается один раз на драйвер, дальше действует само:

```java
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
driver.findElement(By.id("btn"));   // сам подождёт появления
```

Условие зашито и всегда одно: **«элемент появился в DOM»**. Ни видимость, ни кликабельность не проверяются. В коде теста ожидания не видно вообще.

### Почему одного implicit не хватает

Живой пример из падения `proceedToCheckoutTest` (P12-T1, Сессия 15):

```
Element should be visible {div[class='modal-content'] h4}
Element: '<h4 class="modal-title w-100" displayed:false></h4>'
```

Элемент **найден** — Selenide печатает его разметку. Но `displayed:false`: он в DOM и при этом невидим. Implicit wait здесь бесполезен — его условие «есть в DOM» выполнилось сразу, он вернул бы элемент мгновенно, и следующая строка упала бы. Спасло явное условие `visible`.

### Вторая ловушка: implicit работает и там, где вреден

```java
driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
assertTrue(driver.findElements(By.id("error")).isEmpty());   // честно ждёт все 10 секунд
```

Элемента нет — это ровно то, что проверяется. Но implicit об этом не знает и добросовестно опрашивает DOM весь таймаут, прежде чем вернуть пустой список. Выключить точечно нельзя — он глобальный.

## 4. Explicit (явное)

Пишется в конкретном месте под конкретное условие:

```java
new WebDriverWait(driver, Duration.ofSeconds(10))
    .until(ExpectedConditions.elementToBeClickable(By.id("btn")))
    .click();
```

Условие — любое: видимость, кликабельность, текст, URL, исчезновение спиннера. Многословно, зато точно и видно в коде.

## 5. Fluent — и чем он на самом деле приходится explicit'у

```java
Wait<WebDriver> wait = new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(10))
    .pollingEvery(Duration.ofMillis(200))          // как часто опрашивать
    .ignoring(NoSuchElementException.class);       // что игнорировать по пути
```

Факт, проверенный `javap` по `selenium-support-4.19.1` (версия из нашего дерева зависимостей):

```
public class WebDriverWait extends FluentWait<WebDriver>
```

То есть привычный `WebDriverWait` — **это и есть FluentWait**, просто с предзаданными интервалом опроса и списком игнорируемых исключений. Не два разных механизма, а базовый класс и его удобная обёртка.

## 6. Что такое «динамические ожидания»

**Это не термин из документации.** Официальных вида три: implicit, explicit, fluent.

В обиходе (статьи, курсы, чек-листы к собеседованиям) «динамическими» называют любые ожидания, завершающиеся **по факту готовности**, а не по часам — то есть противопоставляют их «статическому» `Thread.sleep`. Под это определение попадают сразу explicit, fluent и встроенные ожидания современных библиотек. Иногда этим словом называют конкретно последние (Selenide, Playwright, Cypress) — те, где `wait` не пишут руками.

**Как отвечать на интервью:** на вопрос «какие бывают ожидания» — implicit / explicit / fluent, это проверяемая терминология. Если интервьюер сам употребил «динамические» — уточнить, что он имеет в виду; за словом стоят разные вещи, и уточняющий вопрос здесь не признак незнания.

## 7. Как это устроено в нашем фреймворке

Selenide fluent по своей природе — ожидание встроено в каждое действие и проверку, отдельной строки `wait` нет:

```java
$("#btn").click();               // ждёт готовности перед кликом
$("#btn").shouldBe(visible);     // явное условие, время — из Configuration.timeout
```

Проверено по `selenide-core-7.2.3`:

| Что проверяли | Как | Результат |
|---|---|---|
| Использует ли Selenide implicit wait | `grep implicitlyWait` по всем классам | **ни одного упоминания** |
| Откуда берётся таймаут | байткод `SelenideConfig` | property `selenide.timeout`, дефолт `4000` |
| Интервал опроса | байткод `SelenideConfig` | property `selenide.pollingInterval`, дефолт `200` |

Подставив наши значения в цикл из раздела 2:

```
жду до 10000 мс, проверяю каждые 200 мс  →  до 50 проверок за одно ожидание
```

Именно это и происходило в падении: Selenide 50 раз спросил «модалка уже видима?», получил 50 отказов и бросил `ElementShould`. Тот же механизм возвращается мгновенно, если ответ «да» пришёл на второй проверке.

**Почему Selenide сознательно не использует implicit:** внутри каждой попытки собственного опроса драйвер начинал бы молча ждать своё implicit-время, таймауты складывались бы непредсказуемо, и 10 секунд превращались бы в минуту. Отсюда общее правило: **смешивать implicit и explicit — классическая ошибка**.

## 8. Что важно не перепутать

Изменение `Configuration.timeout` в P12-T2 **не меняло тип ожиданий**. Было:

```java
Selenide.webdriver().shouldHave(url(APP_URL + "/"), Duration.ofSeconds(3));
```

стало:

```java
Selenide.webdriver().shouldHave(url(APP_URL + "/"));
```

Ожидание было явным и осталось явным — условие `url(...)` никуда не делось. Убрано только локально заданное **время**, теперь оно берётся из общей настройки. `Configuration.timeout` — это не implicit wait, а время по умолчанию для явных ожиданий Selenide.

## 9. Итог 20/80

1. Ожидание — это **опрос в цикле**, а не пауза. Таймаут = потолок, а не длительность.
2. **Implicit ждёт только наличие в DOM** — для реального UI мало: элемент может быть на месте и при этом невидим или перекрыт.
3. **Explicit ждёт любое условие в конкретном месте** — поэтому в проектах используют его.
4. **`WebDriverWait extends FluentWait`** — explicit в Selenium технически и есть fluent.
5. **Selenide = явные ожидания по умолчанию**, implicit не используется принципиально.
6. **Смешивать implicit и explicit нельзя** — таймауты складываются.

Пункты 2 и 6 спрашивают чаще всего, и на оба есть свой пример из этого проекта, а не из учебника.
