# CI и Jenkins — верхнеуровневый разбор

Будущая опора для задачи P13-T1 (Jenkins в Docker + Jenkinsfile) — задача ещё не дана, снята с предынтервью-скоупа 2026-08-03. Файл написан как самостоятельный конспект под вопросы на интервью 2026-08-06.

> **Честная рамка.** В референсном `java-selenide-pp` **нет `Jenkinsfile`** — проверено поиском по всему репозиторию. CI там существует, но его конфигурация живёт вне репозитория (в самом Jenkins), поэтому пройтись по реальному файлу нельзя. Зато механизм **выбора скоупа тестов** в референсе настоящий и разобран ниже по фактическому коду (`${surefire.suiteXmlFile}` + 13 suite-файлов). Всё, что здесь про сам Jenkins — общая индустриальная практика, а не пересказ конкретного файла; на интервью так и стоит формулировать: «в проекте прогон запускался через Jenkins-джобу, конфигурация была на стороне CI-сервера».

---

## 1. Что такое CI и зачем он тестам

**Continuous Integration** — практика, при которой изменения кода **часто** (в идеале — на каждый push/merge request) вливаются в общую ветку, и на каждое такое вливание автоматически запускается проверка: сборка + тесты. Ключевое слово — **автоматически, без человека**.

Три вещи, которые CI даёт именно автотестам:

1. **Тесты запускаются регулярно и без участия инженера.** Не «когда я вспомнил прогнать», а на каждый мёрдж и/или по расписанию ночью.
2. **Единая среда прогона.** Тесты идут не «на машине Дениса, где случайно стоит нужная версия Chrome», а на сервере с фиксированным окружением. Классический эффект «у меня локально зелёное» перестаёт быть аргументом.
3. **Быстрая обратная связь о регрессе.** Сломали логин — знаем через 20 минут после мёрджа, а не за день до релиза.

**Цена отказа (для мотивировки на интервью).** Автотесты, которые может запустить только их автор со своей машины, — это не автоматизация, а личный инструмент одного человека. Ровно это было в нашем проекте на этапе P10-T2: сьют существовал, но зелёным был только при живом человеке, вручную закрывавшем рекламу — и именно поэтому стабилизация ([P10-T3](../curriculum/P10-T3-ui-stabilization.md)) была помечена как блокер для CI. Готовый пример на вопрос «а зачем вам вообще CI?».

**CI vs CD (чтобы не путать):** CI — интеграция и проверка (сборка + тесты). CD — Continuous Delivery/Deployment, автоматическая доставка проверенной сборки дальше (на стенд/в прод). Автотесты живут в CI-части и служат **воротами (quality gate)** для CD: не прошли тесты — дальше по конвейеру не поехало.

## 2. Jenkins: что это и из чего состоит

**Jenkins** — самостоятельный сервер автоматизации с открытым кодом. Его работа: по некоторому **триггеру** запустить некоторый **набор шагов** на некотором **исполнителе**, показать результат и сохранить артефакты.

Четыре понятия, которых достаточно для разговора:

| Термин | Что это |
|---|---|
| **Job / Project** | Настроенная единица работы. «Прогнать UI-регресс» — это job. |
| **Build / Run** | Один конкретный запуск job'ы (#41, #42...). У каждого свой лог, статус и артефакты. |
| **Controller (master)** | Сам сервер Jenkins: веб-интерфейс, конфигурация, планировщик. Тесты на нём напрямую гонять не принято. |
| **Agent (node / slave)** | Машина-исполнитель, на которой физически идёт прогон. Их может быть много и разных (Linux-агент, Windows-агент, агент с GUI/браузерами). |

**Executor** — слот параллельного выполнения на агенте. Если у агента 4 executor'а, он тянет 4 сборки одновременно; пятая ждёт в очереди. Это первый ответ на вопрос «а как у вас параллелятся прогоны на уровне CI».

**Плагины** — почти вся функциональность Jenkins расширяемая: Git, Maven, **Allure**, HTML Publisher, Slack-нотификации и т.д. Отчёт Allure в интерфейсе Jenkins появляется именно через плагин.

### Freestyle vs Pipeline

- **Freestyle job** — настраивается мышкой в веб-интерфейсе (галочки, поля). Просто, но конфигурация живёт только внутри Jenkins: не версионируется, не ревьюится, не переносится.
- **Pipeline job** — сценарий описан кодом в файле **`Jenkinsfile`**, который лежит **в самом репозитории с тестами**. Это подход «pipeline as code»: конфигурация проходит code review, историю видно в git, при откате кода откатывается и пайплайн.

Современный дефолт — Pipeline. Если спросят «почему Jenkinsfile, а не настройка в UI» — ответ ровно этот: версионируемость и ревьюируемость конфигурации.

## 3. Как тесты из фреймворка физически попадают в джобу

Полная цепочка, которую полезно уметь проговорить целиком:

```
git push (тесты в репозитории)
   ↓
Jenkins узнаёт об изменении (webhook / polling / расписание)
   ↓
Jenkins занимает executor на подходящем агенте
   ↓
Агент делает git clone/checkout нужной ветки
   ↓
Агент выполняет шаги сборки: mvn clean test -D<параметры>
   ↓  (Maven скачивает зависимости, компилирует, surefire запускает TestNG-сьют)
Тесты идут на агенте, пишут allure-results/, скриншоты, логи
   ↓
Post-шаги: сгенерировать и опубликовать Allure-отчёт, сохранить артефакты,
           выставить статус сборки, разослать уведомления
```

**Главное, что тут стоит понимать:** Jenkins не «знает» про твои тесты ничего особенного. Он просто машина, которая на чужом компьютере выполняет ту же самую команду `mvn clean test`, которую ты запускаешь локально. Вся «магия» — в том, *когда* он её запускает, *с какими параметрами*, и *что делает с результатом* после.

Отсюда прямое следствие, которое ценят на интервью: **если тест не проходит локально из чистого состояния — он не пройдёт и в CI.** Никакой Jenkins не чинит нестабильные тесты; он только делает их нестабильность видимой всей команде.

## 4. Что настраивает инженер (типовой Jenkinsfile по шагам)

Скелет декларативного пайплайна — важна структура, а не синтаксис наизусть:

```groovy
pipeline {
    agent { label 'ui-tests' }              // ГДЕ запускать: агент с такой меткой

    parameters {                            // ЧТО спросить у запускающего
        choice(name: 'SUITE', choices: ['smoke', 'regression'], description: 'Набор тестов')
        string(name: 'BROWSER', defaultValue: 'chrome')
        string(name: 'BASE_URL', defaultValue: 'https://automationexercise.com')
    }

    triggers {                              // КОГДА запускать само
        cron('H 2 * * *')                   // каждую ночь ~02:00
    }

    stages {
        stage('Checkout') { steps { checkout scm } }

        stage('Test') {
            steps {
                sh "mvn clean test -Dsurefire.suiteXmlFile=${params.SUITE}.xml -DBASE_URL=${params.BASE_URL}"
            }
        }
    }

    post {                                  // ЧТО делать с результатом
        always {
            allure results: [[path: 'target/allure-results']]   // отчёт (плагин Allure)
            archiveArtifacts artifacts: 'build/reports/**', allowEmptyArchive: true
        }
        failure {
            // уведомление в Slack/почту
        }
    }
}
```

Разбор по блокам — это и есть ответ на «какая конфигурация выполняется инженером»:

- **`agent`** — на какой машине выполнять. Метка (`label`) выбирает агента с нужным окружением: например, там установлен Chrome нужной версии. Бывает и `agent { docker { image '...' } }` — тогда шаги идут внутри контейнера, и окружение вообще описано кодом.
- **`parameters`** — превращают job'у в **параметризованную**: при ручном запуске Jenkins показывает форму («Build with Parameters») с выпадающими списками и полями. Так один и тот же job гоняет и smoke, и regression, и разные окружения, и разные браузеры — без правки конфигурации.
- **`triggers`** — расписание и автозапуски (см. раздел 6).
- **`stages`** — сами шаги. Обычно: `Checkout` → `Build/Test` → (опц.) `Report`. Именно в `Test` живёт та самая команда `mvn`.
- **`post`** — что делать после, независимо от исхода: опубликовать Allure, сохранить скриншоты/логи как артефакты, уведомить команду. `always` критичен: отчёт нужен как раз тогда, когда тесты **упали**, а значит он не может стоять в ветке «только при успехе».
- **Credentials** — логины/токены/пароли никогда не пишутся в `Jenkinsfile`. Они хранятся в Jenkins Credentials Store и подставляются в переменные окружения (`withCredentials`/`environment`) в момент прогона. Это прямая параллель с нашим [`FrameworkConfig`](../curriculum/P1-T1-config-facade.md): env var стоит **первым** в порядке разрешения именно затем, чтобы CI мог подставить секрет, не трогая ни код, ни закоммиченный properties-файл.

## 5. Как формируется скоуп запускаемых тестов

Три уровня, от грубого к точному. **Первый — реальный механизм из `java-selenide-pp`**, остальные два — общая практика.

### Уровень 1 — TestNG suite-файл (так сделано в референсе)

В `clincard-ui-test-automation/pom.xml:85-87` surefire получает имя suite-файла не константой, а **свойством**:

```xml
<suiteXmlFiles>
    <suiteXmlFile>${surefire.suiteXmlFile}</suiteXmlFile>
</suiteXmlFiles>
```

Само значение передаётся снаружи при запуске: `mvn test -Dsurefire.suiteXmlFile=vendors.xml`. А в `clincard-ui-test-automation/src/test/resources/testsuites/` лежат **13 готовых suite-файлов** — по одному на функциональную область. Реальный пример (`vendors.xml`), сокращённо:

```xml
<suite name="AUTO_REGRESSION -> G9: Vendor Files">
    <test name="Vendor Files tests">
        <classes>
            <class name="com.suvoda.automation.vendorfiles.ConsumeAndProcessWFFileTest"/>
            <class name="com.suvoda.automation.vendorfiles.CreatingAndReplacingCardsI2CViaFileTest"/>
            ...
        </classes>
    </test>
</suite>
```

Итого схема: **один Jenkins-параметр `SUITE` → одно значение `-Dsurefire.suiteXmlFile` → один XML → фиксированный список классов.** Одна джоба обслуживает 13 разных наборов, ничего не пересобирая. Это самый конкретный, «из проекта» ответ на вопрос про скоуп — его и стоит рассказывать.

### Уровень 2 — TestNG groups

Тесты помечаются аннотацией: `@Test(groups = {"smoke"})`. Дальше либо в suite-файле `<groups><run><include name="smoke"/></run></groups>`, либо флагом `mvn test -Dgroups=smoke`. Удобно, когда «smoke» — это срез **поперёк** функциональных областей (по 2-3 самых важных теста из каждой), а не отдельная папка.

### Уровень 3 — точечный отбор через Maven

`mvn test -Dtest=LoginTest` или `-Dtest=LoginTest#incorrectEmailLoginTest`. В основном для локальной отладки и для перезапуска одного упавшего теста, а не как штатный режим CI.

**Типовой набор джоб в реальном проекте:**

| Джоба | Скоуп | Когда идёт |
|---|---|---|
| Smoke | 10-20 критичных тестов, минуты | на каждый MR/мёрдж |
| Regression | весь сьют, часы | ночью по расписанию |
| Ручной запуск | параметризованный, любой suite | по требованию (проверить фикс/стенд) |

Логика деления простая и её стоит уметь обосновать: **на каждый мёрдж гоняется то, что успевает дать ответ за приемлемое время**, всё остальное — ночью, когда длительность не мешает работе.

## 6. Когда джоба запускается (триггеры и расписание)

Четыре способа, они комбинируются:

1. **По событию в git — webhook.** GitHub/GitLab при push/MR сам дёргает Jenkins. Мгновенно, без лишней нагрузки — предпочтительный вариант.
2. **Polling SCM** (`pollSCM('H/5 * * * *')`) — Jenkins сам раз в N минут спрашивает репозиторий «есть новое?». Запасной вариант, когда webhook не настроить (нет доступа наружу).
3. **По расписанию** (`cron`) — запуск в заданное время независимо от изменений. Основной режим для ночного регресса.
4. **Вручную / по цепочке** — кнопка «Build with Parameters» в UI, или запуск из другой джобы (собрали приложение → дёрнули тесты).

**Синтаксис cron** — 5 полей: `минута час день_месяца месяц день_недели`.

```
H 2 * * *       # каждый день, ~02:00
H 3 * * 1-5     # будни, ~03:00
H/15 * * * *    # каждые 15 минут
```

**Что такое `H`** — это специфика именно Jenkins, и это хороший «мелкий, но показывающий опытность» факт для интервью. `H` = *hash*: Jenkins сам выбирает конкретную минуту внутри интервала, но **стабильно** для этой джобы (вычисляет по её имени). Смысл: если 50 джоб написать как `0 2 * * *`, все 50 стартанут ровно в 02:00 и положат сервер пиковой нагрузкой. С `H 2 * * *` они равномерно размажутся по часу, и каждая при этом будет запускаться каждый день в одну и ту же свою минуту.

## 7. Что делать с результатом

- **Статус сборки.** Упал хоть один тест — сборка красная. Отсюда важность честности сьюта: безусловный retry на всё подряд ([разбор в P10-T3](../curriculum/P10-T3-ui-stabilization.md)) делает билд зелёным ценой пропущенных дефектов.
- **Allure-отчёт** публикуется плагином и доступен по ссылке из сборки — с шагами, скриншотами и историей падений по прогонам.
- **Артефакты** (скриншоты, логи, дампы) — сохраняются через `archiveArtifacts`, чтобы разбирать падение уже после того, как агент освободился и рабочая директория затёрлась.
- **Уведомления** — Slack/почта, обычно только на падение или на смену статуса (зелёный→красный), чтобы не приучать команду игнорировать поток сообщений.
- **Flaky-тесты.** Главная организационная боль CI: тест, падающий через раз, обесценивает весь сьют — люди начинают перезапускать не глядя. Отсюда правило: **нестабильный тест либо чинится, либо помечается и выносится из блокирующей джобы**, но не остаётся молча мигать. У нас в проекте это уже отработано на реальном примере — фильтрация retry строго по транзиентным типам исключений (`TimeoutException`, `StaleElementReferenceException`), а не «перезапускать всё».

## 8. Что стоит сказать на интервью (короткая версия)

> «CI — это автоматический прогон сборки и тестов на каждое изменение и по расписанию, на выделенном сервере, а не на машине инженера. У нас прогон шёл через Jenkins: параметризованная джоба, где параметром выбирается набор тестов — в проекте это TestNG suite-файлы, их около полутора десятков по функциональным областям, и surefire получает нужный через свойство `-Dsurefire.suiteXmlFile`. Smoke гонялся на мёрдж, полный регресс — ночью по cron. Результат — статус сборки плюс опубликованный Allure-отчёт со скриншотами упавших тестов. Секреты и URL стенда приходят из CI через переменные окружения, поэтому в конфиге фреймворка env var стоит первой в порядке разрешения — код и properties-файл ради этого трогать не нужно.»

Если копнут глубже, готовые ветки для развития ответа: `H` в cron и зачем он; почему Jenkinsfile лучше настройки мышкой; чем controller отличается от агента и что такое executor; когда retry допустим, а когда он маскирует дефекты.
