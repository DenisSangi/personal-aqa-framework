# java.util.Random vs ThreadLocalRandom + генерация случайных строк

Нужны для Задачи [P2-T1](../curriculum/P2-T1-random-generators.md).

## Как устроен `java.util.Random`

`new Random()` создаёт объект с внутренним состоянием (seed) — числом, из которого детерминированно вычисляется следующее "случайное" число при каждом вызове. Без явного seed конструктор берёт его из системных источников (время + счётчик), поэтому на практике последовательность выглядит непредсказуемой.

```java
Random random = new Random();
int digit = random.nextInt(10); // число от 0 (включительно) до 10 (не включая) — т.е. 0..9
```

Важное свойство: каждый вызов `nextInt(...)` **меняет** внутреннее состояние объекта. Это значит, что `Random` — не бесплатный статический метод, а объект с изменяемым состоянием, к которому нужно обращаться безопасно из нескольких потоков.

## Проблема параллельного доступа к одному `Random`

Методы `Random` потокобезопасны (можно вызывать из разных потоков без падений), но за счёт внутренней синхронизации — несколько потоков, дёргающих один и тот же объект `Random` одновременно, конкурируют за доступ к его состоянию. При параллельном прогоне тестов (Фаза 12 плана — параллелизация, см. [16-threadlocal-driver-and-testng-parallel.md](16-threadlocal-driver-and-testng-parallel.md)) это превращается в узкое место: потоки простаивают в очереди за одним общим объектом вместо того, чтобы работать независимо.

## `ThreadLocalRandom.current()`

`ThreadLocalRandom` — генератор, у которого **каждый поток получает свой собственный экземпляр** состояния, без разделения с другими потоками:

```java
int digit = ThreadLocalRandom.current().nextInt(10);
```

Не нужно (и не следует) сохранять результат `ThreadLocalRandom.current()` в поле/переменную для переиспользования между вызовами из разных потоков — он привязан к текущему потоку в момент вызова. Правильный паттерн — вызывать `ThreadLocalRandom.current()` заново там, где он нужен.

Компромисс: `ThreadLocalRandom` не подходит, если нужен воспроизводимый (seeded) прогон — у него нет публичного конструктора с фиксированным seed, специально чтобы предотвратить его случайное использование как обычного `Random` в неподходящем месте.

## Диапазоны символов без библиотеки

Чтобы получить случайную букву, не выписывая алфавит строкой, используется арифметика над числовым кодом символа:

```java
char letter = (char) ('a' + random.nextInt(26)); // случайная буква 'a'..'z'
```

`'a' + N` — это `int` (Java продвигает `char` до `int` при сложении), поэтому явное приведение `(char)` обязательно на выходе. Тот же приём для цифр: `(char) ('0' + random.nextInt(10))`.

Для строки заданной длины — `StringBuilder` в цикле (или `IntStream`/`Stream`, если ближе), а не конкатенация `String` в цикле (каждая конкатенация `String + String` в Java создаёт новый объект — линейная память на копирование при каждой итерации).

## Почему это важно именно для тестовых данных

Статическое значение (захардкоженный email/имя) — не проблема само по себе один раз. Проблема — что оно ломается ровно тогда, когда прогон повторяется: второй прогон видит "уже существующий" email, параллельный прогон видит гонку за один и тот же email между потоками. Случайная генерация с диапазоном, достаточным для практической уникальности (например, 10 alphanumeric-символов — космически малый шанс коллизии), убирает саму категорию таких ложных падений.

## Та же идея с другой стороны — `DateTimeFormatter` vs `SimpleDateFormat` (задача P2-T2)

Разница `Random` vs `ThreadLocalRandom` выше — частный случай общего правила: **mutable объект с общим состоянием, используемый из нескольких потоков одновременно, — источник проблем; immutable — нет**.

То же самое правило (только уже не "конкуренция за состояние", а "порча состояния") справедливо для форматирования дат: старый `java.text.SimpleDateFormat` — mutable и не потокобезопасен, а его "потомок" `DateTimeFormatter` из `java.time` — immutable и потокобезопасен по конструкции, поэтому его можно смело держать как переиспользуемый `static final`. В отличие от `Random`/`ThreadLocalRandom`, где решение — "не делить общий объект между потоками", здесь решение другое — "взять immutable инструмент, которым можно безопасно делиться". Два разных способа получить один и тот же результат: код, который не падает и не портит данные при параллельном прогоне тестов (Фаза 12 плана).

Подробный разбор `DateTimeFormatter`/`LocalDateTime` и паттернов форматирования — в [theory/04-datetime-formatting.md](04-datetime-formatting.md), задача — [P2-T2](../curriculum/P2-T2-datetime-util.md).
