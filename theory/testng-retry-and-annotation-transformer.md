# TestNG: IRetryAnalyzer, IAnnotationTransformer и регистрация через ServiceLoader

Опора для [P10-T3](../curriculum/P10-T3-ui-stabilization.md). Написано по итогам живой сборки 2026-08-04.

## 1. Зачем вообще перезапускать упавший тест

Есть два принципиально разных повода для красного теста:

- **Дефект** — приложение реально сломано. Перезапуск здесь вреден: он прячет баг, который надо чинить.
- **Транзиентный сбой** — сеть моргнула, внешний сервис не ответил, рендерер браузера подвис. Приложение исправно, красный цвет — ложь.

Перезапуск (retry) лечит только второе. Отсюда правило, которое стоит уметь сформулировать на интервью: **слепой retry на все падения — плохая практика**, он превращает сьют в генератор случайных зелёных прогонов и убивает доверие к нему. Retry допустим, когда причина нестабильности **диагностирована и задокументирована**, а перезапуск ограничен конкретными типами отказа.

В этом проекте задокументированные транзиентные падения — единичные CDP-таймауты рендерера и сетевые сбои живого `automationexercise.com` (см. записи по P3-T2, P7-T2, P10-T1: «не воспроизвелось повторно»).

## 2. `IRetryAnalyzer` — сам механизм перезапуска

Интерфейс с единственным методом:

```java
public interface IRetryAnalyzer {
    boolean retry(ITestResult result);   // true → TestNG запустит метод ещё раз
}
```

TestNG зовёт его **после каждого падения**. Вернул `true` — тест выполняется заново; вернул `false` — падение фиксируется окончательно.

Два обязательных момента:

**Счётчик и лимит.** Без ограничения `retry()` вернёт `true` бесконечно, и реально сломанный тест зациклит прогон навсегда. Счётчик — обычное поле объекта; оно переживает вызовы, потому что TestNG держит экземпляр анализатора между попытками.

```java
private int count = 0;
private static final int MAX = 3;
```

Почему `count` **не** `static`: TestNG создаёт свой экземпляр анализатора на каждый тестовый метод, поэтому нестатическое поле даёт каждому тесту персональный счётчик. Сделай его `static` — счётчик станет общим на весь сьют, и после трёх перезапусков (пусть даже все три съел один тест) ни один другой тест retry уже не получит.

Почему `MAX` — `static final`: значение одинаково для всех экземпляров (`static`) и не меняется (`final`, проверяется компилятором).

**Фильтрация по типу отказа.** Параметр `result` нужен именно для этого — `result.getThrowable()` даёт исключение, по которому можно решить, транзиентный это сбой или дефект.

Подвох: **Selenide оборачивает исключения драйвера**. В `getThrowable()` лежит `ElementNotFound` (наследник `UIAssertionError`), а исходный `NoSuchElementException` спрятан в `getCause()` — это видно в выводе теста:

```
Element not found {input[id='search_product']}     ← верхнее исключение (Selenide)
Expected: exist
...
Caused by: NoSuchElementException: no such element  ← исходное (Selenium)
```

Прямой `instanceof` по верхнему исключению не сработает. Нужен обход цепочки причин — **и порядок внутри цикла имеет значение**: проверять надо ДО перехода к причине, иначе само переданное исключение никогда не будет проверено (транзиентное исключение без обёртки окажется пропущено):

```java
Throwable t = someException;
while (t != null) {
    if (t instanceof IOException) { /* нашли нужный тип где-то в цепочке */ }
    t = t.getCause();   // null, когда причин больше нет
}
```

## 3. `IAnnotationTransformer` — как применить анализатор ко всем тестам сразу

Штатный способ подключить анализатор — атрибут аннотации:

```java
@Test(retryAnalyzer = MyRetryAnalyzer.class)
```

Но это требует правки **каждого** тестового метода — дублирование ровно того же сорта, от которого избавлялись в Фазе 6 (общий `@AfterMethod` вынесли в `BaseTest`).

`IAnnotationTransformer` решает это централизованно. TestNG вызывает его **до старта сьюта**, по разу на каждую найденную аннотацию, и позволяет изменить её программно — как будто атрибут дописан руками:

```java
void transform(ITestAnnotation annotation, Class<?> testClass,
               Constructor<?> testConstructor, Method testMethod);
```

- `annotation` — сама `@Test` в виде объекта, с сеттерами на все атрибуты (`setRetryAnalyzer`, `setEnabled`, `setDescription`, …).
- Три остальных параметра говорят, **на чём** висит аннотация — ровно один из них не `null`. Для глобального применения не нужны.

`setRetryAnalyzer(...)` принимает `Class<?>`, а не готовый объект: экземпляр создаёт сам TestNG, отдельно под каждый тестовый метод. Именно поэтому счётчик из раздела 2 получается персональным.

## 4. Регистрация — где ловушка

`@Listeners(MyTransformer.class)` на `BaseTest` **не работает** для `IAnnotationTransformer`. Причина в порядке lifecycle: `@Listeners` обрабатывается уже после того, как TestNG прочитал аннотации тестовых методов — трансформировать нечего, поезд ушёл. С `ITestListener` (как наш `ScreenshotOnFailureListener`) такой проблемы нет, он подключается штатно.

Рабочие способы — два:

1. **`testng.xml`** с блоком `<listeners>` + настройка surefire на этот файл (`<suiteXmlFiles>` в `pom.xml`).
2. **ServiceLoader** — файл на classpath:

```
src/test/resources/META-INF/services/org.testng.ITestNGListener
```

Внутри — одна строка с полным именем класса (пакет + имя). TestNG при старте сканирует classpath на такие файлы (стандартный механизм `java.util.ServiceLoader`) и регистрирует перечисленные классы как листенеры — **до** чтения аннотаций. Ни `testng.xml`, ни правок `pom.xml` не требуется.

Две частые опечатки, обе дают **тихий отказ** (всё компилируется и прогоняется, retry просто не работает):

- `META_INF` через подчёркивание вместо `META-INF` через дефис;
- класс не реализует интерфейс (`implements` забыт) — сигнатура метода совпадает случайно, TestNG о классе ничего не знает. Лечится привычкой ставить `@Override`: компилятор тогда сам проверит соответствие.

## 5. Как убедиться, что механизм реально включился

Не на глаз, а по выводу прогона:

```
Total tests run: 4, Passes: 0, Failures: 1, Skips: 0, Retries: 3
```

Показатели рабочего retry: ненулевое `Retries`, строки `Test ignored` на промежуточных попытках (перезапущенные попытки не считаются падениями), и `org.testng.internal.invokers.TestInvoker.retryFailed` в стек-трейсе.

Отдельно обрати внимание на арифметику: `Total tests run: 4` при одном тестовом методе — это 1 исходный запуск + 3 перезапуска. Метод в отчёте один, `Failures: 1`.

**Обратная проверка — что retry НЕ сработал вхолостую.** Если число прогнанных тестов совпадает с ожидаемым (количество методов `@Test` плюс строки `@DataProvider`), значит перезапусков не было ни одного и сьют зелёный сам по себе. Это важно проверять после включения retry: иначе зелёный цвет может означать «дожали ретраями», а не «всё работает». В `personal-aqa-framework` ожидаемое число — 29 (26 методов, один из которых параметризован).
