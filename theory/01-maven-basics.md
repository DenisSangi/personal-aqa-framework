# Maven — базовые понятия

Нужны для Задачи [P0-T1](../curriculum/P0-T1-repo-maven-skeleton.md).

## Что такое Maven

Инструмент сборки для Java: описываешь **что** нужно проекту (зависимости, версия Java, плагины) в одном XML-файле — `pom.xml` («Project Object Model») — а Maven сам скачивает зависимости, компилирует, гоняет тесты, собирает jar, в правильном порядке.

Без Maven (или аналога) пришлось бы вручную скачивать `.jar`-файлы каждой библиотеки, вручную собирать classpath для `javac`/`java`, вручную следить за версиями и их совместимостью — то, что `java-selenide-pp` делает автоматически при `mvn compile`.

## GAV-координаты — как Maven идентифицирует библиотеку

Любая библиотека в Maven-мире (своя или чужая) однозначно определяется тройкой:

```
groupId    — кто издал (обычно домен наоборот: com.codeborne, org.testng)
artifactId — имя самой библиотеки (selenide, testng)
version    — версия (7.5.1, 7.9.0...)
```

Пример — как объявляется зависимость в `pom.xml`:

```xml
<dependency>
    <groupId>com.codeborne</groupId>
    <artifactId>selenide</artifactId>
    <version>7.5.1</version>
</dependency>
```

Это ровно то же самое, что твой собственный проект тоже описывает о себе в самом верху `pom.xml` (свои groupId/artifactId/version — то, как ДРУГИЕ проекты подключали бы твой, если бы он был библиотекой).

Искать актуальные координаты и версии — на [mvnrepository.com](https://mvnrepository.com) или search.maven.org.

## Dependency vs Plugin

- **Dependency** — код, который твой проект ИСПОЛЬЗУЕТ во время компиляции/выполнения (Selenide, TestNG, Allure-адаптер).
- **Plugin** — код, который РАСШИРЯЕТ поведение самого Maven на определённой фазе сборки (например, `maven-surefire-plugin` — как именно запускать тесты; `allure-maven` — как собрать HTML-отчёт из результатов). Плагин не попадает в твой скомпилированный код — он работает во время сборки.

## Scope зависимости

`<scope>` в `<dependency>` определяет, где именно доступна библиотека:

- `compile` (по умолчанию, можно не писать) — доступна везде, попадает в финальный артефакт.
- `test` — доступна только в `src/test/java`, не попадает в `package`. TestNG и Selenide в тестовом фреймворке обычно именно `test` (даже если Selenide формально используется в `src/main` вспомогательных классах — тогда `compile`; в конкретно этом проекте, где всё — тестовый код, чаще всего `test`).

## Build lifecycle — фазы

Maven выполняет команду не как одно действие, а как **последовательность фаз** — каждая следующая тянет за собой предыдущие:

```
validate → compile → test → package → verify → install → deploy
```

Например, `mvn test` реально прогоняет `validate → compile → test` — то есть сначала скомпилирует код, потом тесты, и только потом запустит их. `mvn package` дополнительно соберёт `.jar`.

Самые ходовые команды на практике:
- `mvn clean` — удалить `target/` (результаты предыдущей сборки).
- `mvn test` — скомпилировать + прогнать тесты.
- `mvn clean test` — то же самое, но сначала гарантированно с чистого листа.

## `src/main` vs `src/test`

Maven ожидает жёстко заданную структуру папок (convention over configuration — не нужно её объявлять явно):

```
src/
├── main/java/...   ← "боевой" код фреймворка (POM-классы, утилиты, конфиг)
└── test/java/...   ← сами тестовые классы (@Test методы)
```

В `java-selenide-pp` это видно один в один: `pages/`, `core/utils/`, `api/` — всё в `src/main/java`; сами `@Test`-классы — в `src/test/java`.

## Версия Java в `pom.xml`

Maven по умолчанию может компилировать под старую версию байткода, если явно не указать нужную. Указывается через `<properties>`:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

(Более старый вариант — отдельно `maven.compiler.source` и `maven.compiler.target` — тоже встречается, но `release` — один параметр вместо двух и строже проверяет совместимость API.)

## Структура pom.xml — блок за блоком

Как все концепции выше физически собираются в один файл, сверху вниз внутри корневого `<project>`:

1. **XML-заголовок + `<project>`** — корневой тег, внутри которого живёт весь файл. Обязательные атрибуты `xmlns`/`xsi:schemaLocation` — «паспорт» версии XML-схемы, одинаковый в любом Maven-проекте на планете, копируется как есть.
2. **`<modelVersion>`** — первый ребёнок `<project>`, единственное возможное значение — `4.0.0`. Версия формата самого файла pom.xml, не твоего проекта.
3. **Координаты проекта — `<groupId>` / `<artifactId>` / `<version>`** — сразу после `modelVersion`, на одном уровне вложенности. Твоя собственная GAV-тройка (см. выше) — как если бы фреймворк сам был библиотекой, которую кто-то мог бы подключить. Рядом опциональный сосед — `<packaging>` (по умолчанию `jar`, можно не писать).
4. **`<properties>`** — отдельный блок-контейнер, обычно сразу после координат. Место для именованных значений, на которые потом ссылаешься через `${имя}` в других частях файла: версия Java (`maven.compiler.release`), кодировка исходников, часто — версии зависимостей вынесены сюда одной переменной, чтобы не дублировать число в нескольких `<dependency>`.
5. **`<dependencies>`** — контейнер, внутри — несколько блоков `<dependency>` (по одному на библиотеку — см. GAV выше), каждый со своей GAV-тройкой и опциональным `<scope>` (см. выше). Порядок внутри Maven не важен, но принято группировать логически.
6. **`<build>` → `<plugins>`** — необязателен на старте. Здесь конфигурируются не зависимости, а ПЛАГИНЫ (см. «Dependency vs Plugin» выше) — поведение самой сборки, например как surefire ищет и запускает тесты. Пока можно не трогать — TestNG обычно подхватывается автоматически. Пригодится в Фазе 10 под Allure-плагин для сборки отчёта.

Порядок 2→6 не требование схемы (кроме `modelVersion` — та всегда первая), но устоявшаяся идиома — тот же порядок увидишь в `pom.xml` `java-selenide-pp`.

Форма файла без значений (сама «форма», а не готовый файл — координаты, версии и набор зависимостей свои):

```xml
<project xmlns="..." xmlns:xsi="..." xsi:schemaLocation="...">
    <modelVersion>4.0.0</modelVersion>

    <groupId>...</groupId>
    <artifactId>...</artifactId>
    <version>...</version>

    <properties>
        <!-- версия Java, кодировка, версии зависимостей -->
    </properties>

    <dependencies>
        <dependency>
            <!-- одна библиотека: groupId + artifactId + version (+scope) -->
        </dependency>
        <!-- ещё зависимости... -->
    </dependencies>

    <!-- <build><plugins>...</plugins></build> — пригодится позже, не сейчас -->
</project>
```
