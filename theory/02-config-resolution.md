# Разрешение конфигурации: env var → system property → properties-файл

Нужны для Задачи [P1-T1](../curriculum/P1-T1-config-facade.md).

## `System.getenv()` vs `System.getProperty()`

Это два РАЗНЫХ источника значений, легко перепутать по одинаково звучащим названиям:

- **`System.getenv(String name)`** — читает **переменные окружения ОС** (то, что видно в шелле через `echo $VAR`, что задаётся в `Dockerfile` через `ENV`, что Jenkins прокидывает в job как build-параметр). Общие для всех процессов, запущенных из этого окружения. Изнутри самой JVM их поменять нельзя — это то, что процесс получил при старте.
- **`System.getProperty(String key)`** — читает **системные свойства JVM**. Задаются флагом при запуске (`java -Dkey=value ...` / `mvn test -Dkey=value`), либо программно через `System.setProperty(...)` прямо в коде. Живут только внутри одного процесса JVM.

Изолированный пример (форма вызова, не готовое решение):

```java
String fromEnv  = System.getenv("MY_VAR");      // переменная окружения ОС
String fromProp = System.getProperty("my.var"); // JVM-флаг -Dmy.var=...
```

## Почему порядок именно такой: env var → system property → properties-файл

Три источника — это фактически цепочка фолбэков: если самого приоритетного источника нет, идём к следующему. Порядок не случаен:

1. **env var — наивысший приоритет.** Это то, что впрыскивает CI/CD (Jenkins) и Docker при разворачивании — конфигурация окружения, а не конкретного локального запуска. Она должна побеждать всегда, иначе поведение в CI станет непредсказуемым (например, если где-то в коде/скрипте случайно остался старый `-D`-флаг).
2. **system property — средний приоритет.** Удобный способ разработчику переопределить значение для ОДНОГО локального запуска, не трогая переменные окружения ОС и не редактируя файлы.
3. **properties-файл — низший приоритет, дефолт.** Значение, закоммиченное в репозиторий — то, что работает «из коробки», если никто ничего не переопределил.

## Properties + classpath

`.properties`-файл, положенный в `src/main/resources/`, автоматически попадает в classpath при сборке (Maven копирует `src/main/resources/**` → `target/classes/`). Загружается через `Properties` + поток:

```java
Properties properties = new Properties();
try (InputStream in = MyClass.class.getResourceAsStream("/my-file.properties")) {
    properties.load(in);
}
String value = properties.getProperty("key"); // null, если ключа нет
```

Важная деталь: `getResourceAsStream("/имя.properties")` с ведущим `/` ищет от КОРНЯ classpath, а не от пакета вызывающего класса.

## Параллель с уже знакомым тебе Optional

Цепочка «нет в источнике A → пробуем B → нет в B → пробуем C → нет нигде → падаем» — та же форма, что `Optional.orElse(...)`/`orElseGet(...)`, которую ты уже проходил. Реализовывать через `Optional` не обязательно (обычный `if`-каскад тоже нормален и читаем для трёх шагов), но если тянет — это ровно тот случай, где `Optional`-цепочка естественна.

## Facade — как это выглядит СНАРУЖИ

Сам механизм разрешения (`getValue(key)` с цепочкой из трёх источников) — деталь реализации. Наружу вызывающий код (POM, API-сервисы) не должен вызывать `getValue("BASE_URL")` россыпью по всей кодовой базе — вместо этого один раз, в конфиг-классе, объявляется простая константа (`BASE_URL`), которая уже прошла через `getValue(...)` внутри статического блока инициализации класса. Это и есть Facade — концепция уже разобрана в `design-patterns.md` (`java-selenide-pp/Framework explanation/design-patterns.md`, раздел #6): простой интерфейс наружу поверх более сложной логики внутри.
