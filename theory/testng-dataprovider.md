# TestNG @DataProvider

Опора для [P8-T1](../curriculum/P8-T1-dataprovider.md).

## 1. Механика на изолированном примере

Два метода в одном классе — поставщик данных и потребитель:

```java
@DataProvider(name = "additionData")
public Object[][] additionData() {
    return new Object[][] {
        {2, 3, 5},      // строка 1: a=2, b=3, ожидаемая сумма 5
        {0, 0, 0},      // строка 2
        {-1, 1, 0}      // строка 3
    };
}

@Test(dataProvider = "additionData")
public void additionTest(int a, int b, int expectedSum) {
    Assert.assertEquals(a + b, expectedSum);
}
```

Что делает TestNG: находит провайдер по имени `"additionData"`, получает массив из 3 строк и запускает `additionTest` **три раза** — по разу на строку. Каждая строка распаковывается в параметры метода по позициям: `{2, 3, 5}` → `a=2, b=3, expectedSum=5`.

Ключевое следствие для отчётов: это не "один тест с циклом внутри", а **три отдельных запуска** — в выводе TestNG/Allure каждый виден отдельной строкой со своими параметрами. Упала только `{-1, 1, 0}` — остальные две зелёные, и сразу видно, какие именно данные сломались.

## 2. Связка держится на рефлексии — компилятор её не видит

`Object[][]` — массив массивов `Object`, типы элементов стёрты. Если провайдер отдаёт `{2, 3, "пять"}`, а метод ждёт `(int, int, int)` — **компиляция пройдёт**. Ошибка вылезет только в рантайме, при попытке TestNG подставить `"пять"` в `int`-параметр.

То же с именем: `dataProvider = "aditionData"` (опечатка) — компилятор молчит, в рантайме TestNG не найдёт провайдер и тест упадёт с ошибкой конфигурации. Связка `@DataProvider` ↔ `@Test` существует только в рантайме, через рефлексию — компилятор не проверяет ни имя, ни соответствие типов, ни количество параметров. Поэтому дисциплина "количество и порядок элементов строки = сигнатура метода" — целиком на тебе.

## 3. Данные ≠ логика проверки

Провайдер отвечает на вопрос "с какими данными гонять сценарий". Он НЕ отвечает на вопрос "что проверять". Если два теста различаются ожидаемым ИСХОДОМ (один ждёт `false`, другой — исключение), это разные сценарии — их не стоит склеивать в один параметризованный метод с ветвлением `if (expectException) ... else ...` внутри: тело теста превращается в мини-интерпретатор, читаемость падает, отчёт врёт (один метод "про всё сразу"). Правило: **один `@Test`-метод = один класс исхода**, провайдер варьирует только входы.

## 4. Отличие от JUnit 5 @ParameterizedTest (коротко, для интервью)

| | TestNG `@DataProvider` | JUnit 5 `@ParameterizedTest` |
|---|---|---|
| Источник данных | Метод, возвращающий `Object[][]` | Набор аннотаций: `@ValueSource`, `@CsvSource`, `@MethodSource` |
| Связка | По имени строки (`dataProvider = "..."`) | Аннотацией над тем же методом |
| Простые случаи | Всегда полная форма `Object[][]` | `@ValueSource(ints = {1,2,3})` — короче |

Идея одна и та же: отделить данные от сценария и получить по запуску на набор. Различие — в оформлении.
