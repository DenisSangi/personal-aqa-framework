# JDBC — основы

Опора для [P9-T2](../curriculum/P9-T2-database-connection-util.md).

## 1. Что такое JDBC и зачем драйвер

**JDBC** (Java Database Connectivity) — стандартный набор интерфейсов в самой Java (`java.sql.*`) для работы с любой реляционной БД: `Connection`, `Statement`, `ResultSet`. Это только **интерфейсы** — самой реализации в JDK нет.

Реализацию даёт **драйвер** — библиотека конкретной базы (`org.postgresql:postgresql` для Postgres, свой для MySQL, свой для Oracle). Драйвер знает сетевой протокол своей БД и реализует интерфейсы JDBC поверх него.

Ровно та же идея, что и в твоём `RestClient`: код работает с общим интерфейсом, а под ним меняется конкретная реализация. Поэтому смена БД (Postgres → MySQL) для кода означает смену драйвера и URL, а не переписывание всех запросов.

Драйвер подключается как обычная зависимость в `pom.xml` — и всё, `DriverManager` находит его сам.

## 2. Строка подключения (JDBC URL)

```
jdbc:postgresql://localhost:5434/aqa_db
└┬─┘ └────┬────┘  └───┬───┘ └┬─┘ └─┬──┘
 │        │           │      │     └── имя базы
 │        │           │      └──────── порт (ХОСТА — тот, что слева в "5434:5432")
 │        │           └─────────────── хост
 │        └─────────────────────────── подпротокол = какой драйвер использовать
 └──────────────────────────────────── всегда jdbc
```

Java-код живёт снаружи контейнера, поэтому стучится на хост-порт — то, что мы разбирали при пробросе портов.

```java
Connection conn = DriverManager.getConnection(url, user, password);
```

Есть и вариант с `Properties` (как в референсе) — та же вещь, просто параметры пачкой.

## 3. `Statement` vs `PreparedStatement` — и SQL-инъекции

**`Statement`** — запрос как готовая строка:

```java
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery("SELECT * FROM users");
```

Годится, когда запрос фиксированный и в нём нет внешних данных.

**`PreparedStatement`** — запрос с «дырками» `?`, значения подставляются отдельно:

```java
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE email = ?");
ps.setString(1, someEmail);      // нумерация с 1, не с 0!
ResultSet rs = ps.executeQuery();
```

Почему это важно — классика собеседований. Сравни с конкатенацией:

```java
String sql = "SELECT * FROM users WHERE email = '" + input + "'";
```

Если `input` = `x' OR '1'='1`, то в базу уйдёт:

```sql
SELECT * FROM users WHERE email = 'x' OR '1'='1'
```

Условие истинно всегда → вернутся **все** пользователи. Это **SQL-инъекция**: данные пролезли в текст запроса и изменили его смысл. С `PreparedStatement` такого не происходит: база сначала разбирает шаблон запроса, потом подставляет значение как **данные**, и оно уже не может стать частью SQL-синтаксиса — та же строка просто не найдёт совпадений.

Вторая польза — типы: `setString`/`setInt`/`setNull` кладут значение в правильном формате, не надо вручную возиться с кавычками и экранированием.

## 4. `ResultSet` — это курсор, а не список

`executeQuery` возвращает не готовую коллекцию, а **курсор**: указатель, который стоит ПЕРЕД первой строкой и умеет двигаться вперёд.

```java
while (rs.next()) {          // сдвинуть на строку вперёд; false = строк больше нет
    String email = rs.getString("email");
}
```

`rs.next()` делает две вещи сразу: двигает курсор и отвечает, получилось ли. Поэтому он и стоит условием `while` — цикл идёт, пока строки есть.

Читать значения можно по имени колонки (`rs.getString("email")`) или по номеру (`rs.getString(1)`). **Нумерация колонок в JDBC начинается с 1**, не с 0 — единственное место в Java, где так, ловушка на ровном месте.

Курсор живёт, пока открыто соединение. Поэтому вернуть `ResultSet` наружу из метода нельзя — соединение к тому моменту закроется. Отсюда и `List<Map<String, String>>` как возвращаемый тип: данные **вычитываются** в обычную структуру, которая переживёт закрытие соединения.

## 5. `ResultSetMetaData` — узнать колонки, не зная их заранее

Чтобы `executeQuery` работал с **любым** `SELECT`, метод не может знать имена колонок заранее. Их сообщает сам результат:

```java
ResultSetMetaData meta = rs.getMetaData();
int columnCount = meta.getColumnCount();       // сколько колонок вернул запрос
String name = meta.getColumnName(i);           // имя i-й колонки (i с 1!)
```

Отсюда рождается универсальная структура: внешний цикл `while (rs.next())` — по строкам, внутренний `for (i = 1; i <= columnCount; i++)` — по колонкам, каждая строка складывается в `Map<имя колонки, значение>`.

Почему значения всегда `String`: тесту обычно надо сравнить значение, а не считать по нему. Единый тип избавляет от `getInt`/`getDate`/`getBoolean` под каждый случай. Цена — приведение типов при необходимости на стороне теста.

## 6. `try-with-resources` для трёх ресурсов сразу

`Connection`, `Statement`, `ResultSet` — все реализуют `AutoCloseable`, и все три надо закрывать. В одном `try` можно объявить несколько через `;`:

```java
try (Connection conn = getConnection();
     Statement stmt = conn.createStatement();
     ResultSet rs = stmt.executeQuery(query)) {
    // работа с rs
}   // закроются автоматически, в ОБРАТНОМ порядке: rs → stmt → conn
```

Порядок закрытия обратный порядку объявления — и это правильно: сначала закрывается то, что зависит от других.

Незакрытое соединение — не мелочь: сервер БД держит ограниченное число одновременных соединений (по умолчанию у Postgres 100). Тест, который течёт соединениями, в CI исчерпает лимит и повалит весь прогон с `too many clients already` — причём падать начнут *другие* тесты, а не виновник.

## 7. `executeQuery` vs `executeUpdate`

| | Для чего | Возвращает |
|---|---|---|
| `executeQuery(...)` | `SELECT` | `ResultSet` — строки результата |
| `executeUpdate(...)` | `INSERT`, `UPDATE`, `DELETE` | `int` — сколько строк затронуто |

Возвращаемое число `executeUpdate` — само по себе полезная проверка: `UPDATE`, затронувший 0 строк, обычно означает, что условие `WHERE` не нашло цель.
