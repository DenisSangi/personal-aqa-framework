# Page Object + навигация через `return new NextPage()` + Lazy Initialization

Нужны для Задачи [P4-T1](../curriculum/P4-T1-home-login-page.md).

## Page Object — что это, минимальный пример

Идея: один класс = одна страница (или логически цельный кусок UI). Локаторы и действия над этой страницей живут ВНУТРИ класса, тест обращается только к методам, никогда к `$`/`$x` напрямую.

```java
public class HomePage {
    private final ButtonElement signupLoginLink = new ButtonElement($x("//a[@href='/login']"));

    public HomePage verifyPageIsOpen() {
        signupLoginLink.waitAndGetElement();
        return this;
    }

    public LoginPage clickSignupLoginLink() {
        signupLoginLink.click();
        return new LoginPage();
    }
}
```

Без паттерна: тот же локатор `//a[@href='/login']` пришлось бы копипастить в тело каждого теста, которому нужен переход на логин. Поменялся DOM (например, ссылка превратилась в кнопку с другим атрибутом) — правишь N мест вместо одного класса. Полный разбор — `design-patterns.md` #1 в `java-selenide-pp` (`Framework explanation/design-patterns.md`).

Локаторы — константой или инлайн? Не универсальное правило, а вопрос, окупается ли индирекция. Если локатор фиксирован (известен целиком уже сейчас, ничего не подставляется в рантайме) и используется в ровно одном месте — как в примере выше — константа над ним просто дублирует то, что уже сообщает имя поля (`signupLoginLink`), лишний уровень без пользы. Константа реально нужна, когда локатор **параметризован** (`%s`) и его значение собирается только в момент вызова метода — тогда его физически нельзя зашить в готовое `Element`-поле при конструировании объекта страницы. Пример из реального проекта: `px-ui-test-automation/src/main/java/pages/settings/AuditLogsPage.java` — `ROW_BY_TYPE_XPATH`, `INNER_NAME_XPATH` и другие содержат `%s` и собираются в разных комбинациях внутри `getRowsByParameters(AuditLogEntryModel model)` через `format(ROW_BY_TYPE_XPATH, model.type())` — значение `model.type()` известно только в момент вызова, поэтому единственный вариант — хранить сырую строку-константу, а не готовый элемент.

## Навигация — `return new NextPage()`

Метод, который вызывает реальный переход на сайте (клик по ссылке, сабмит формы), возвращает не `this`, а **новый экземпляр класса следующей страницы**:

```java
public LoginPage clickSignupLoginLink() {
    signupLoginLink.click();
    return new LoginPage();
}
```

Дальше в тесте это читается как последовательность шагов:

```java
new HomePage()
    .verifyPageIsOpen()
    .clickSignupLoginLink()   // вернул LoginPage
    .verifyPageIsOpen();      // теперь это уже метод LoginPage
```

Компилятор проверяет цепочку статически: если `clickSignupLoginLink()` — это переход, а не действие "остаться на месте", тип возврата — другой класс, и следующий вызов в цепочке обязан существовать именно у НЕГО. Ошибиться и вызвать метод не той страницы физически нельзя — код просто не скомпилируется.

## Почему `new LoginPage()` не падает, даже если страница ещё не открылась

Ключевой вопрос: `signupLoginLink.click()` вызывает реальный клик в браузере, но переход на новую страницу занимает какое-то (пусть маленькое) время. Как же `return new LoginPage()` не падает с ошибкой "элемент не найден", если конструктор `LoginPage` создаёт поля-локаторы для страницы, которая физически ещё может не успеть загрузиться?

Ответ — **Lazy Initialization**. Изолированный пример, без Selenide и без Page Object вообще:

```java
SelenideElement el = $x("//h1[@id='does-not-exist-yet']");
// Никакого исключения здесь нет! $x(...) не ищет элемент в DOM прямо сейчас —
// он просто создаёт "прокси"-объект с ЗАПОМНЕННЫМ локатором.

el.shouldBe(Condition.visible);
// А вот ТУТ Selenide реально идёт в DOM искать элемент — и если его пока нет,
// он не падает сразу, а ждёт (retry с таймаутом), пока элемент появится.
```

`$x(...)` (и `$(...)`) — это не "найди элемент сейчас", а "запомни, как его найти, когда понадобится". Поэтому конструктор `new LoginPage()` — это просто создание объекта с набором таких "запомненных" локаторов, он ничего не ищет в DOM и не может упасть из-за того, что страница ещё грузится. Реальный поиск (и ожидание) произойдёт только на первом `.shouldBe(...)`/`.click()`/`.setValue(...)` — то есть уже внутри `verifyPageIsOpen()` или любого другого метода, который дальше вызовет `waitAndGetElement()`.

Это та же идея, что уже встречалась в `BaseElement` (Фаза 3): ожидание — не «мгновенная проверка», а retry-цикл с таймаутом. Здесь она объясняет ещё один эффект: navigation-метод может безопасно вернуть `new NextPage()` сразу после клика, не дожидаясь явно загрузки страницы — реальное ожидание переносится на следующий шаг, который и обязан о ней позаботиться (`verifyPageIsOpen()`).

## Fluent Interface — уже знакомо

`verifyPageIsOpen()` возвращающий `this` — тот же приём, что `BaseElement`/`InputElement` в Фазе 3 (`return this` для методов, которые остаются на месте). Ничего нового не добавляется — конвенция просто переносится с уровня "элемент" на уровень "страница".
