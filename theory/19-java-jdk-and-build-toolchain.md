# 19 — Java, JDK, JRE: кто и где выбирает версию для сборки

Опора для [P12-T2](../curriculum/P12-T2-parallel-hardening.md), Вопрос 4. Написан 2026-08-11 по итогам живого разбора — все факты проверены на реальной машине, а не взяты из статей.

---

## 1. Три слова, которые путают

**Java** — язык и платформа. Фраза «версия Java» неоднозначна: она может означать версию языка, версию JDK, которой собирают, или версию рантайма, на котором запускают. Отсюда почти вся путаница в теме.

**JDK** (Java Development Kit) — комплект разработчика: компилятор `javac`, инструменты (`javap`, `jar`, `jshell`) и рантайм внутри. Им **собирают**.

**JRE** (Java Runtime Environment) — только запуск: `java` и стандартные библиотеки. Им **выполняют**. Начиная с Java 11 отдельно не поставляется — JDK включает всё необходимое.

## 2. На одной машине почти всегда несколько JDK

Реальная инвентаризация машины Дениса на 2026-08-11:

| Путь | Откуда взялась | Видна `java_home`? |
|---|---|---|
| `/Users/<user>/Library/Java/JavaVirtualMachines/openjdk-22.0.2` | скачана IntelliJ IDEA | да |
| `/Library/Java/JavaVirtualMachines/jdk-22.jdk` | установлена инсталлятором, системно | да |
| `/opt/homebrew/Cellar/openjdk/26.0.1` | поставлена Homebrew **как зависимость Maven** | **нет** |

`/usr/libexec/java_home -V` — это реестр JDK в macOS, и он показывает только первые две. Homebrew ставит мимо реестра, поэтому третья JDK существует, работает, но в списке не значится. Именно она и оказалась источником проблемы.

## 3. Точек выбора JDK несколько, и они независимы

Это ключевая мысль всей темы: **нет одного места, где «задана версия Java»**.

| Что запускаешь | Кто решает, какая JDK |
|---|---|
| `java` / `javac` в терминале | `PATH` |
| `mvn` в терминале | `JAVA_HOME`; если пуст — дефолт из launcher-скрипта |
| Maven из IntelliJ | Settings → Build Tools → Maven → Runner → **JRE** |
| Компиляция самой IDEA (без Maven) | Project Structure → **Project SDK** |
| Запуск отдельного теста из IDEA | конфигурация запуска |

Эти настройки не связаны между собой. Отсюда классическая ситуация «в IDEA собирается, в терминале нет» — и наоборот.

## 4. Как `mvn` выбирает JDK: разбор launcher-скрипта

`/opt/homebrew/bin/mvn` — не бинарник, а shell-скрипт в одну строку:

```bash
JAVA_HOME="${JAVA_HOME:-/opt/homebrew/opt/openjdk/libexec/openjdk.jdk/Contents/Home}" exec .../mvn "$@"
```

Конструкция `${VAR:-default}` читается как **«взять `VAR`, если он задан и непуст, иначе подставить default»**.

Практическое следствие, наблюдавшееся вживую:

| Окружение | `JAVA_HOME` | Какая JDK поедет | Результат |
|---|---|---|---|
| терминал Дениса | задан в `~/.zshrc` (`java_home -v 22`) | JDK 22 | сборка зелёная |
| сессия агента | не задан | **Homebrew JDK 26** | Lombok не отработал, `cannot find symbol` |

То есть проект собирался правильно **не потому, что так настроен**, а потому что в личном файле `~/.zshrc` есть нужная строка. Этого файла нет ни в репозитории, ни у CI-агента, ни у любого другого разработчика.

## 5. Почему `maven.compiler.source/target` не спасает

В `pom.xml` было единственное упоминание версии Java:

```xml
<maven.compiler.source>17</maven.compiler.source>
<maven.compiler.target>17</maven.compiler.target>
```

- `source` — какой синтаксис языка разрешён (не использовать фичи новее 17);
- `target` — под какую версию JVM генерировать байткод.

Но **компилирует всё равно тот `javac`, который лежит в `JAVA_HOME`**. Эти параметры ограничивают уровень языка и байткода, а не выбирают JDK.

### Почему при этом ломается именно Lombok

Lombok — аннотационный процессор: он работает **внутри** `javac` и обращается к его внутренним API (`com.sun.tools.javac.*`). Эти API меняются от версии JDK к версии, поэтому каждая новая JDK требует новой версии Lombok.

Отказ при несовместимости **тихий**: процессор не падает с ошибкой, он просто не отрабатывает. Исчезают все генерируемые методы — `builder()`, геттеры, конструкторы от `@RequiredArgsConstructor` — и компиляция сыплется десятками `cannot find symbol` в файлах, которых никто не трогал. Диагностика уводит в сторону: выглядит так, будто автор забыл написать код, который на самом деле должен был сгенерироваться.

## 6. Два способа перестать зависеть от окружения

| | `maven-enforcer-plugin` | Toolchains |
|---|---|---|
| Что делает | **обнаруживает** несовместимость и падает с внятным сообщением | **решает**: заставляет Maven компилировать нужной JDK |
| Требует от окружения | ничего | файл `~/.m2/toolchains.xml` на каждой машине, включая CI-агент |
| Когда уместно | нужна понятная диагностика вместо загадочного отказа | нужно собирать конкретной JDK независимо от `JAVA_HOME` |

Для этого проекта выбран enforcer: он ничего не требует от окружения и работает одинаково у разработчика, у агента и в чужом клоне репозитория.

## 7. Как это выглядит в нашем `pom.xml`

Три уровня вложенности, каждый отвечает на свой вопрос:

```
executions  → когда запускать (цель + фаза)
  rules     → что проверять
    правило → его собственные параметры
```

У цели `enforce` фаза `validate` стоит по умолчанию — то есть проверка идёт **до компиляции**, что здесь и требуется.

Нотация диапазонов версий в Maven (общая, не только для этого правила):

| Запись | Значение |
|---|---|
| `[17,26)` | 17 включительно, 26 исключительно |
| `[17,21]` | обе границы включительно |
| `[17,)` | 17 и выше, без верхней границы |
| `22` | мягкое «рекомендуется 22» — **не** ограничение |

Последняя строка важна: одиночное число ничего не запрещает.

Выбранный диапазон `[17,26)` обоснован двумя фактами, а не взят наугад: нижняя граница следует из `maven.compiler.target`, верхняя — из воспроизведённого отказа Lombok 1.18.46 на JDK 26.

## 8. Результат: что видит человек с «неправильной» JDK

Было (12 строк, диагностика уводит не туда):

```
[ERROR] .../AccountApiService.java:[19,45] cannot find symbol
[ERROR] .../AccountFactory.java:[14,28] cannot find symbol
...
```

Стало (одна строка, на фазе `validate`, до компиляции):

```
Detected JDK /opt/homebrew/Cellar/openjdk/26.0.1/... is version 26.0.1
which is not in the allowed range [17,26).
```

Сообщение называет **какая** JDK подхватилась, **где** она лежит и **что** требуется — этого достаточно, чтобы человек нашёл проблему у себя сам.

## 9. Итог 20/80

1. «Версия Java» — три разные вещи: язык, JDK для сборки, рантайм для запуска.
2. На машине почти всегда несколько JDK, и часть из них не видна системному реестру.
3. **Точек выбора JDK несколько и они независимы** — `PATH`, `JAVA_HOME`, Maven Runner в IDE, Project SDK.
4. `maven.compiler.source/target` задают уровень языка и байткода, **но не выбирают JDK**.
5. Аннотационные процессоры (Lombok) исполняются внутри `javac` и потому чувствительны к версии JDK; отказ у них тихий.
6. Проект, который собирается только благодаря строчке в чьём-то `~/.zshrc`, не защищён — фиксировать требование надо в `pom.xml`.
