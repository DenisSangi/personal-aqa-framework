## Содержание фреймворка (что воспроизвести своими руками)

Фреймворк должен зеркалить `java-selenide-pp` и покрыть, как минимум, эти слои/темы (это ориентир для плана, не жёсткий порядок — уточни последовательность в PLAN.md):
1. Скелет репозитория и тулинга (Maven, Java 17, Selenide, тест-раннер, Allure, .gitignore, GitHub-репо, README).
2. Слой конфигурации/инфраструктуры (разрешение параметров: env var > system property > properties-файл; фасад-конфиг).
3. Слой утилит (`RandomGenerators`: email/alphanumeric/дата; `DateTimeUtil`; `WaitUtil`).
4. Слой element-обёрток (self-bounded generic `BaseElement<T extends BaseElement<T>>` с fluent-возвратом, адаптеры над Selenide: Input/Button/Dropdown/Table).
5. Слой Page Object (приватные локаторы-константы, fluent-действия, навигация через `return new NextPage()`).
6. Слой Reusable Actions (оркестрация сценариев поверх нескольких POM).
7. Базовый тест + lifecycle (Template Method: BaseTest → продуктовый base → конкретный тест; листенер/скриншот при падении).
8. Слой API-сервисов (REST Assured; сервис генерации тестовых данных для setup/teardown; `RestClient`-адаптер; модели через records/`@Builder`; Factory).
9. Продвинутые тестовые данные (records, `@DataProvider`/параметризация, фабрика, внутренний `static`-класс состояния сценария по образцу `ParticipantState`).
10. Слой БД (JDBC-утилита коннекта + `executeQuery` → `List<Map<String,String>>`, SQL-верификация в тесте).
11. Allure-отчётность (Steps, Attachments, скриншоты).
12. Параллелизация и потокобезопасность (ThreadLocal-драйвер, parallel-конфиг).
13. CI/CD на базе Jenkins с нуля (поднять Jenkins локально в Docker, декларативный `Jenkinsfile`, параметризованная job, публикация Allure).
14. Финальный проход по паттернам (какой паттерн где применён — заготовка для рассказа на интервью).

2. Мы обсуждаем задачу, пока у меня не возникнет ПОЛНОЕ понимание (я задаю вопросы, ты поясняешь минимальными изолированными примерами по моему стилю). Код решения ты мне НЕ даёшь.
3. Я реализую код сам.
4. Ты проверяешь: что верно, что нет, подводные камни — по возможности через живую компиляцию/прогон (`mvn` в этом окружении может быть недоступен — тогда `javac` + ручной harness, либо JUnit-jar'ы из `~/.m2`, как делали раньше).
5. Итерации: правки → повторная проверка, пока не будет финального аппрува.
6. После аппрува — задача закрывается, фиксируется в PROGRESS.md, переходим к следующей.
Правило: НИКОГДА не пиши мой продакшн-код за меня. Минимальные изолированные сниппеты «для объяснения концепции» — можно; готовое решение задачи — нельзя.

## Формат задачи-урока (он же — модель контента будущего веб-приложения)

Каждую задачу оформляй как markdown-файл-«урок» в папке `curriculum/` с фиксированной схемой полей (это и есть мост к веб-приложению — каждый такой узел позже станет экраном-уроком в приложении):
- `id`, фаза/слой, заголовок;
- **Описание** — что построить;
- **Место в фреймворке** — зависимости вверх/вниз;
- **Мотивировка** — зачем + цена отказа;
- **Теория** — нужные концепции + ссылка на файл в `theory/` (теоретический блок — самостоятельный артефакт, а не абзац внутри задачи; на него ссылаются задачи);
- **Definition of Done** — критерии приёмки;
- **Типичные ошибки** — заполняется ПОСЛЕ ревью моими реальными ошибками (это самое ценное для приложения);
- **Ссылка на реальный код `java-selenide-pp`**.
Помечай каждый урок тегами стека (java/selenide/testng/rest-assured/sql/jenkins), чтобы позже можно было добавить параллельные треки (Python, TypeScript, Cucumber) в то же дерево уроков.

## Связка с будущим веб-приложением

Веб-приложение (desktop-first) будет вести человека через такую же постройку фреймворка руками, с привязанной теорией и interview-prep. Поэтому: (а) веди весь `curriculum/` и `theory/` как чистый, самодостаточный, версионируемый контент по схеме выше — он и есть будущий контент приложения; (б) фиксируй мои реальные ошибки и их разбор (раздел «Типичные ошибки») — это будущая ценность для пользователей; (в) держи структуру дерева уроков расширяемой на другие языки/инструменты.

**Идея (зафиксирована 2026-07-23):** разработать для этого веб-приложения собственный учебный веб-сервис со сложной микросервисной архитектурой, публичным API и доступной схемой БД. Причина: публичные demo-сайты (напр. `automationexercise.com`, выбранный для `personal-aqa-framework`) не дают доступа к своей БД, поэтому слой БД в текущем проекте (Фаза 9 `PLAN.md`) вынужденно самостоятельное упражнение на изолированной схеме, а не сквозной UI→API→Database сценарий. Собственный сервис снял бы это ограничение и позволил бы подходу UI → API → Database работать по-настоящему сквозным образом для пользователей будущего приложения.
