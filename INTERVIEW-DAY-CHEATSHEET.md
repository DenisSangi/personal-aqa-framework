## 1. «Какие паттерны вы использовали?» — 60-секундный ответ

1. **Page Object** — одна страница = один класс (`HomePage`, `LoginPage`, `ProductsPage`, `CartPage`).
2. **Fluent Interface** — методы POM возвращают `this`/следующую страницу; `BaseElement<T>` возвращает `T` через `(T) this` (self-bounded generic).
3. **Adapter** — POM работает с полями `BaseElement`/`InputElement`/`ButtonElement`/`TableElement`, не с сырым `SelenideElement`.
4. **Facade** — `FrameworkConfig` прячет порядок обхода источников (env var → system property → 2 properties-файла) за простыми константами.
5. **Builder** — `AccountModel.builder()...build()` (Lombok) вместо конструктора с кучей позиционных `String`.
6. **Factory** — `AccountFactory.createValidAccountModel()` возвращает готовую валидную модель, вызывающий код не знает деталей сборки.

**Если попросят углубиться — цена отказа (по одной фразе):**
- Page Object: без него — дублирование локаторов по всем тестам, правка DOM = правка N тестов.
- Fluent Interface: без него — цепочка шагов рассыпается на отдельные вызовы, теряется наглядность сценария.
- Adapter: без него — смена Selenium/Appium/Playwright требует переписать каждое поле каждого POM.
- Facade: без него — логика выбора источника конфига дублируется в каждом месте использования.
- Builder: без него — конструктор на 10+ `String`-параметров, легко перепутать соседние аргументы, компилятор не поймает.
- Factory: без него — ручная сборка валидной модели в каждом тесте вместо одного места.

**Осторожно, не путать снова (ошибки при подготовке 05.08):**
- Adapter — класс называется `BaseElement`/`InputElement`/..., НЕ «`Elements`».
- Factory — `AccountFactory.createValidAccountModel()`, НЕ «`AccountModelFactory`»/«`AccountFabric`».
- Fluent Interface — пример свой (`BaseElement<T>`), не `RestClient`/`given()` (это чужой fluent-API библиотеки REST Assured, у нас `RestClient.get()` не чейнится).

## 2. Три темы блица (закрыты 05.08)

- **`AutoCloseable` vs `Closeable`**: `AutoCloseable` (`java.lang`) — база, `close() throws Exception`. `Closeable` (`java.io`) **расширяет** `AutoCloseable`, сужает до `throws IOException` + требует идемпотентности повторного `close()`.
- **`Comparator.comparing().thenComparing()`**: `Comparator.comparing(User::getLastName).thenComparing(User::getAge)` — сначала сортирует по фамилии, при равенстве фамилий — по возрасту.
- **Жизненный цикл бага**: `Open → In Progress → Ready for testing → Testing → Closed` (закрывает QA после успешного ретеста, не менеджер), с точками `Reopen` при провале ретеста; альтернативные терминальные статусы — `Not a bug`, `Can't reproduce`, `Won't fix` (это решение менеджера/приоритизация), плюс `Duplicate`.

## 3. Разрозненные факты, накопленные за спринт (готовые примеры под руками)

- **`SELECT` без `ORDER BY` не гарантирует порядок строк** — источник флаки-теста, если assert полагается на порядок.
- **«Expected X, got X» в логе** обычно значит сравнение разных типов (`String` vs `java.sql.Date`, `int` vs `Integer` и т.п.), не логическую ошибку.
- **Constraint в БД vs валидация в приложении** — разные уровни защиты; БД — последний рубеж, приложение должно проверять раньше.
- **`PreparedStatement` вместо конкатенации строк** — защита от SQL-инъекций, параметры `?`.
- **Health-check ≠ работоспособность** — `pg_isready` может ответить «готов», даже если конкретная база/схема ещё не существует.
- **Same-origin policy блокирует JS-доступ к чужому iframe** (например, рекламному) — а `WebDriver.switchTo().frame(...)` работает, потому что переключение происходит на уровне драйвера, а не через JS в контексте страницы.
- **Своё правило, набитое 5 раз подряд за спринт:** verify-метод должен возвращать содержательное значение (строку/объект) и сравниваться через `assertEquals` — не голый `boolean` через `assertTrue`. `assertEquals` печатает оба значения в стектрейс, `assertTrue` — нет.
