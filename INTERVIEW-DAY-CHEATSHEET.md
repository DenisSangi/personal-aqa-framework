# Шпаргалка на день интервью

Единственная шпаргалка проекта. Собрана из подготовки к inDrive (2026-08-06) и TradingView (2026-08-12), дополняется по мере постройки фреймворка. Актуально на **2026-08-19**.

Всё ниже опирается на **свой** код `personal-aqa-framework` и на реальные истории отладки — не на пересказ статей. Читается за 10 минут; разделы 1, 7, 8 и 12 — обязательный минимум перед любым интервью.

## 1. «Какие паттерны вы использовали?» — 60-секундный ответ

1. **Page Object** — одна страница = один класс (`HomePage`, `LoginPage`, `ProductsPage`, `CartPage`).
2. **Fluent Interface** — методы POM возвращают `this`/следующую страницу; `BaseElement<T>` возвращает `T` через `(T) this` (self-bounded generic).
3. **Adapter** — POM работает с полями `BaseElement`/`InputElement`/`ButtonElement`/`TableElement`, не с сырым `SelenideElement`.
4. **Facade** — `FrameworkConfig` прячет порядок обхода источников (env var → system property → properties-файлы) за простыми константами.
5. **Builder** — `AccountModel.builder()...build()` (Lombok) вместо конструктора с кучей позиционных `String`.
6. **Factory** — `AccountFactory.createValidAccountModel()` возвращает готовую валидную модель, вызывающий код не знает деталей сборки.

**Если попросят углубиться — цена отказа (по одной фразе):**
- Page Object: без него — дублирование локаторов по всем тестам, правка DOM = правка N тестов.
- Fluent Interface: без него — цепочка шагов рассыпается на отдельные вызовы, теряется наглядность сценария.
- Adapter: без него — смена Selenium/Appium/Playwright требует переписать каждое поле каждого POM.
- Facade: без него — логика выбора источника конфига дублируется в каждом месте использования.
- Builder: без него — конструктор на 10+ `String`-параметров, легко перепутать соседние аргументы, компилятор не поймает.
- Factory: без него — ручная сборка валидной модели в каждом тесте вместо одного места.

**Осторожно, не путать (реальные ошибки при подготовке):**
- Adapter — класс называется `BaseElement`/`InputElement`/…, НЕ «`Elements`».
- Factory — `AccountFactory.createValidAccountModel()`, НЕ «`AccountModelFactory`»/«`AccountFabric`».
- Fluent Interface — пример свой (`BaseElement<T>`), не `RestClient`/`given()` (это чужой fluent-API библиотеки REST Assured).

**Третье применение Facade, появилось 18.08:** SLF4J — фасад над реализацией логирования (см. раздел 7).

## 2. Selenium — что это и как работает

Не один инструмент, а **семейство**:

| Компонент | Что делает |
|---|---|
| **WebDriver** | Ядро. Программное управление браузером из кода. Это и имеют в виду в 95% случаев. |
| **Selenium IDE** | Плагин для браузера, запись/воспроизведение. Для прототипов, не для боевых сьютов. |
| **Selenium Grid** | Распределённый прогон на нескольких машинах/браузерах параллельно. |

**Одна фраза:** Selenium WebDriver — стандартизированный способ управлять реальным браузером так, как это делал бы пользователь, из кода на любом языке.

**Цепочка из 4 звеньев:**

```
Твой код (Java)
   ↓  selenium-java (клиентская библиотека, «биндинги»)
HTTP-запрос по W3C WebDriver Protocol
   ↓  chromedriver / geckodriver — ОТДЕЛЬНЫЙ процесс-исполняемый файл
Нативные команды браузера (CDP у Chrome и т.п.)
   ↓
Браузер выполняет, ответ идёт обратно вверх по цепочке
```

- **Драйвер — отдельный процесс** со своим локальным HTTP-сервером. `driver.findElement(...)` — буквально `POST /session/{id}/element`.
- **Каждая команда = отдельный round-trip по HTTP.** Отсюда ответ на «почему UI-тесты медленные» и «почему setup через API в разы быстрее кликов».
- **W3C WebDriver Protocol** — стандарт с Selenium 4, до него JSON Wire Protocol (legacy). Смысл перехода: драйверы разных браузеров ведут себя одинаково.
- **Selenium Manager** (с 4.6) сам скачивает драйвер — ручной путь к `chromedriver` и `WebDriverManager` больше не нужны.

**Сильный пример из своего проекта:** на `automationexercise.com` рекламная виньетка перехватывала клики. JS-решение было **принципиально бессильно** — рекламный iframe кросс-доменный, same-origin policy блокирует доступ к `contentDocument`. А `switchTo().frame(...)` сработал, **потому что WebDriver переключает контекст на уровне драйвера, а не изнутри JS-песочницы страницы**. Демонстрация того, что WebDriver работает снаружи страницы, а не внутри неё.

## 3. Чего Selenium НЕ делает

- ❌ Нет ассертов → нужен TestNG / JUnit.
- ❌ Нет тест-раннера, репортинга, ретраев → TestNG + Allure.
- ❌ Нет умных ожиданий из коробки → только implicit, остальное руками.
- ❌ Не умеет ничего вне браузера (файлы ОС, почта, БД).
- ❌ `findElement` **не ждёт**: либо нашёл сразу, либо `NoSuchElementException`.

Отсюда и берутся надстройки вроде Selenide.

## 4. Ожидания

| Тип | Где задаётся | Суть |
|---|---|---|
| **Implicit** | Один раз на драйвере, глобально | Применяется ко **всем** поискам элемента. |
| **Explicit** | Локально, `WebDriverWait` + `ExpectedConditions` | Ждёт **конкретное условие** в конкретном месте. |
| **Fluent** | `FluentWait` | То же + настраиваемый интервал опроса и игнорируемые исключения. |

**Проверенные факты (не «кажется»):**
- `WebDriverWait extends FluentWait` — explicit это частный случай fluent.
- **Не смешивать implicit и explicit** — суммарное время ожидания непредсказуемо.
- Ловушка implicit: проверка **отсутствия** элемента будет честно ждать весь таймаут.
- «Динамические ожидания» — **не термин** из документации. Официальных три.
- Таймаут — это **потолок, а не длительность**: подъём с 4 до 10 с не замедлил сьют (замерено).

## 5. Selenide — чем выгоден

Selenide = обёртка над Selenium. В проекте: **Selenide 7.2.3 тянет Selenium 4.19.1** (Selenium никуда не делся, он внутри).

| Выгода | Конкретика |
|---|---|
| **Умные ожидания в каждом действии** | `$(...).click()` сам ждёт элемент. Убирает 90% флака и весь boilerplate `WebDriverWait`. |
| **Ленивые элементы** | `$(...)` ищет элемент только в момент действия. Меньше `StaleElementReferenceException`. |
| **Zero-config браузер** | Не нужно вручную создавать/закрывать `WebDriver`; внутри свой `ThreadLocal`. |
| **Лаконичный API** | `$("#id")`, `$$(...)`, `shouldBe(visible)`. |
| **Коллекции полноценные** | `ElementsCollection` со своими ожиданиями: `shouldHave(size(3))`, `texts()`. |
| **Внятные ошибки** | Что ожидал, что было, скриншот, page source. |
| **Скриншоты и отчётность** | Из коробки, плюс интеграция с Allure. |

**Цифры (проверены разбором jar, называть смело):** дефолтный таймаут — **4000 мс**, интервал опроса — **200 мс**. Selenide **нигде** не вызывает `implicitlyWait` — его ожидания это explicit-механика под капотом.

**Честная обратная сторона:** абстракция прячет Selenium, и для нестандартного приходится спускаться ниже — `WebDriverRunner.getWebDriver()`. Плюс на Selenium 4.19.1 CDP-команды не заработали под свежий Chrome.

## 6. Локаторы

**Приоритет:** `id` → `name` / `data-*` → CSS → XPath.

- **CSS** — быстрее и читаемее.
- **XPath** — умеет то, чего не умеет CSS: подниматься к родителю и искать **по тексту**.
- **Избегать** абсолютных и позиционных путей.

**Реальная история:** локатор `(//button)[1]` попал в **рекламный виджет Google**, а не в элемент сайта.

**Свой хороший локатор — XPath с предикатом-фильтром:**
```
//div[@class='productinfo'][.//p[text()='%s']]//a[@class='add-to-cart']
```
`[.//p[...]]` в скобках — **фильтр** (возвращается сам `div`), `//a` снаружи скобок — **шаг навигации** (меняет результат).

## 7. Логирование и SLF4J (закрыто 18.08)

**Главное различие, с которого начинается любой вопрос по теме:**

> **`slf4j-api` — это фасад: только интерфейсы (`Logger`, `LoggerFactory`, уровни), реализации в нём нет.** Библиотеки (Selenide, TestNG) зависят **только** от API и не решают за меня, чем логировать. Провайдера выбирает **приложение**.

Отсюда самая коварная ловушка, проверенная на своём проекте: `slf4j-api` был в classpath транзитивно через Selenide, **а провайдера не было ни одного** — любой `log.info(...)` скомпилировался бы и напечатал **ноль строк**, уйдя в NOP-заглушку. Это опаснее отсутствующей зависимости: там был бы `NoClassDefFoundError`, здесь — тишина без ошибки.

**Три провайдера:** `slf4j-simple` (одна зависимость, но **одно** назначение вывода — `logFile` перенаправляет консоль, а не добавляет аппендер), `logback-classic` (референсная реализация SLF4J, XML-конфиг), `log4j2` (стоит в боевом `java-selenide-pp`, две зависимости + ловушка поколений `log4j-slf4j-impl` vs `log4j-slf4j2-impl`).

**Почему выбрали logback — правильная формулировка:** не «потому что он уже был» (его не было), а потому что дешевле вход, чем у log4j2, и — главное — **ошибиться дёшево**: фасад делает замену провайдера правкой одной строки в `pom.xml` плюс конфиг, **без единой правки Java-кода**.

**Как подключается:**
- зависимость `logback-classic` в `pom.xml` со `<scope>test</scope>`;
- конфиг `logback.xml` в **корне** `src/test/resources`.

Обе половины по одной причине: **scope решает «какая реализация», ресурс — «с какими настройками», и то и другое выбирает приложение — библиотека не решает ни за кого.** Замер: два провайдера в classpath → `SLF4J(W): Class path contains multiple SLF4J providers` и **произвольный** выбор одного.

**Как объявляется и вызывается:**

```java
@Slf4j                                            // Lombok генерирует private static final Logger log
public class AccountApiService { ... }

log.debug("Create Account: {}", body);            // параметризация через {}, не конкатенация
log.warn("Test {} retry attempt: {}", name, n, throwable);   // Throwable — ПОСЛЕДНИМ и ЦЕЛИКОМ
```

**Исключение передаётся последним аргументом, без `{}` под него, целиком** — не `.getMessage()` и не `.getCause()`. Замер:

| Форма | Что в логе |
|---|---|
| `log.warn(msg, wrapper)` | верхний уровень **и** `Caused by:` — вся цепочка |
| `log.warn(msg, wrapper.getCause())` | только внутреннее исключение, верхний уровень потерян |
| `log.warn(msg, e.getMessage())` | одна строка текста, ни типа, ни стектрейса |
| `getCause()` там, где причины нет | **пусто** (реально было: в логе `due to null`) |

Не путать с `isTransient(Throwable)`, где цепочка обходится **вручную** циклом `throwable = throwable.getCause()` — там цель другая: **принять решение** (повторять тест или нет), а не показать человеку.

**Уровни — это порог.** `TRACE < DEBUG < INFO < WARN < ERROR`; печатается всё, что не ниже установленного. Критерий выбора: строка уровня `INFO` должна иметь смысл для человека, который смотрит на упавшую сборку в CI и про твой код ничего не знает. **Логгер не знает про результат теста** — он печатает в момент выполнения строки, поэтому «только при падении» порогом не выражается, нужно условие в коде.

**«log and throw» — антипаттерн.** Если бросаешь исключение, логировать то же событие не нужно: попадёт в вывод дважды. Решение о сообщении принимает тот, кто **обрабатывает**. Полезный текст кладётся в сообщение самого исключения: `throw new RuntimeException("framework.properties file is missing", e)`.

**Логгер не лечит маскировку отказа.** `catch (SQLException e) { log.error(...); }` и продолжение работы = тест зеленеет при лежащей базе. **В боевом `java-selenide-pp` на этом месте стоит `LOG.error` и дефект точно такой же** — лечится не логом, а поведением: `throw new RuntimeException(msg, e)`.

**Готовая история «зачем вам логирование»:** в первый же прогон после подключения всплыл `WARN` TestNG об отсутствующем DOCTYPE в `regression.xml` — инструмент предупреждал об этом всё время жизни проекта, а предупреждение уходило в NOP-заглушку.

**Признак, что конфиг не подхватился:** дефолтный формат logback `13:19:04.626 [main] DEBUG полное.имя.Класса -- текст` (точки во времени, двойной дефис) и `root=DEBUG`. Проверяется через `<configuration debug="true">` — печатает, какой ресурс реально найден. Плюс: **`logback-test.xml` имеет приоритет над `logback.xml`.**

## 8. Allure-отчётность (закрыто 19.08)

### Отчёт — это две независимые стадии, а не одна

```
mvn test                          mvn allure:report
    ↓                                    ↓
allure-testng                       allure-maven
(БИБЛИОТЕКА — пишет)                (ПЛАГИН — читает и строит HTML)
    ↓                                    ↓
    └──────►  target/allure-results  ◄───┘
                                         ↓
                            target/site/allure-maven-plugin/index.html
```

Библиотека подписана на события TestNG и после каждого теста кладёт в папку `<uuid>-result.json`. Генератор — **отдельная программа**, библиотека его не запускает: прогон уже закончился, JVM завершилась.

**Генератор один, носителей три:** CLI (`allure serve`), Maven-плагин `allure-maven`, плагин Jenkins. Работу делает одна и та же программа, меняется способ её позвать.

**Почему в проекте плагин, а не CLI:** он уезжает в git вместе с проектом — ни на машине коллеги, ни на агенте CI ничего доустанавливать не надо.

**Почему Allure 2, а не 3:** Allure 3 — генератор на Node.js; его использование требует `npm install -g allure` **на каждом агенте** Jenkins. Это возвращает ту самую ручную подготовку окружения, ради ухода от которой и выбирался плагин. Критерий выбора инструмента здесь — **не «новее/мощнее», а сколько ручных действий он требует в чужом окружении**.

### Гигиена результатов

`allure-results/` по умолчанию создаётся **в корне проекта**, а `mvn clean` чистит только `target/`. Итог: результаты копятся вечно, и отчёт склеивает все прогоны в один. В этом проекте так накопилось 6797 файлов и 27 МБ за 26 дней — отчёт показывал **232 теста вместо 32**.

Лечится файлом `allure.properties` в корне тестовых ресурсов:

```properties
allure.results.directory = target/allure-results
```

**Важно не перепутать стороны:** это конфиг **библиотеки-писателя**, он говорит, куда *писать результаты*. К тому, где строится HTML, отношения не имеет. Настраивать надо писателя, а не читателей: читателей будет несколько (плагин локально, Jenkins в CI), и каждого пришлось бы настраивать отдельно.

### Откуда берутся шаги — три механизма

| | Что это | Цена |
|---|---|---|
| `@Step` на методе | **ядро** библиотеки (`Step.class` лежит в `allure-java-commons`) | требует AspectJ weaver |
| `allure-selenide` | отдельная официальная интеграция, шаг на каждое действие Selenide | шаги на языке DOM, их много |
| мост «лог → Allure» | каждая строка лога становится шагом | **публичного артефакта не существует**, писать самому |

**Как сделано в боевом `java-selenide-pp`:** `@Step` не встречается **ни разу** (grep по 6 модулям). Работает третий путь: `tmiComment(...)` → лог log4j2 → самописный `<AllureAppender/>` → `Allure.step(...)`. Appender написан внутри компании; ни `allure-logback`, ни `allure-log4j2` в публичных артефактах Allure нет.

### `@Step` и aspectjweaver — почему без него молчит

**Одной фразой:** аннотация — это **данные, а не поведение**. Она ничего не делает сама; поведение появляется только тогда, когда есть тот, кто её читает.

Кто может читать аннотации:

| Читатель | Когда работает | Пример |
|---|---|---|
| компилятор | при сборке | `@Override` |
| фреймворк через рефлексию | в рантайме | `@Test` — TestNG сам сканирует классы |
| **javaagent (AspectJ weaver)** | **при загрузке класса в JVM** | `@Step` |

`@Step` — точка **AOP** (аспектно-ориентированного программирования). Идея AOP: есть сквозная задача (логирование, замер времени, шаги отчёта), которая нужна в сотне мест и не относится к бизнес-логике ни одного из них. Вместо того чтобы дописывать её руками в каждый метод, её описывают **один раз** как «аспект» и указывают, куда она применяется. Дальше специальный инструмент **вплетает** (weave) этот код в нужные методы.

Механика для `@Step` по шагам:

1. Аспекты Allure физически лежат в jar — `io/qameta/allure/aspects/StepsAspects.class`. Это код «перед методом открыть шаг, после — закрыть».
2. Но сам по себе он не выполняется — нужно вплести его вокруг твоих методов.
3. Этим занимается **AspectJ weaver**, подключаемый как `-javaagent:` — надстройка над JVM, которая стартует **раньше** прикладных классов и переписывает их байткод на лету, в момент загрузки.
4. Нет weaver'а — нет вплетения. Аннотация остаётся просто пометкой в байткоде: код компилируется, тест проходит, шага в отчёте нет, **ошибки тоже нет**.

Замер на изолированном проекте:

```
без -javaagent:   steps: [Allure.step(...) — есть]                    ← @Step отсутствует
с  -javaagent:    steps: [@Step — есть, {url} подставлен;  Allure.step(...) — есть]
```

`Allure.step("текст")` — обычный вызов метода библиотеки, weaver ему не нужен вовсе. Отсюда практическое правило: **если шагов от аннотаций нет, а от прямых вызовов есть — не подключён weaver.**

**Как подключается в Maven** (путь к jar у каждого свой, хардкодить нельзя):

```xml
maven-dependency-plugin, goal properties   →  ${org.aspectj:aspectjweaver:jar}
                                               (абсолютный путь на ЭТОЙ машине)
                                                      ↓
surefire:  <argLine>-javaagent:${org.aspectj:aspectjweaver:jar}</argLine>
```

### Где размечать шаги

Слой — **Page Object, методы-действия**. Тест → Reusable Actions → Page Object → BaseElement: чем ниже слой, тем мельче и бесполезнее шаг.

**Контринтуитивный факт, виден только на живом отчёте:** размеченный метод работает **контейнером** — прячет свои технические шаги внутрь и сворачивается в одну строку. Неразмеченный контейнера не создаёт, и вся его техника **всплывает на верхний уровень** вперемешку с бизнес-шагами. То есть правило «не размечать verify, чтобы не было шума» даёт шума больше.

**Не класть в текст шага секреты:** `@Step("Enter password {password}")` отправит пароль в отчёт, который публикуется в Jenkins и хранится по настройкам сборки.

**Шаг краснеет только от исключения.** `@Step` на методе, возвращающем `boolean`, даёт зелёную галочку даже когда проверка не прошла — падает `assertTrue` уже снаружи закрытого шага. Замер:

```
тест: t                                            -> failed
   шаг: Check search results contains product: ... -> passed
```

Отчёт в такой конфигурации уводит диагностику в противоположную сторону.

### Вложения (скриншот, page source)

**Момент вызова важнее места в коде.** Замер по трём точкам:

| Откуда вызван `Allure.addAttachment(...)` | Результат |
|---|---|
| из тела `@Test` | вложение в отчёте ✅ |
| из `@AfterMethod(alwaysRun = true)` | `attachments: []` ❌ |
| из `ITestListener.onTestFailure(...)` | `attachments: []` ❌ |

Причём объяснение «браузер уже закрыт» неверно — замерен порядок: `onTestFailure` идёт **до** `@AfterMethod`, драйвер ещё жив. Теряется именно привязка вложения к тесту.

**Рабочий механизм — `allure-selenide`:**

```java
SelenideLogger.addListener("AllureSelenide",
    new AllureSelenide().screenshots(true).savePageSource(true).includeSelenideSteps(false));
```

В его `afterEvent` **два независимых блока**: один прикладывает скриншот и HTML, другой создаёт шаги. `includeSelenideSteps(false)` гасит только второй — то есть библиотеку можно взять **ради вложений, не беря шаги**. Работает потому, что вложение добавляется во время события, то есть внутри теста.

**Граница механизма:** срабатывает на `FAIL` **события Selenide**. Если падает `assertEquals`/`assertTrue` в теле теста — скриншота не будет. Лечится не подпоркой, а переводом проверок на Selenide (`shouldHave(size(...))`, `findBy(text(...)).shouldBe(visible)`), чтобы падение происходило изнутри Selenide.

### Готовые истории для интервью

- **«Отчёт, который вводит в заблуждение»** — зелёная галочка на шаге «проверить, что товар найден» ровно тогда, когда товар не найден.
- **«Месяц копившихся результатов»** — 232 теста вместо 32 и вопрос, почему `mvn clean` их не чистит.
- **«Тихий отказ аннотации»** — `@Step` без weaver: компилируется, проходит, молчит. Тот же класс, что `logback.xml` в неправильной папке.
- **«Вложение окупилось за полчаса»** — сохранённый `Page source` из отчёта был инструментом, которым диагностировали ловушку XPath `position()`.

## 9. Параллельный запуск и стабильность (закрыто 11.08)

- `testng.xml` с `parallel="classes"`, `threadCount` — через property с дефолтом (свойство **окружения**, а не тестов, поэтому задаётся снаружи, в том числе из Jenkins).
- **Копию на поток дают только `ThreadLocal` и локальные переменные** — не `final`-поля и не `ConcurrentHashMap`.
- `ConcurrentHashMap` **не делает атомарной составную операцию** — в `UserService` референса поверх неё стоит `synchronized` на «найти свободного / занять».
- **Боевой референс не параллелит вообще** (13 объявлений `parallel`, все `none`/`false`) — причина в общих тестовых данных, не в потокобезопасности Java.
- **Уровень фикстуры определяется тем, изменяет ли тест сущность и сколько стоит её создание.** Читатели (логин) не конфликтуют — им общий аккаунт не мешает; изменяющие тесты требуют своего.
- Retry: решение о повторе принимается **не по типу обёртки, а по содержимому цепочки причин** — снаружи один `UIAssertionError`, разделяет их обход `getCause()`. Расширять фильтр на всё подряд вредно: замаскирует настоящие дефекты.

## 10. Разрозненные факты (готовые примеры под руками)

- **`SELECT` без `ORDER BY` не гарантирует порядок строк** — источник флака, если assert полагается на порядок.
- **«Expected X, got X»** обычно значит сравнение разных типов (`String` vs `java.sql.Date`), не логическую ошибку.
- **Constraint в БД vs валидация в приложении** — разные уровни защиты; БД последний рубеж.
- **`PreparedStatement` вместо конкатенации** — защита от SQL-инъекций.
- **Health-check ≠ работоспособность** — `pg_isready` отвечает «готов» даже при несуществующей базе.
- **Недоступность бывает двух сортов:** отказ (`docker stop` → соединение отвергается сразу) и **зависание** (`docker pause` → порт проброшен, ответа нет, JDBC ждёт без ограничения). Второе опаснее: тест не краснеет, а висит; лечится `connectTimeout`/`socketTimeout`, а не обработкой исключений.
- **Проверять защиту можно только сломав то, от чего она защищает** — тест на недоступную базу проверяется остановкой контейнера.
- **Verify-метод должен возвращать содержательное значение** и сравниваться через `assertEquals`, а не голый `boolean` через `assertTrue`: `assertEquals` печатает оба значения в стектрейс.
- **Порядок аргументов в TestNG — `assertEquals(actual, expected)`**, наоборот, чем в JUnit.
- **Тихий отказ бывает и в конфигурации, не только в коде:** опечатка в suite-XML (`ProductApiService` вместо `ProductApiServiceTest`) молча исключила тест из сьюта — поймано арифметикой (ожидалось 32, пришёл 31).

## 11. Если покажут код на ревью

Пробегись по тому, что реально ловил у себя:

1. **Проверка, которая ничего не проверяет** — `.equals()`/`verify...()`, чей результат не подключён к ассерту. Самая частая находка.
2. **Жёсткие/позиционные локаторы.**
3. **`Thread.sleep`** вместо условного ожидания.
4. **Отсутствие teardown** / тесты, зависящие от порядка выполнения.
5. **Тест зависит от данных, которые сам не создаёт** — реально было: тест две недели держался на товарах, положенных в корзину руками.
6. **Тихий отказ** — `catch`, который печатает ошибку и продолжает: тест зеленеет при сломанном окружении.
7. **«log and throw»** — об одном событии сообщают дважды.
8. **Магические числа** вместо констант (`!= 201` вместо `CREATED_CODE`).
