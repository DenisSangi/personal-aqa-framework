## Открытые решения — подтверждены Денисом (2026-07-23)

1. **Целевой сайт:** `automationexercise.com` — UI и REST API в одном домене, что держит связку «API-setup → UI-verify» (и наоборот) реальной в рамках одного сайта, как в `java-selenide-pp`.
2. **БД-тесты:** локальный PostgreSQL в Docker + сид-данные. Явная оговорка (учтена в P9-T3): это самостоятельное упражнение на своей схеме, не сквозной UI/API→БД сценарий — `automationexercise.com` доступа к своей БД не даёт. Механика при этом (JDBC `try-with-resources`, `executeQuery` → `List<Map<String,String>>`, SQL-верификация) тренируется полноценно. См. также идею для будущего веб-приложения ниже — собственный сервис снял бы это ограничение.
3. **Тест-раннер:** TestNG — зеркалит `java-selenide-pp` (`@DataProvider`, `testng.xml`, listeners), максимальный перенос знаний на интервью.
4. **Место в рутине:** решено 2026-07-22 — постройка фреймворка это главный упор ежедневной рутины; Блок 7 на паузе.

## Фаза 0 — Скелет репозитория и тулинга

Зависимость: ничего не зависит от неё, она сама ни от чего не зависит. Первая задача цикла.

- **P0-T1 — Repo & Maven skeleton.** Maven-проект, Java 17, `.gitignore`, публичный GitHub-репозиторий, README-заглушка, зависимости: Selenide, TestNG, Allure (без кода фреймворка ещё — просто `pom.xml` компилируется и `mvn -v`/тестовый прогон пустого TestNG-сьюта проходит зелёным). Мотивировка: без рабочего тулинга и CI-пайплайна нечего показывать на портфолио и не с чем всё остальное интегрировать. Теория: Maven lifecycle (`compile`/`test`/`package`), зависимости vs плагины, структура `src/main` vs `src/test`. Тег: java, maven.

## Фаза 1 — Конфигурация и инфраструктура

Зависимость: опирается на Фазу 0 (нужен проект, куда класть properties/классы). От неё зависят все слои, которым нужен URL/креды (POM, API-сервисы, БД-util).

- **P1-T1 — Config facade + порядок разрешения параметров.** Facade-класс `FrameworkConfig` (по образцу `ClinCardConfig`): порядок приоритета env var → system property → `.properties`-файл; наружу — простые статические константы (`BASE_URL` и т.п.). Мотивировка: без единой точки конфигурации каждый вызывающий код сам городит логику «откуда брать URL» — дублирование и рассинхрон между окружениями. Теория: `System.getenv()` vs `System.getProperty()`, чтение `.properties` через `Properties`/classpath, паттерн Facade (см. `design-patterns.md` #6). Тег: java, config.

## Фаза 2 — Утилиты

Зависимость: опирается на Фазу 0. От неё зависят слой тестовых данных (Фаза 8) и любые тесты, которым нужны случайные/датированные значения.

- **P2-T1 — RandomGenerators.** `generateAlphabetic()`, `generateAlphanumeric()`, `generateEmail()`, `generateNumber()`. Мотивировка: без генератора тесты либо используют статичные данные (коллизии между параллельными прогонами), либо дублируют генерацию в каждом тесте. Теория: `java.util.Random` / `ThreadLocalRandom`, почему статичные тестовые данные ломаются при параллелизации. Тег: java.
- **P2-T2 — DateTimeUtil.** Форматирование текущей даты под разные паттерны (для уникальности имён сущностей — план на это ссылается в Фазе 8). Теория: `java.time` (`LocalDateTime`, `DateTimeFormatter`). Тег: java.

## Фаза 3 — Слой element-обёрток

Зависимость: опирается на Фазу 0 (Selenide уже в `pom.xml`). От неё зависит вся Фаза 4 (POM работает только через эти обёртки, не напрямую с Selenide).

- **P3-T1 — BaseElement<T extends BaseElement<T>> + первый адаптер (Input).** Self-bounded generic база с fluent-возвратом `(T) this`, единый `waitAndGetElement()` (видимость + скролл), первый конкретный класс `InputElement`. Мотивировка: без этого слоя POM обращается к Selenide напрямую — миграция на другой драйвер/библиотеку означает переписать каждый POM-класс вместо одного слоя адаптеров (см. «Без паттерна» для Adapter, `design-patterns.md` #5). Теория: bounded self-type generics, паттерны Adapter + Fluent Interface + Template Method (`waitAndGetElement` в базе, специфика в наследнике). Тег: java, selenide.
- **P3-T2 — Button/Dropdown/Table.** Ещё три обёртки по образцу Input. Мотивировка: закрепление паттерна на разных типах взаимодействия (клик, выбор, чтение таблицы). Теория: инкапсуляция специфики Selenide API (`selectOption`, `$$` коллекции) за бизнес-методами. Тег: java, selenide.

## Фаза 4 — Page Object

Зависимость: опирается на Фазу 1 (URL из конфига) и Фазу 3 (элементы). От неё зависят Фаза 5 (Reusable Actions) и Фаза 6 (тесты).

- **P4-T1 — Первая страница (Login/Home) + навигационный переход.** Приватные локаторы-константы, поля-обёртки из Фазы 3, `verifyPageIsOpen()` (fluent), один навигационный метод `return new NextPage()`. Мотивировка: без POM — локаторы прямо в теле теста; изменился DOM → правишь N тестов вместо одного класса (см. «Без паттерна» для Page Object, `design-patterns.md` #1). Теория: Page Object, Fluent Interface, Lazy Initialization (Selenide `$` не ищет элемент сразу). Тег: java, selenide.
- **P4-T2 — Вторая страница + сценарий из двух шагов.** Закрепление на второй странице реального сайта, первый живой fluent-переход между двумя POM. Тег: java, selenide.

## Фаза 5 — Reusable Actions

Зависимость: опирается на Фазу 4 (оркеструет несколько POM).

- **P5-T1 — Login/Navigation ReusableActions.** Сценарный хелпер поверх ≥2 POM (например: открыть сайт → залогиниться → оказаться на нужной странице), возвращает нужный POM. Мотивировка: без этого слоя каждый тест сам склеивает многошаговый сценарий из вызовов POM — дублирование одного и того же «пути» в каждом тесте. Тег: java, selenide.

## Фаза 6 — Базовый тест и lifecycle

Зависимость: опирается на Фазы 1, 4, 5. От неё зависит вся Фаза 7+ (реальные тесты пишутся поверх базового класса).

- **P6-T1 — BaseTest (Template Method) + первый реальный @Test.** Иерархия `BaseTest` → продуктовый base (если нужен) → конкретный тестовый класс; `@BeforeMethod`/`@AfterMethod` — открыть/закрыть браузер; первый содержательный `@Test`, использующий POM+ReusableActions из Фаз 4–5. Мотивировка: без общего lifecycle каждый тестовый класс copy-paste'ит открытие браузера/логин/закрытие — правка в одном месте невозможна (см. «Без паттерна» для Template Method, `design-patterns.md` #7). Теория: TestNG lifecycle-аннотации, наследование `BaseTest`. Тег: java, testng.
- **P6-T2 — Listener на падение теста (скриншот).** TestNG `@Listeners`, `onTestFailure` → скриншот. Мотивировка/паттерн: Observer (`design-patterns.md` #9) — TestNG не знает и не заботится, что делает листенер. Тег: java, testng.

## Фаза 7 — Слой API-сервисов

Зависимость: опирается на Фазу 1 (конфиг/URL). Независима от Фаз 3–6 (UI), но используется тестами из Фазы 6+ для setup/teardown.

- **P7-T1 — RestClient адаптер + первый API-сервис.** Обёртка над REST Assured (адаптер, как GPElement над Selenide), один сервис под реальный эндпоинт `automationexercise.com` API. Мотивировка: без адаптера каждый вызывающий код собирает REST Assured запрос заново — дублирование, и миграция HTTP-библиотеки требует правки везде. Теория: REST Assured базовый синтаксис (`given().when().then()`), паттерн Adapter повторно на новом слое. Тег: java, rest-assured.
- **P7-T2 — Модель через record/@Builder + Factory для тестовых данных setup.** Модель ответа/запроса, фабрика с преднастроенными вариантами (по образцу `ClinCardProgramFactory`). Мотивировка: без фабрики каждый тест вручную собирает объект с нуля — дублирование сборки. Теория: `record` vs Lombok `@Builder`, паттерн Factory (`design-patterns.md` #8). Тег: java, rest-assured.

## Фаза 8 — Продвинутые тестовые данные

Зависимость: опирается на Фазы 2 (утилиты) и 7 (модели/фабрика). Готовит почву для параметризованных тестов в Фазе 6+/9.

- **P8-T1 — @DataProvider + параметризованный тест.** Реальный параметризованный сценарий на 2 сайта API/фичи. Теория: TestNG `@DataProvider`, отличие от JUnit `@ParameterizedTest`. Тег: java, testng.
- **P8-T2 — Внутренний static-класс состояния сценария (по образцу ParticipantState).** Только если реальный сценарий framework’а того потребует (≥3-4 связанных сущности на один прогон) — не делать искусственно ради галочки. Мотивировка: без группировки — десятки плоских полей вместо `Map<Integer, State>` по индексу сценария. Тег: java.

## Фаза 9 — Слой БД

Зависимость: опирается на Фазу 1 (конфиг коннекта) и (для тестов) на Фазу 6.

- **P9-T1 — Docker Postgres + сид-данные.** Локальный контейнер, схема, сид под сценарии фреймворка. Тег: sql, docker.
- **P9-T2 — DatabaseConnectionUtil (JDBC) + `executeQuery` → `List<Map<String,String>>`.** По образцу боевого `DatabaseConnectionUtil.java` (без AWS IAM auth — локальный Postgres, простой user/password). Мотивировка: без этого слоя SQL-верификация в тестах невозможна — assert может опираться только на то, что видно в UI/API. Теория: JDBC `try-with-resources`, `Connection`/`Statement`/`ResultSet`. Тег: java, sql.
- **P9-T3 — SQL-верификация в реальном тесте.** Тест создаёт запись в локальной схеме через `executeUpdate` (эмулирует то, что в боевом проекте делает API-setup) и проверяет результат отдельным SQL-запросом через `executeQuery` — по механике как `ClinCardMergeProfilesI2cEUOnlyTest`, но на своей изолированной схеме, а не на данных `automationexercise.com` (публичный сайт своей БД не отдаёт — см. «Открытые решения» п.2). Тег: java, sql, testng.

## Фаза 10 — Test Coverage (реальный regression suite)

Зависимость: опирается на весь стек Фаз 1–9 (POM, Reusable Actions, BaseTest, API-сервисы, БД-слой уже готовы — здесь на них пишутся содержательные тесты). От неё зависят Фазы 11 (Allure) и 12 (параллелизация) — им нужно несколько реальных тестов, а не один демонстрационный, чтобы отчёт и parallel-конфиг были осмысленными, а не пустой витриной.

- **P10-T1 — Регистрация/логин: 2–3 сценария.** Happy path + минимум один негативный (например, невалидные креды), поверх POM/ReusableActions из Фаз 4–5. Тег: java, selenide, testng.
- **P10-T2 — Поиск + корзина: 2–3 сценария.** Поиск товара, добавление в корзину, переход к оформлению — новые POM по необходимости, уже по устоявшемуся паттерну Фазы 4. Тег: java, selenide, testng.
- **P10-T3 — API CRUD (продукт/пользователь): несколько тестов.** Поверх API-сервисов из Фазы 7, включая setup/teardown через API (не через UI). Мотивировка: закрывает тот же принцип «UI проверяет UI, setup — через API» из `framework-layer-definition.md` (слой 4). Тег: java, rest-assured, testng.

## Фаза 11 — Allure-отчётность

Зависимость: опирается на Фазу 6 (lifecycle) и Фазу 10 (несколько реальных тестов — есть что документировать шагами, а не один прогон).

- **P11-T1 — Allure Steps + Attachments + скриншот при падении в отчёте.** Мотивировка: без шагов в отчёте падение теста показывает только stack trace, а не «на каком бизнес-шаге» упало — долгая диагностика. Тег: java, allure.

## Фаза 12 — Параллелизация и потокобезопасность

Зависимость: опирается на Фазу 6 (полноценный BaseTest + драйвер) и Фазу 10 (без нескольких независимых тестов параллельный прогон нечего демонстрировать).

- **P12-T1 — ThreadLocal-драйвер + parallel-конфиг в testng.xml.** Мотивировка: без ThreadLocal при параллельном прогоне все потоки делят один WebDriver — тесты случайно кликают в чужом браузере. Теория: `ThreadLocal<T>`, TestNG `parallel="methods"/"classes"`. Тег: java, testng.

## Фаза 13 — CI/CD на Jenkins

Зависимость: опирается на всё вышестоящее (нужен рабочий прогон, который CI будет запускать).

- **P13-T1 — Jenkins в Docker + декларативный Jenkinsfile.** Параметризованная job, публикация Allure-отчёта как артефакта/plugin. Тег: jenkins, docker.

## Фаза 14 — Финальный проход по паттернам

Зависимость: опирается на весь фреймворк (Фазы 0–13 закрыты).

- **P14-T1 — Карта «какой паттерн где применён».** Заготовка на 60 секунд под интервью (по образцу секции «Как отвечать на собеседовании» в `design-patterns.md`), но на СВОЁМ фреймворке — свои ссылки на код. Тег: interview-prep.

## Идея для будущего веб-приложения (не в рамках этого проекта)

Зафиксировано 2026-07-23 при обсуждении решения №2 («БД-тесты»): текущее ограничение — публичные demo-сайты не дают доступа к своей БД, поэтому слой БД в Фазе 9 вынужденно самостоятельное упражнение, не сквозной UI→API→БД сценарий. Для будущего веб-приложения (см. `STARTING-PROMPT.md`, «Связка с будущим веб-приложением») стоит рассмотреть постройку **собственного учебного веб-сервиса** со сложной микросервисной архитектурой, публичным API и доступной схемой БД — тогда подход UI → API → Database работает по-настоящему сквозным образом, без компромиссов, на которые пришлось пойти здесь.

## Как читать этот план

- Задачи внутри фазы обычно последовательны; фазы 3↔4, 7↔8 частично можно чередовать по факту (например, начать API-сервисы раньше, чем закончить все Page Object) — не жёсткая стена, решаем по ходу.
- П8-T2 и любые задачи с пометкой «только если потребуется» — не делать искусственно ради количества; framework должен зеркалить `java-selenide-pp` там, где это оправдано реальным сценарием, а не механически копировать каждую деталь.
- Полная схема-урок (Описание / Место в фреймворке / Мотивировка / Теория / DoD / Типичные ошибки / ссылка на `java-selenide-pp`) создаётся в `curriculum/` в момент, когда задача реально даётся Денису — не заранее.
